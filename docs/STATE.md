- **Task 21 완료 — 동시성·EOS 둘 다 늘리고/꺼서 재측정, 천장 안 밀림·원인 미확정** — Task 20 이 1순위로 지목한 고정 동시성 상한 세 곳을 측정 전용 설정 손잡이로 열고(payment-service `ConfirmedEventConsumer` 리스너 동시성 `payment.kafka.events-confirmed.consumer.concurrency` 신설, pg-service `pg.outbox.channel.worker-count`/`pg.inbox.channel.worker-count` 를 yml 리터럴에서 env override 가능하게 전환 — 기본값은 전부 현재 운영 동작과 동일, `./gradlew test` 전체 통과 확인) `CONFIRMED_CONSUMER_CONCURRENCY=3`·`PG_INBOX_WORKERS=20`·`PG_OUTBOX_WORKERS=5` 로 올려 재측정했으나 잔류 비율(r75 3.36%/r100 2.87%)이 기존과 통계적으로 동일했다 — 고정 동시성 상한 가설은 틀렸다. 처음엔 payment-service CPU 컨테이너 **최댓값** 상승을 근거로 "호스트 총 CPU 공유"를 다음 후보로 적었으나, 오케스트레이터가 그 근거(독립 최댓값의 합은 동시 포화의 증거가 아니다 — Task 20 이 CPU 후보를 반박할 때 쓴 논리와 동일)를 지적해 정정했다 — 전 컨테이너 CPU **평균의 합**은 116~146%(10코어 중 1.2~1.5개)로 포화와 거리가 멀다. 이 지적을 받아 `bench-scaleout-cycle.sh` 의 자원 표본화에 **처음부터 빠져 있던 kafka 컨테이너**(CPU·메모리·네트워크·디스크)와 전용 비운영 토픽에 대한 Kafka 발행 지연 프로브(`kafka-producer-perf-test acks=all`)를 추가해 같은 두 지점을 다시 찍었다 — Kafka CPU 도 최대 122%(1.3코어)로 여유였지만 발행 지연은 idle 기저선(137~143ms) 대비 도착률이 높을수록 더 튀었다(r75 +38ms/r100 +63ms·최대 552ms). 이 신호가 이 토픽 설계 문서와 Task 17 이 남긴 "메시지 커밋 직렬화" 후보와 결이 맞아, EOS 트랜잭션(메시지당 begin/sendOffsetsToTransaction/commit 4단계 브로커 왕복)을 1회성으로 꺼서(`payment.kafka.diagnostic.eos-enabled` 임시 플래그 — 결과를 본 뒤 코드는 `git checkout` 으로 되돌리고 이미지도 원상태로 재빌드, 커밋에 안 남음) r100 을 재측정했다. 잔류 비율이 3.35%로 EOS 켠 상태(3.32%)와 역시 통계적으로 동일했다 — **EOS 직렬화 가설도 배제됐다.** 최종 결론은 "이 환경에서 손댈 수 있는 설정 손잡이(동시성·워커 수·EOS)로는 더 못 민다"이지 "호스트 CPU 때문"이 아니다 — CPU 총량이 원인이라는 근거(실제로 그 총량에 닿는 관측)가 없어 원인을 이 토픽 범위에서 확정하지 못한 채 반복을 멈춘다. 다음은 설정 조정이 아니라 요청당 처리 경로 프로파일링(범위 밖). 상세는 PLAN Task 21 완료 결과
- **Task 21 종료 — 고정 도착률로 능력을 집고 판정선을 계산했다** — 오케스트레이터가 "지금까지의 판정이 부하 종료 후 최종 수치만 봐서, 부하 도중 적체가 계속 쌓이는지를 못 봤다"고 지적해 `bench-scaleout-cycle.sh`에 부하 구간 동안만(정산 대기 전 멈춤) 미종결 건수를 10초 간격으로 재는 `backlog_trend` 표본화를 추가했다. 기준 구성(인스턴스 1)에서 60/70/80 req/s 세 점을 각 3분 고정 도착률로 찍은 결과 r60 은 적체가 특정 대역(170~214)에서 진동하다 부하 중 자연 감소(PASS)했지만 r70/r80 은 저점 이후 부하 구간 대부분 거의 단조로 쌓였다(각 63건/514건 영구 미종결) — **단일 인스턴스 지속 가능 능력은 60~70 req/s 사이**로 좁혔다. 이전까지 "천장 84~88 req/s"로 불러온 값은 과부하 지점의 배출 속도였지 지속 가능한 능력이 아니었다. 능력을 넘는 r100 을 인스턴스 1대·2대로 같은 조건에서 재측정(인스턴스 유지는 healthy+Eureka 로그와 consumer group client-id 분할로 확인)해 확정 처리율 비를 냈다 — **0.80x, 판정선(1.6배)에 크게 미달, 그것도 역방향(2대가 1대보다 처리율도 낮고 적체 최댓값도 더 컸다)** — 이 토픽의 판정선을 유효한 조건에서 유일하게 계산했다. 측정 중 2인스턴스 첫 시도가 `Too many connections`로 죽는 것을 겪어 원인 규명(`docker-compose.scaleout.yml`이 `docker-compose.benchmark.yml`의 mysql-payment `command`(max_connections=300)를 compose 의 command-배열-비병합 특성 때문에 통째로 덮어써 실제로는 MySQL 기본값 151로 돌고 있었다 — Task 7 이래 두 파일을 함께 쓴 모든 라이브 측정이 그 상태였다) 후 원장 정합(DONE↔COMMITTED/READY↔NOISE 1:1)을 먼저 확인하고 compose 파일을 고쳤다(Rule 1). 지목 가능한 후보(동시성·워커 수·EOS·발행 실행기 상한·CPU·잠금·블록·복제 지연·Kafka 브로커) 전부를 배제 목록에 넣고 원인은 이 토픽 범위 밖(요청당 처리 경로 프로파일링 또는 공유 자원 자체 확장)으로 남긴 채 반복을 닫는다. 상세는 PLAN Task 21 최종 정리
- **인프라 기동 상태** — gateway/product-service/user-service, mysql-payment/replica/pg/product/user, eureka, kafka, redis-dedupe/stock, redis-idempotency-cluster 3대, redis-stock-cluster 1대(Task 21 마지막 구성), 관측 스택(prometheus/grafana/kafka-exporter/tempo/loki/promtail) 기동 유지. alertmanager는 이 태스크 착수 전부터 이미 정지 상태였다(Exited, 이 태스크가 원인 아님 — 웹훅 URL 미설정 추정, ship 단계 확인 대상으로 별도 기록). payment-service/pg-service는 Task 21 마지막 사이클(인스턴스 2대) 종료 후 정지된 채 남아 있다(다음 사이클이 재기동한다 — 다음 사이클이 INSTANCES 를 명시하지 않으면 compose 기본값 1대로 스케일된다). mysql-payment 는 이 태스크에서 발견한 `command:` 병합 결함 수정 이후 `max_connections=300` 이 실제로 적용된 상태로 재생성됐다(라이브 확인 완료). payment 원장 여섯 테이블은 빈 상태, 재고는 상수로 재시드된 상태, Kafka consumer lag(payment-service/pg-service 둘 다) 0 확인. Docker 메모리는 20GB(20480MiB)로 이미 상향 확인됨
