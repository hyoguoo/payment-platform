## 사전 브리핑

**상태**: 승인 대기 (남은 질문 있음)
**제안 규모**: 큼 (서비스 DB 스키마, 멱등성 계약, 클라이언트 키 보관이 함께 바뀐다)

### 목표

서버가 중단·재기동된 뒤, 실패한 요청이 Gateway까지 갔는지, payment 업무에 들어갔는지, 주문 DB에 저장됐는지 구분해 조사할 수 있게 한다.
같은 구매를 다시 요청하면, 저장된 주문은 그대로 돌려주고 저장되지 않았으면 새로 만들어 안전하게 복구되게 한다.

**판정**: 미정. 아래 "검증 기준 후보"를 바탕으로 정한다.

### 요구사항 (확정한 보장)

- R1. 같은 구매의 재요청은 커밋된 주문이 있으면 그 주문을 재사용하고, 저장되지 않았으면 새로 만든다. 저장되지 않은 주문을 재요청으로 만드는 것은 정상 복구이며, 조사가 끝날 때까지 복구를 막지 않는다.
- R2. 같은 구매의 다른 요청이 진행 중이거나 DB 확인이 실패하면 미저장으로 단정하지 않는다. 구매 키의 영속 연결을 확인하지 못했다는 이유로 다른 키로 새 구매를 시작하게 하지 않는다.
- R3. 주문 저장 전에 서버가 중단되고 로그까지 유실된 요청은 도달 여부를 "미확인"으로 남겨도 된다(개발자 허용). 별도 영속 도달 이력은 이 보장의 필수 범위가 아니다.
- R4. 관측된 도달 지점과 커밋된 주문의 저장 여부를 구분해 기록한다. 재요청으로 저장된 주문을 원래 실패 시도의 커밋으로 소급 판정하지 않는다.
- R5. 시간·경로만으로 동시 요청을 짝짓거나, 로그가 없다는 이유로 미도달을 확정하지 않는다.

### 지금 동작 (as-is)

- 관측: Gateway·payment에 trace 계측과 로그 설정이 있고, 주문 생성 로그에 주문 ID가 남는다. Promtail → Loki 수집 설정도 있다. 다만 클라이언트가 traceparent를 보내지 않는 일반 요청에서 서버가 만든 trace ID가 필요한 로그에 모두 이어지는지는 실행으로 확인하지 않았다(미확인). 기존 스모크는 클라이언트가 traceparent를 보내는 경로만 검사한다.
- checkout 로그: 시작 로그는 업무 코드 진입 기록이고, 주문 생성 로그는 DB 커밋 전 기록이다. 로그로 주문 ID를 찾은 뒤 DB와 대조해야 한다. confirm은 주문 ID를 알고 시작하므로 상태·outbox·이력을 조사에 쓸 수 있다. outbox가 없다고 미도달이 증명되지는 않고, 모든 202가 영속 접수를 확정하지도 않는다.
- 측정 도구: k6는 구매 시도와 멱등키를 기록하지만 서버 trace ID는 보관하지 않는다. 판정 도구는 주문 ID를 못 받은 경우 Redis 결과와 DB만 대조하고, 실행 구간의 서버 로그·trace를 원자료로 남기는 경로가 없다.
- 멱등성: checkout의 Redis 결과·잠금은 기본 10초 만료이고, 결과 저장이 DB 커밋보다 먼저 일어난다. 주문 DB에는 구매 키 연결이 없고, 같은 키로 다른 내용이 와도 대조하지 않는다. Redis 결과가 남아 있으면 같은 키의 기존 주문 ID와 금액을 돌려주므로, 별도 조회 API 없이 재요청으로 결과를 회수하는 출발점은 있다.

### 문제

부하 테스트 중 서버를 중단·재기동한 뒤, 실패한 요청이 어디까지 갔는지 알 수 없었다. 기존 관측은 있지만 실행 도구와 판정이 그것을 쓰지 않는다.
멱등성은 Redis 10초 결과에만 기대고 DB 커밋과 함께 확정되지 않아, 장시간 장애 뒤의 재요청을 안전하게 보장하지 못한다.

### 제안 방향

아직 확정이 아니다. 제품 계약, DB 배치, 새 API 도입은 결정하지 않았다.

1. 기존 관측 검증과 영속 멱등성 설계를 함께 진행한다. 일반 요청의 Gateway·payment trace 연결을 실행으로 확인하고, 주문과 구매 키를 같은 트랜잭션에서 확정하는 구조를 비교한다.
2. 같은 키·같은 구매 내용의 재요청은 커밋된 기존 주문을 돌려주고, 저장되지 않았으면 만들 수 있게 한다. 동시 요청이나 DB 조회 실패를 주문 부재로 보지 않는다.
3. 저장된 주문은 영속 구매 키 연결로, Gateway·payment 도달 지점은 기존 trace·로그로 조사한다. 개별 실패 시도와 trace를 잇는 최소 보완은 실행 검증 뒤 고른다.
4. 기존 checkout 재요청으로 충분한지 먼저 비교한다. 본문 없이 키만으로 조회하거나 도달 이력을 조회해야 한다는 요구가 생기면 그때 별도 조회 API를 검토한다.

영속 구매 키 연결은 안전한 재요청과 주문 저장 확인 양쪽에 쓸 수 있지만, 주문 저장 전 도달을 증명하지는 않는다. 구매 키 생성·보관은 클라이언트까지 이어져야 하므로 서버만 바꿔 완성됐다고 설명하지 않는다.

**독립 검토가 더한 설계 조건** (reviewer·domain-expert, 2026-10-15)

- DB 원자성: 구매 키 고유 제약과 주문·주문 항목의 같은 커밋. 경쟁에서 진 쪽이 만든 주문은 전체 롤백하고, 롤백된 트랜잭션 안에서 기존 주문을 다시 조회하지 않게 경계를 둔다.
- 커밋 전 결과: 지금 Redis 결과가 DB 커밋보다 먼저 보이므로, DB에 없는 주문 ID를 재요청 성공으로 돌려주는 경로를 없앤다.
- 내용 대조: 같은 키로 다른 사용자·상품·수량·결제수단이 오면 저장된 구매 내용과 비교하는 방안을 검토한다.
- 기존 주문 회수: 가격 변경이나 상품·사용자 조회 장애로 이미 확정된 결과의 회수가 막히지 않게 기존 주문 조회를 먼저 하는 방안을 검토한다.
- 재시도: DB 커밋 결과가 불명확하면 미저장으로 단정하지 않고 같은 키를 유지한다. 종결된 주문을 같은 키로 새로 만드는지의 계약을 확인한다.
- 클라이언트와 비노출: 지금 결제 화면은 구매 키를 보내지 않고, Redis 대기 초과 예외에 원문 키가 들어간다. 구매 키 계약의 적용 대상과 로그·오류 응답의 비노출을 확인한다.
- 구매 키는 여러 HTTP 재시도가 공유하므로 개별 시도 식별자와 구분한다.

| 멱등성 | 같은 구매의 동시 재요청, Redis 만료·유실, 서버 재기동 뒤에도 커밋된 주문 한 건과 같은 주문 ID 반환 |
| 부분 실패 | 커밋 전 실패면 주문과 구매 키 연결이 함께 롤백, 커밋 뒤 응답 유실이면 같은 키로 기존 주문 회수 |

| 회수 안정성 | 가격 변경·상품 조회 장애에도 기존 주문의 확정 ID·금액 반환, 구매 키 원문 로그 비노출 |
| 조사 결과 | Gateway 도달·payment 업무 진입·DB 저장을 각각 기록하고, 원래 실패 시도와 재요청의 증거를 구분 |

단위 테스트, DB·동시성 통합 테스트, 일반 요청 trace 실행 검증을 구분한다. DB·통합·관측 실행에는 Docker 로컬 환경이 필요하다.

### 결정이 필요한 질문

1. 요청 추적과 안전한 재요청을 한 토픽에서 할까 — **답**: 둘 다 이 토픽에서 한다. 선후 순서는 상관없다 (2026-10-15)
2. 로그·응답이 함께 유실된 요청을 미확인으로 남겨도 될까 — **답**: 허용한다. 별도 영속 도달 이력은 필수가 아니다 (2026-10-15)
3. 특정 테스트 실패 요청을 서버 trace와 정확히 짝지을 때 기존 정보로 충분한가, 어느 지점에 최소 보완이 필요한가 — **답**: 미결 (일반 요청 trace 실행 검증 뒤 정한다)
4. 구매 키 계약: 필수 여부, 보관 기간, 키 소지자의 접근 범위, 내용 충돌 정책 — **답**: 미결. 아래 "지난 논의의 사용자 선택"을 설계 입력으로 존중하되, 최신 범위와 충돌하거나 구현상 바꿔야 하는 부분만 다시 묻는다
5. DB 경합과 커밋 결과 불명 처리, 클라이언트의 키 보관과 재요청 방식 — **답**: 미결
6. 공개 조회 API, trace ID의 DB 저장, k6의 trace 생성이 각각 필요한가 — **답**: 미결. 필요를 검증한 뒤 고른다

### 개발자가 설명한 요구 (2026-10-15)

- 조사 목적: 서버 중단·재기동 뒤 요청 도달 지점과 실제 주문 저장 여부 확인
- 범위 점검: 기존 trace·로그·멱등성을 먼저 조사하고, 필요한 변경인지는 근거로 판단
- 문서 표현: 처리 흐름과 상황별 판단을 중심으로 쉽게 설명한다. 이해하기 어려운 토글이나 과한 추상화는 뺀다
- 작업 경계: 실제 부하 측정·성능 탐색은 별도 작업. 제외한 과거 보고서·수치를 공식 결과나 확정 요구로 다시 쓰지 않는다

### 이번 범위가 아닌 것

- 실제 부하 측정·성능 탐색 (PAYMENT-THROUGHPUT 토픽)
- 제외한 과거 보고서·수치를 공식 결과나 확정 요구로 다시 쓰는 것
- 근거 없이 공개 API나 새 인증 계약으로 범위를 넓히는 것

### 지난 논의 기록

**지난 논의의 사용자 선택 (2026-10-12~13)** — 과설계 점검 이전의 선택이다. 지금 구현의 확정 요구로 쓰지 않지만 없던 일로 만들지도 않는다.

- 대상과 목표: 접수 확인뿐 아니라 같은 구매의 안전한 재요청. 사용자·클라이언트도 쓴다. 이후 개발자가 "도달 확인이 출발점"이라고 설명해 범위를 다시 봤다.
- 구매 식별: 모든 checkout에 구매별 `Idempotency-Key` 필수. 새 구매는 새 키, 같은 구매는 기존 키 유지.
- 접근: 비공개 구매 키를 가진 요청의 조회·재요청 허용, 응답 최소화, 키 로그 비노출, 로그인 체계 제외.
- 보관: 주문 기록을 보관하는 동안 키 연결 유지. 시간이 지났다고 같은 키로 새 주문을 만들지 않는다.
- 충돌: 이미 접수된 키의 사용자·상품·수량·결제수단이 달라지면 거절하고, 변경 구매는 새 키를 쓴다.
- 실패 경계: 주문과 키 연결을 함께 커밋·롤백하고, 확정 전 실패한 요청의 최초 내용은 따로 보존하지 않는다.
- 재시도: 처리 중·DB 장애는 확인 보류, 같은 키로 제한된 자동 재시도 뒤 중단하고 키·내용 보관.

SHA-256 digest, fingerprint, 생성 시도 ID의 DB 저장, 새 조회 API 응답·트랜잭션 상세 배치는 에이전트의 기술 제안이었고 설계 본문에서 뺐다.

**작업 이력**: 측정 도구 준비는 #160 / PR #161로 main에 병합됐고 실제 측정은 별도 토픽(PAYMENT-THROUGHPUT)이다. discuss 당시 workflow 질답 지침 기준 커밋은 `07f5196c`다. 이 토픽의 이슈·구현 브랜치·계획은 아직 없다.

**철회한 추천** — 아래는 장애 조사 목적의 필수 변경이라는 추천을 철회했다. 모든 상황에서 불필요하다는 뜻이 아니라 이번 목적에 필요한 근거를 먼저 대지 못했다는 정정이다([과설계 기록](checkout-receipt-tracking-corrections.md)).

- k6에서 trace ID를 만들도록 변경
- 별도 HTTP 시도 ID 도입
- 주문 DB에 trace ID나 생성 시도 ID 추가
- 공개 접수 조회 API와 키 소지자 접근 체계 신설
- 추적 개선과 모든 클라이언트의 재요청 계약 개편을 한 구현 범위로 묶음
