요청 확인과 안전한 재요청을 함께 다룬다

두 목표를 한 토픽에서 진행한다. 어느 쪽을 먼저 할지는 고정하지 않았다.

01 · 요청 확인

어디까지 처리됐는지 확인

Gateway 도달, payment 업무 진입, 주문 DB 저장을 각각 확인한다.

02 · 안전한 재요청

같은 구매의 주문 중복 방지

이미 저장됐으면 기존 주문을 돌려주고, 저장되지 않았다면 주문을 생성한다.

03 · 증거 유실

도달 여부는 미확인 허용

서버가 꺼지고 로그까지 사라지면 도달을 단정하지 않는다. 그래도 같은 구매를 안전하게 재요청할 수 있어야 한다.

이 보고서에서 checkout은 주문 생성 요청이다. 주문 저장은 결제 승인 완료를 뜻하지 않는다. 결제 확정은 주문 ID로 보내는 별도 confirm 요청에서 진행한다.

현재 코드

추적과 중복 억제는 있지만, 장애 후 보장이 부족하다

요청을 확인하는 쪽

Gateway·payment의 trace와 로그, Promtail→Loki 로그 수집 설정은 이미 있다.

하지만 측정 도구는 실행별 서버 로그를 보존하지 않고, 특정 k6 실패 요청과 서버 trace를 정확히 연결하는 정보도 없다.

같은 구매를 다시 요청하는 쪽

구매 키와 주문의 연결은 Redis에 잠시 남는다. 결과와 처리 잠금의 기본 만료 시간은 10초다.

연결이 만료되거나 사라지면 DB에서 같은 구매를 찾지 못하고 새 주문을 만들 수 있다.

↓
주문 생성 처리 · 주문 ID 로그 출력DB 커밋(저장 확정) 전이므로 저장 완료 증거가 아님
↓
Redis에 주문 결과를 먼저 기록DB 커밋 전 · 기본 10초 뒤 결과 만료
↓ 이 사이에 종료·커밋 실패가 발생할 수 있음
주문 DB 저장 완료 → 주문 ID 응답DB 커밋이 성공한 신규 주문 경로

두 가지 실패가 가능하다. DB에는 없는 주문을 Redis 결과만 보고 반환하거나, 실제 주문은 저장됐는데 Redis 연결이 사라져 재요청 때 다른 주문을 만들 수 있다.

기존 Redis 결과를 바로 반환하는 중복 경로에서는 신규 주문 생성 로그를 다시 찍지 않는다. 일반 요청의 서버 생성 trace가 모든 필요한 지점에 이어지는지도 아직 실행 검증하지 않았다.

구현 방향 제안 · 미구현

같은 구매 키로, DB에 저장된 주문을 다시 찾는다

구매 키는 같은 구매를 다시 요청할 때 유지하는 값이다. 아래 K-1과 O-1은 구매 키와 주문 ID의 설명용 예시다.

DB가 마지막 중복 방지 기준이 된다. DB에서 같은 구매 키를 한 건만 허용하고, 키 연결과 주문을 함께 저장하거나 함께 취소하도록 설계한다. Redis는 DB 저장 완료의 증거를 대신하지 않는다.

기존 checkout은 이미 중복 요청에 기존 주문을 반환한다. 이 동작을 장애·만료 후에도 이어가는 방향이며, 테이블 배치와 동시 요청 처리 방식은 아직 정하지 않았다.

제안이 구현됐을 때의 결과

서버가 어느 시점에 꺼졌는지에 따라 결과가 달라진다

아래는 같은 구매 키와 같은 내용으로 재요청하는 경우다. 현재 서비스가 이미 이 보장을 제공한다는 뜻은 아니다.

주문 저장 전에 서버가 꺼짐

앞선 요청이 더 이상 진행 중이지 않고, DB에 같은 키의 확정 주문이 없는 경우

재요청으로 주문 생성
저장 확정된 기존 주문이 없으므로 구매를 이어간다.

원래 요청의 도달 여부는 로그가 없으면 미확인으로 남는다.

주문 저장 후 응답만 잃음

DB에는 K-1과 O-1이 저장됐지만 클라이언트는 응답을 받지 못한 경우

기존 O-1 반환
새 주문 없이 이미 저장된 결과를 회수한다.

Redis가 만료됐거나 서버가 재기동돼도 영속 연결로 확인한다.

같은 구매가 동시에 재요청됨

앞선 요청이 아직 처리 중이거나 같은 키의 여러 요청이 겹친 경우

중복 주문 확정 방지
DB에서 한 건만 확정하고 기존 결과 회수 또는 재시도 가능한 상태로 처리한다.

대기 시간과 응답 방식은 상세 설계에서 정한다.

DB 상태를 확인할 수 없음

DB 조회 실패나 커밋 결과 불명으로 기존 주문 유무를 모르는 경우

새 주문 생성을 확정하지 않음
같은 구매 키를 유지하고 확인·재요청 가능 상태로 둔다.

“조회 실패”를 “주문 없음”으로 바꾸지 않는다.

이미 주문과 함께 확정된 키로 구매 내용을 바꾸면 충돌로 처리한다. 과거에 선택한 사용자·상품·수량·결제수단 변경 거절을 설계 입력으로 유지하며, 내용 비교와 오류 응답의 상세를 정한다.

재요청으로 새 주문이 생성됐다고 해서 원래 실패 요청이 저장됐다고 판정하지 않는다. 기존 주문이 결제 실패·만료 상태인 경우의 재구매 계약도 상세 설계에서 다룬다.

증거로 확인 · 유실되면 미확인 허용

요청 도달과 주문 저장은 각각 확인한다

구매 키는 같은 구매를 찾는 값이다. trace는 서버 처리 경로를 따라가는 값이며, 하나의 trace에 여러 요청이 포함될 수도 있다. 구매 키만으로 개별 요청의 도달 지점을 알 수는 없다.

먼저, 이 실패 요청의 서버 기록을 정확히 식별해야 한다현재 k6 시도와 trace의 연결 방식은 미결 · 식별하지 못하면 해당 요청의 도달은 미확인

해당 요청의 기록을 식별한 경우에만 아래 로그로 도달을 판단한다. 주문 저장 여부는 주문 ID나 제안의 영속 구매 키 연결로 따로 확인한다.

Gateway까지 왔나?

해당 요청의 Gateway 수신 로그

발견하면 그 기록 지점의 도달을 확인한다. 로그가 없다는 이유로 미도달을 확정하지 않는다.

payment 업무까지 들어갔나?

checkout 시작 로그

발견하면 주문 생성 업무 진입을 확인한다. HTTP 수신 전체를 증명하는 로그는 아니다.

주문이 실제 저장됐나?

커밋된 주문 DB 기록

현재는 주문 ID로 대조한다. 제안 구현 후에는 영속 구매 키 연결로도 저장된 주문을 찾는다.

예시: payment 시작 로그는 있지만 주문 ID를 찾지 못함

payment 업무 진입 확인 / DB 저장 여부 미확인

확인한 증거는 남긴다. 주문 저장 여부를 몰라도 이미 확인한 도달 지점은 지우지 않는다. Gateway 로그가 없어도 payment·DB 조사는 계속한다.

비슷한 시각·경로만으로 요청을 짝짓지 않는다. DB는 원본 DB(primary)에서 조회 시점과 함께 확인하며, 진행 중인 요청이 나중에 저장될 가능성도 고려한다.

다음 설계·검증 제안

서버·클라이언트·조사 도구를 함께 맞춘다

아래는 작업 묶음이다. 실행 순서나 구현 계획의 확정 목록은 아니다.

  1. 서버: 구매 키와 주문을 함께 확정

    같은 키의 중복 저장 방지, 구매 내용 비교, 동시 요청·저장 실패 처리를 설계한다. 기존 주문을 회수할 때 현재 상품 가격이나 조회 장애에 막히지 않도록 한다.

  2. 클라이언트: 같은 구매 키를 계속 보관

    같은 구매의 재요청에는 같은 키를 보내고, 새 구매에는 새 키를 사용한다. 현재 결제 화면은 키를 보내지 않으므로 이 경로도 보완 대상이다. 재시도는 제한하고 키·구매 내용은 유지한다.

  3. 조사 도구: 기존 관측을 검증하고 원자료 보존

    클라이언트가 traceparent를 보내지 않은 일반 요청의 trace 연결을 확인한다. 실행 구간·인스턴스별 서버 로그를 보존하고 실패 요청과 서버 기록의 정확한 연결 방식을 선택한다.

Redis 만료·유실동일 키 동시 요청같은 키의 내용 충돌커밋 전 서버 중단커밋 후 응답 유실DB 확인 실패구매 키 비노출

추가 장치는 필요에 따라 선택한다. 별도 공개 조회 API, trace ID의 DB 저장, k6의 trace 생성은 확정된 필수 변경이 아니다. 별도 영속 도달 이력 없이도 미확인 허용과 안전한 재요청이라는 목표를 설계할 수 있다.

구매 키 계약·보관 기간·접근 범위는 과거 사용자 선택을 설계 입력으로 존중하고, 최신 범위와 충돌하거나 구현상 변경이 필요한 부분만 다시 논의한다.

검증 경계: 현재 동작은 코드 정적 점검과 독립 코드·도메인 검토에 근거한다. 제안은 미구현이며 일반 요청의 trace 연속성·Loki 실수집·장애 시 재요청 보장은 아직 실행 검증하지 않았다. 실제 부하 측정·성능 탐색은 별도 작업이다.
