# 접수 추적 논의의 과설계 및 설명 정정 기록

> 기록일: 2026-10-15 · 작성 주체: 이 작업을 진행한 assistant · 사용자 요청에 따라 보존

## 무엇을 잘못 판단했는가

사용자의 출발점은 부하 테스트에서 서버를 중단했다가 살린 뒤 요청이 어디까지 처리됐는지 확인하기 어려웠다는 문제였다.
assistant는 기존 trace·로그와 판정 도구가 실제로 사용하는 정보를 충분히 조사하기 전에 해결책을 확대했다.
영속 멱등키, 공개 접수 조회 API, 키 소지자 접근, 클라이언트 개편, 별도 시도 ID와 DB 저장까지 한 토픽에 쌓았다.
이 중 일부는 안전한 재요청이라는 별도 목표에는 의미가 있지만, 원래 장애 조사 목적에 필요한 최소 범위라는 근거는 제시하지 못했다.

사용자가 질답에서 안전한 재요청과 사용자용 기능을 선택한 사실은 보존한다.
그러나 assistant가 추천한 선택지에 동의했다는 사실로 초기 목표와 대안의 차이를 충분히 설명할 책임이 사라지지는 않는다.
범위를 확대하고 이를 다시 최소안처럼 설명한 책임은 assistant에게 있다.
이번 기록은 사용자의 요구가 잘못됐다는 평가가 아니다.

## 구체적인 오류와 정정

| assistant의 판단·설명 | 문제 | 정정 |
| :---: | :---: | :---: |
| 접수 추적을 영속 멱등성·공개 복구 API와 한 설계로 확대 | 기존 관측의 부족한 지점을 먼저 확인하지 않았고 목적별 비용을 분리하지 않음 | 장애 조사, 중복 방지, 사용자 복구를 별도 목표로 구분 |
| 기존 추적을 잇기 위해 새 식별자나 k6 trace 생성을 먼저 추천 | 기존 trace 기능과 서버 생성 경로의 검증 범위를 조사하지 않음 | 기존 계측은 존재하며 실제 누락과 연결 요구를 확인하기 전 필수 변경으로 추천하지 않음 |
| 주문 DB에 trace ID 저장을 최소안에 가까운 방식으로 제시 | 로그 활용으로 해결되는 범위와 추가 영속성이 필요한 요구를 구분하지 않음 | DB 컬럼은 필수 추천에서 제외. 요청별 영속 연결이 필요한 요구가 별도로 확정될 때 비교 |
| 기존 trace로 이미 연결된다고 단정했다가 사용자의 지적에 따라 설명 변경 | 서버 내부 trace와 k6의 개별 실패 요청 연결을 혼동하고 실행 검증 없이 확정적으로 설명 | 계측의 존재, 일반 요청의 실행 연속성, 테스트 시도와의 대응을 각각 구분 |
| 클라이언트 trace 생성 설명에서 사실관계보다 사용자의 반응에 맞춰 결론 변경 | 서버 생성과 클라이언트 시작 모두 가능한데 필요성 판단과 기술적 가능성을 섞음 | k6 생성은 가능하지만 필수는 아님. 기존 서버 생성 방식을 바꿔야 한다는 근거 없음 |
| 원래 결과를 조사한 뒤 재요청하도록 권고 | 원래 구매를 완료하려는 사용자 의도보다 조사 편의를 앞세움 | 미저장 주문을 재요청으로 생성하는 것은 정상 복구. 조사 완료를 구매 복구의 필수 선행 조건으로 두지 않음 |
| 새 설계의 안전한 흐름을 보고서의 중심으로 제시 | 기존 동작·추가 제안·미검증 사실을 읽는 사람이 구분하기 어려워짐 | 현재 동작과 조사 흐름을 중심으로 전면 교체하고 가정·한계는 해당 그림에 표시 |
| 기술 검토에서 설계 논리가 성립한다는 판단을 범위의 적정성 근거처럼 사용 | 특정 보장을 구현할 수 있는 것과 지금 그 보장이 필요한 것은 별개 | 독립 검토와 사용자 목적의 적합성을 별도로 판단 |

## 다시 조사해 확인한 근거

기존 Gateway·payment tracing과 주문 ID 로그가 이미 존재한다.
현재 품질 판정기는 주문 ID가 없으면 Redis 결과와 DB만 대조하고 서버 로그·Tempo는 사용하지 않는다.
실행 도구도 서버 로그·trace를 실행 원자료로 수집하지 않는다.
기존 trace 스모크는 클라이언트가 traceparent를 넣어 보낸 경우를 검사하며, 일반 요청의 서버 생성 경로까지 검증한 것은 아니다.

이 사실들은 새 추적 시스템이 필요하다는 결론보다 기존 관측을 먼저 확인하고 활용해야 한다는 판단을 뒷받침한다.
동시에 로그를 잃은 요청을 모두 복원할 수 있다는 주장도 뒷받침하지 않는다.
코드 위치와 해석 한계는 [코드 점검 결과](checkout-receipt-tracking-review.md)에 기록했다.

## 이번 수정에서 바꾼 것

- 플로우 보고서: 미구현 복구 시스템의 정상 작동 설명을 현재 요청 흐름·현 판정 방식·조사 가능한 증거 중심으로 교체
- 코드 점검 결과: 과거 설계를 전제로 한 효율·안전성 결론을 제거하고 코드 사실과 미검증 범위를 정리
- discuss 문서: 최신 문제와 미결 사항을 앞에 두고, 과거 사용자 선택을 별도 이력으로 보존
- STATE: 오래된 설계 권고와 반복 기록을 정리하고 현재 재개 지점으로 갱신

서비스 코드, 데이터베이스 구조, 테스트 도구는 변경하지 않는다.
과거 측정 수치는 공식 결과로 복원하지 않으며 로컬 원자료도 그대로 보존한다.

## 이후 판단 기준

새 변경을 추천할 때는 현재 코드의 기능, 실제 관측 결과, 아직 검증하지 못한 부분을 먼저 구분한다.
사용자에게 필요한 보장과 그 보장을 위해 드는 변경을 함께 설명하고, 기존 장치로 해결할 수 없는 구체적인 실패 조건을 제시한다.
trace 존재를 DB 커밋으로, 로그 부재를 미도달로, 설정 존재를 실행 검증으로 바꿔 설명하지 않는다.
미확인 구간을 허용할 수 있는지 결정하기 전에 이를 없애기 위한 새 영속 시스템을 전제하지 않는다.
독립 검토와 문서 작성 완료는 사용자 합의나 discuss 완료를 대신하지 않는다.
