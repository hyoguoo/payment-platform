# 결제 처리량 측정과 개선 — 합의

> 토픽: PAYMENT-THROUGHPUT · 시작 2026-10-28 · 합의 갱신 2026-10-29 · discuss 완료

## 목표와 범위

로컬 Fake PG 환경에서 현재 서버의 처리 한계를 찾고, 실측 병목을 수정한 뒤 한계가 얼마나 올라가는지 비교한다.
같은 부하에서 지연만 줄였다고 완료하지 않는다. 첫 병목 개선 이후에도 다음 포화 위치를 확인하며 반복한다.
요청 추적·안전한 재요청 토픽은 별도로 유지한다. 성능 변경이 해당 경로에 영향을 주면 필요한 회귀 검증을 포함한다.
구현·로컬 검증과 추적 이슈 생성은 사용자 요청 범위다. 2026-10-29 후속 요청으로 문서 보완과 로컬 커밋까지 포함했다.
푸시·PR 게시·병합은 요청 범위에 포함하지 않는다.

새 제품 동작이나 범위 결정이 필요한 경우에만 사용자에게 질문한다.

## 두 시험과 비교 원칙

| 시험 | 부하 구성 | 확인할 것 |
|:---:|:---:|:---:|
| 서버 처리 용량 | checkout·confirm 요청 주입과 완료 관측을 분리하고 전수 상태 폴링 제외 | 실제 유입·DB 완료 처리율·대기 증가·부하 종료 후 해소 시간 |
| 사용자 품질 | 같은 구매의 상태를 실제 화면처럼 1초 간격·최대 30회 조회 | 접수 응답과 사용자가 완료를 확인하는 시간 |
| 기존 500ms 조건 | 기존 500ms·60초 관찰 정책을 별도 재현·스트레스 조건으로 보존 | 조회 부하가 처리량과 지연에 미치는 영향 |

두 시험은 각각 낮은 부하부터 올리며 정상·지연 허용·과부하 구간을 찾는다.
주입이 완료 관측 슬롯에 막히지 않도록 하고, 발생기 자원·요청 누락도 기록한다.
폴링 정책이 다른 회차끼리 개선 배수를 계산하지 않는다. 새 방식은 수정 전 기준부터 다시 측정한다.
기존 `async-payment.js`의 분리 패턴은 참고할 수 있지만 benchmark 설정·판정 기준을 그대로 혼용하지 않는다.

## 합의한 결제 성능 기준

대상은 사용자 인증을 마친 뒤의 카드·간편결제 승인 처리에 해당하는 흐름이다.
인증·3DS·입금 대기를 승인 처리 시간에 섞지 않는다. Fake PG 지연은 기존 100~300ms를 유지한다.
아래 수치는 공식 사례를 참고해 합의한 이 프로젝트의 초기 목표이며 업계 공통 표준이나 외부 PG의 성능 보장이 아니다.

| 항목 | 기준 |
|:---:|:---:|
| checkout 응답 | p95 500ms 이하 |
| confirm 접수 응답 | p95 500ms 이하 |
| 사용자 완료 확인 | confirm 요청 시작부터 p95 3초 이하·p99 5초 이하 |
| 사용자 조회 정책 | confirm 응답 후 실제 화면과 같은 1초 간격·최대 30회 |
| 정상 Fake 시험 | API 오류·주문/승인/재고 불일치 관측 0건, 전수 대조 |
| 유효 유입 | 요청 누락 0, 실제 시작률과 예정률 대조, 발생기 포화 없음 |

사용자 조회 종료와 백엔드의 추가 완료 관찰을 분리한다.
조회 종료 뒤 완료된 주문을 사용자 기한 내 성공으로 소급하지 않는다.
DB 완료 이력과 product 재고 반영을 전수 대조하며, 표본만 관측한 지표는 표본임을 명시한다.
접수 응답, DB 완료, 사용자 관측 완료, 재고 반영의 이름과 시간 경계를 구분한다.

## 처리 구간과 한계 판정

| 구간 | 판정 근거 |
|:---:|:---:|
| 품질 목표 충족 | 유효 유입·정합성·접수 및 완료 지연 목표 충족 |
| 지연 허용 지속 처리 | 지연 목표는 넘지만 유입을 유지하며 완료 처리율·잔량·메모리가 관측 구간에서 안정 |
| 일시 폭주 흡수 | 부하 중 잔량이 계속 늘고 요청을 멈춘 뒤에야 해소 |
| 측정 미확정 | 요청 누락·발생기/호스트 포화·접수 미확인·증거 누락 등으로 서버 한계 분리 불가 |

단순히 모든 주문이 나중에 완료됐다는 이유로 지속 가능한 TPS로 판정하지 않는다.
5초 초과만으로 지속 처리 불가라고 판정하지도 않는다.
미확인·미종결 주문은 유실로 단정하지 않고, 관찰 기한과 남은 작업을 보고한다.
Kafka raw lag에는 TX 완료 표식이 포함될 수 있으므로 업무 적체와 구분한다.

## 실험 순서와 완료 조건

각 조건을 3분 탐색하고, 부하를 올려 통과·미달 경계를 좁힌다.
후보 한계는 10분 지속 시험으로 확인하고 초기 구간과 후반 추세를 구분한다.
80·100·120·160건/초는 시작 탐색 지점이며 실제 유입·완료·발생기 상태에 따라 조정한다.
수정 전 기준을 확보한 뒤 첫 병목 하나만 변경하고, 같은 두 시험으로 한계를 다시 찾는다.
관측된 코드 병목의 개선 또는 보류 근거와 자원 한계·효과 정체가 설명될 때 반복을 마무리한다.

최종 결과에는 다음을 함께 적는다.

- 수정 전후 최고 품질 통과 TPS와 지연 허용 지속 처리 TPS, 처음 미달한 부하와 탐색 해상도
- 실제 유입률·부하 중 DB DONE 처리율·완료 p95/p99·잔량 추세·종료 후 해소 시간
- 첫 포화 위치, 실제 변경, 정합성·실패/복구 검증, 남은 한계
- 시험 기간 안에서 확인한 처리량임을 명시하며 로컬 결과를 운영 보장으로 확대하지 않음

## 환경·증거·검토

매 본측정 회차는 새 프로젝트·새 컨테이너·새 볼륨으로 시작한다.
빈 DB·Redis·Kafka 확인 → 상품 100종 동일 재고 시드 → 10건/초·120초 워밍업 → 본측정 순서다.
워밍업과 본측정만 한 환경을 공유한다. 기존 데이터·볼륨·원자료는 보존하고 미처리 상태에서 재시드하지 않는다.
서버 자원·Fake PG·내구성·로그/트레이스·부하 구성은 수정 요소 외 동일하게 맞춘다.

행동 변경은 실패 테스트부터 구현한다. reviewer는 설계·코드·완료 검토를 독립 수행하고,
상태·멱등성·보상·동시성·PG 실패 경로 변경에는 domain-expert도 포함한다.
사용량·도구 제한으로 독립 검토가 불가능하면 메인이 대조하고 미실시를 구분한다.
의미 있는 원자료와 실제 런타임 설정·소스 해시를 보존하며, 실행 중 소스 변경을 숨기지 않는다.

## 현재까지 확인한 사실

| 회차 | 관측 | 해석 |
|:---:|:---:|:---:|
| 기존 80/s·180초, 동시성 1 | 14,400건 완료, 누락 0, 완료 관측 p95 1,553ms | 기존 500ms 조건의 짧은 탐색 통과 |
| 기존 80/s·180초, 동시성 3 | 14,401건 완료, 누락 0, 완료 관측 p95 544ms | 한 쌍에서 지연 감소 관측, 기본값 채택·최대 TPS는 미확정 |
| 기존 160/s·180초, 동시성 1 | 28,800건 예정 중 10,062건 시작·전부 완료, 누락 18,738 | 목표 160/s 유입 유지 실패, 서버 상한으로 확정 불가 |

160/s 회차의 접수 p95는 694ms, 완료 관측 p95는 16,738ms·최대 21,680ms다.
결과 lag 표본 최대 628·payment DB 연결 대기 표본 최대 411도 관측됐다.
이전 실행은 원래 판정과 설정으로 보존하며 새 합의 목표로 자동 재판정하지 않는다.
상세 이력은 [PLAN 실행 기록](../PAYMENT-THROUGHPUT-PLAN.md#실행-기록)과 [실측 보고서](../reports/tps-clean-measurements.html)에 있다.

## 기준의 외부 근거

- [PayPal 통합 모니터링 예시](https://developer.paypal.com/checkout/integrate#post-launch-monitoring): 주문 생성 2초 미만·capture 3초 미만. 보장·SLA·p95 기준이 아니다.
- [Stripe 상태 확인](https://docs.stripe.com/payments/payment-intents/verifying-status): 웹훅 활용과 반복 조회의 신뢰성·호출 제한 주의. PG→서버 웹훅과 브라우저 표시 수단은 별개다.
- [Stripe 결제수단 구분](https://docs.stripe.com/payments/payment-methods): 즉시 결과와 지연 결과 결제수단을 구분한다.
- 실제 UI 조회 정책: `payment-service/src/main/resources/static/payment/success.html`.
