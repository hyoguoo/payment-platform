# PAYMENT-THROUGHPUT — 결제 처리량 한계 측정과 병목 개선

> 개발자가 읽고 승인한 문서다. 측정 회차는 [EXPERIMENTS](EXPERIMENTS.md), 측정 도구와 코드 태스크·재개 메모는 [DESIGN](DESIGN.md)에 있다.
> 2026-10-28~29에 옛 형식(합의 문서 + PLAN)으로 진행했고, 2026-11-06 지침 개편(#163)에서 내용을 그대로 이 형식으로 옮겼다.

## 사전 브리핑

**상태**: 승인됨 (2026-10-29)
**제안 규모**: 실험

### 목표

로컬 Fake PG 환경에서 지금 서버의 처리 한계를 찾고, 실측으로 찾은 병목을 고친 뒤 한계가 얼마나 올라가는지 비교한다.
같은 부하에서 지연만 줄였다고 끝내지 않는다. 첫 병목을 고친 뒤에도 다음 포화 위치를 확인하며 반복한다.

**판정**: 수정 전과 수정 후 각각 두 시험(서버 처리 용량, 사용자 품질)의 최고 품질 통과 TPS와 지연 허용 지속 처리 TPS를 같은 조건으로 찾아 비교한다.
관측된 코드 병목을 고쳤거나 보류한 근거가 있고, 남은 한계가 자원 한계나 효과 정체로 설명되면 반복을 끝낸다.

### 두 시험

| 시험 | 부하 구성 | 확인할 것 |
|---|---|---|
| 서버 처리 용량 (`capacity`) | checkout·confirm 요청 주입과 완료 관측을 분리하고 전수 상태 조회를 하지 않는다 | 실제 유입, DB 완료 처리율, 적체 증가, 부하 종료 후 해소 시간 |
| 사용자 품질 (`user-quality`) | 같은 구매의 상태를 실제 화면처럼 1초 간격, 최대 30회 조회한다 | 접수 응답과 사용자가 완료를 확인하는 시간 |
| 기존 500ms 조건 (`legacy`) | 기존 500ms 간격·60초 관찰 정책을 재현·스트레스 조건으로 보존한다 | 조회 부하가 처리량과 지연에 주는 영향 |

- 두 시험은 각각 낮은 부하부터 올려 정상, 지연 허용, 과부하 구간을 찾는다. 주입이 완료 관측 슬롯에 막히지 않게 하고 발생기 자원과 요청 누락을 기록한다.
- 조회 정책이 다른 회차끼리 개선 배수를 계산하지 않는다. 새 방식은 수정 전 기준부터 다시 잰다.

### 성능 기준

대상은 사용자 인증을 마친 뒤의 카드·간편결제 승인 처리 흐름이다. 인증, 3DS, 입금 대기는 승인 처리 시간에 넣지 않는다. Fake PG 지연은 100~300ms를 유지한다.
아래 수치는 공식 사례를 참고해 정한 이 프로젝트의 초기 목표이며 업계 표준이나 외부 PG의 성능 보장이 아니다.

| 항목 | 기준 |
|---|---|
| checkout 응답 | p95 500ms 이하 |
| confirm 접수 응답 | p95 500ms 이하 |
| 사용자 완료 확인 | confirm 요청 시작부터 p95 3초 이하, p99 5초 이하 |
| 사용자 조회 정책 | confirm 응답 후 실제 화면과 같은 1초 간격, 최대 30회 |
| 정상 Fake 시험 | API 오류, 주문·승인·재고 불일치 0건. 전수 대조 |
| 유효 유입 | 요청 누락 0, 실제 시작률과 예정률 대조, 발생기 포화 없음 |

- 사용자 조회 종료와 백엔드의 추가 완료 관찰을 나눈다. 조회가 끝난 뒤 완료된 주문을 사용자 기한 안의 성공으로 세지 않는다.
- DB 완료 이력과 product 재고 반영을 전수 대조한다. 표본만 본 지표는 표본이라고 적는다.
- 접수 응답, DB 완료, 사용자 관측 완료, 재고 반영의 이름과 시간 경계를 구분한다.

### 처리 구간 판정

| 구간 | 판정 근거 |
|---|---|
| 품질 목표 충족 | 유효 유입, 정합성, 접수·완료 지연 목표를 모두 충족 |
| 지연 허용 지속 처리 | 지연 목표는 넘지만 유입을 유지하고 완료 처리율, 잔량, 메모리가 관측 구간에서 안정 |
| 일시 폭주 흡수 | 부하 중 잔량이 계속 늘고 요청을 멈춘 뒤에야 해소 |
| 측정 미확정 | 요청 누락, 발생기·호스트 포화, 접수 미확인, 증거 누락으로 서버 한계를 분리할 수 없음 |

- 모든 주문이 나중에 완료됐다는 이유만으로 지속 가능한 TPS로 판정하지 않는다. 5초 초과만으로 지속 처리 불가라고 판정하지도 않는다.
- 미확인·미종결 주문은 유실로 단정하지 않고 관찰 기한과 남은 작업을 보고한다.
- Kafka raw lag에는 트랜잭션 완료 표식이 섞일 수 있으므로 업무 적체와 구분한다.

### 고정 조건

매 회차 같아야 하는 조건이다. 회차별 실제 값은 [EXPERIMENTS](EXPERIMENTS.md#고정-조건)에 적는다.

- 매 본측정 회차는 새 Compose 프로젝트, 새 컨테이너, 새 볼륨으로 시작한다. 빈 DB·Redis·Kafka 확인 → 상품 100종 동일 재고 시드 → 10건/초·120초 워밍업 → 본측정 순서다.
- 워밍업과 본측정만 한 환경을 공유한다. 기존 데이터·볼륨·원자료는 보존하고, 처리되지 않은 상태에서 다시 시드하지 않는다.
- 서버 자원, Fake PG, 내구성 설정, 로그·트레이스, 부하 구성은 바꾸는 요소 말고 모두 같게 둔다. 실행 중 측정 소스를 바꾸지 않고, 바꿨으면 숨기지 않는다.
- 의미 있는 원자료와 실제 런타임 설정, 소스 해시를 보존한다.

### 진행 방식과 첫 가설

- 각 조건을 3분 탐색하고 부하를 올려 통과·미달 경계를 좁힌다. 80·100·120·160건/초는 시작 탐색 지점이며 실제 유입·완료·발생기 상태에 따라 조정한다.
- 후보 한계는 10분 지속 시험으로 확인하고 초기 구간과 후반 추세를 나눈다.
- 수정 전 기준을 확보한 뒤 첫 병목 하나만 바꾸고, 같은 두 시험으로 한계를 다시 찾는다.
- **첫 가설**: 지연은 PG 승인 뒤 결과 반영(결과 소비) 구간에서 커진다. 결과 소비 동시성 1→3이 첫 비교 후보다.
  80/s 한 쌍 비교에서 지연 감소를 봤지만 단독 원인과 효과는 확정하지 않았다([EXPERIMENTS](EXPERIMENTS.md)의 r80-c·r80-d).

### 기준의 외부 근거

- [PayPal 통합 모니터링 예시](https://developer.paypal.com/checkout/integrate#post-launch-monitoring): 주문 생성 2초 미만, capture 3초 미만. 보장·SLA·p95 기준이 아니다.
- [Stripe 상태 확인](https://docs.stripe.com/payments/payment-intents/verifying-status): 웹훅 활용과 반복 조회의 신뢰성·호출 제한 주의. PG→서버 웹훅과 브라우저 표시 수단은 별개다.
- [Stripe 결제수단 구분](https://docs.stripe.com/payments/payment-methods): 즉시 결과와 지연 결과 결제수단을 구분한다.
- 실제 화면의 조회 정책: `payment-service/src/main/resources/static/payment/success.html`
