## 고정 조건

- 새 Compose 프로젝트·컨테이너(20개)·볼륨(14개), 빈 DB·Redis·Kafka(18파티션) 확인, 상품 100종 동일 재고 시드, 10건/초·120초 워밍업 뒤 본측정
- 결과 소비 동시성 1(운영 기본), 같은 빌드 JAR(회차마다 해시 대조), Fake PG 지연 100~300ms
- T2.4부터의 새 모드 드라이버: 정상 VU 650, 워밍업 VU 100, 관측 슬롯 최대 256, 3분 탐색. 실행 명령은 [인계 문서](tps-handoff.md)와 [실행 안내](../../quality/RUNBOOK.md)
- 실행 중 측정 소스를 바꾸지 않는다. 바꾸면 그 회차의 `sourceChanged`에 남는다
- 회차마다 스택을 완전히 내렸다 올리고, 기동 전 자원 상태와 부하 전 안정 여부를 확인한다. 확인 항목은 [실행 안내의 "회차마다 지킬 것"](../../quality/RUNBOOK.md#회차마다-지킬-것)

### 실행 안내 변경 (2026-11-06, #163)

지침 개편에서 [실행 안내](../../quality/RUNBOOK.md)를 코드와 대조해 고쳤다. 측정 결과에 영향을 줄 수 있는 변경은 아래에 적는다.

- **명령·조건 변경: 없음.** 실행 안내의 명령, 옵션 기본값, Compose 값(heap, 복구 설정, 모의 PG 지연), 판정 기준은 코드와 같았다.
  고친 것은 문장 한 줄(완료된 T2.3을 남은 일로 적은 곳)과 옮긴 토픽 문서 링크뿐이다.
- **실행 안내의 예시 명령은 지난 회차의 실제 명령과 다르다.** 지난 회차는 로컬 드라이버(`live-drill/throughput-split-measurements-20261029/run-round-v2.py`, Git 제외)로 돌았다.
  예시 명령을 그대로 따르면 아래 조건이 달라져 이전 회차와 비교할 수 없다. 재개할 때는 드라이버나 [인계 문서](tps-handoff.md)의 명령을 쓴다.

  | 항목 | 실행 안내 예시 | 지난 회차 실제 |
  |---|---|---|
  | 기동 | `compose-up.sh --mode quality` | 같은 명령 + `--skip-build`(bootJar 빌드 생략. JAR가 최신인지 확인 필요) |
  | 본측정 `--preallocated-vus` | 지정 안 함(기본 100) | 650 |
  | 워밍업 `--preallocated-vus` | 지정 안 함(기본 100) | 100 |
  | `--observer-workers` | 지정 안 함(기본 32) | 256 |

- **측정 소스 해시가 달라졌다.** `scripts/quality/evidence.py`가 `docs/quality/README.md`, `RUNBOOK.md`를 소스 해시에 넣는다. 이번 수정으로 다음 회차의
  `source-hashes.json`은 이전 회차와 이 두 파일에서 다르다. 측정 코드는 바뀌지 않았고, 회차 안의 `sourceChanged` 판정(실행 중 변경)과는 관계없다.

## 준비와 도구 검증 (2026-10-28~29)

- **준비**: 전용 quality 환경 20컨테이너 기동, 결제 테이블·Redis·Kafka 18파티션 빈 상태와 100종 재고 시드 확인. `preparation-01`(1건/초·30초) PASS. 관리자 화면과 Grafana는 로그인 없이 접근돼 인증 코드 변경은 필요 없었다.
- **warmup-01, normal-01**(정리 전 환경, 10건/초·600초): 6,001건 전부 DONE·5초 안 관측, confirm p95 12ms. Grafana의 "발행 vs 종결" 패널 제목(rate)과 식(increase) 불일치를 발견했으나 측정 중이라 바꾸지 않았다. DONE 가드 재수신 지표가 관측됐고 중복 원인은 미확정이다(`post-normal-01-duplicate-counters.json`).
- **r80-a 뒤 도구 보완**: 주문별 고유 URL로 시계열이 10만 개를 넘는 경고, VU 사전 할당 100에서 139까지 증가를 확인했다. 상태 URL name 태그를 고정하고 VU 650 사전 할당으로 바꿨다. 수정은 r80-a 부하 종료 뒤라 그 회차의 `sourceChanged` 기록 대상이다.
- **r80-b 로그 분석**: 초기 지연 뒤 약 105초부터 따라잡았고 수신 → DONE p95는 8ms였다. relay 완료 → 수신 p95 9,438ms는 음수 표본과 로그 없는 주문 47건이 있어 정확한 broker 체류 시간으로 해석하지 않는다.
