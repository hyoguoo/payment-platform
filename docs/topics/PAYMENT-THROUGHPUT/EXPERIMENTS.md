# PAYMENT-THROUGHPUT 실험 기록

> 회차마다 블록을 추가하고 이전 회차는 고치지 않는다. 목표·판정 기준·고정 조건은 [BRIEF](BRIEF.md)의 승인된 사전 브리핑을 따른다.
> 2026-10-28~29 회차는 옛 PLAN의 실행 기록에서 옮겼다. 회차 이름은 원자료 폴더 이름과 같다. 원자료는 저장소 밖 `live-drill/`(Git 제외)에 있다.

## 고정 조건

- 새 Compose 프로젝트·컨테이너(20개)·볼륨(14개), 빈 DB·Redis·Kafka(18파티션) 확인, 상품 100종 동일 재고 시드, 10건/초·120초 워밍업 뒤 본측정
- 결과 소비 동시성 1(운영 기본), 같은 빌드 JAR(회차마다 해시 대조), Fake PG 지연 100~300ms
- T2.4부터의 새 모드 드라이버: 정상 VU 650, 워밍업 VU 100, 관측 슬롯 최대 256, 3분 탐색. 실행 명령은 [인계 문서](tps-handoff.md)와 [실행 안내](../../quality/RUNBOOK.md)
- 실행 중 측정 소스를 바꾸지 않는다. 바꾸면 그 회차의 `sourceChanged`에 남는다
- 회차마다 스택을 완전히 내렸다 올리고, 기동 전 자원 상태와 부하 전 안정 여부를 확인한다. 확인 항목은 [실행 안내의 "회차마다 지킬 것"](../../quality/RUNBOOK.md#회차마다-지킬-것)

### 실행 안내 변경 (2026-11-06, #163)

지침 개편에서 [실행 안내](../../quality/RUNBOOK.md)를 코드와 대조해 고쳤다. 측정 결과에 영향을 줄 수 있는 변경은 아래에 적는다.

- **명령·조건 변경: 없음.** 실행 안내의 명령, 옵션 기본값, Compose 값(heap, 복구 설정, 모의 PG 지연), 판정 기준은 코드와 같았다.
  고친 것은 문장 한 줄(완료된 T2.3을 남은 일로 적은 곳)과 옮긴 토픽 문서 링크뿐이다.
- **실행 안내의 예시 명령은 지난 회차의 실제 명령과 다르다.** 지난 회차는 로컬 드라이버(`live-drill/throughput-split-measurements-20261029/run-round-v2.py`, Git 제외)로 돌았다.
  예시 명령을 그대로 따르면 아래 조건이 달라져 이전 회차와 비교할 수 없다. 재개할 때는 드라이버나 [인계 문서](tps-handoff.md)의 명령을 쓴다.

  | 항목 | 실행 안내 예시 | 지난 회차 실제 |
  |---|---|---|
  | 기동 | `compose-up.sh --mode quality` | 같은 명령 + `--skip-build`(bootJar 빌드 생략. JAR가 최신인지 확인 필요) |
  | 본측정 `--preallocated-vus` | 지정 안 함(기본 100) | 650 |
  | 워밍업 `--preallocated-vus` | 지정 안 함(기본 100) | 100 |
  | `--observer-workers` | 지정 안 함(기본 32) | 256 |

- **측정 소스 해시가 달라졌다.** `scripts/quality/evidence.py`가 `docs/quality/README.md`, `RUNBOOK.md`를 소스 해시에 넣는다. 이번 수정으로 다음 회차의
  `source-hashes.json`은 이전 회차와 이 두 파일에서 다르다. 측정 코드는 바뀌지 않았고, 회차 안의 `sourceChanged` 판정(실행 중 변경)과는 관계없다.

### capacity100-a (2026-11-06) 조건과 자원

- 서버 로그: 비즈니스 서비스 WARN/ERROR는 서비스당 2~4줄(기동 중 Tempo 연결 오류 등), 트랜잭션 실패 의심 줄 0. 결과 토픽 lag 표본 최대 352(초기 적체 구간)

## 준비와 도구 검증 (2026-10-28~29)

- **준비**: 전용 quality 환경 20컨테이너 기동, 결제 테이블·Redis·Kafka 18파티션 빈 상태와 100종 재고 시드 확인. `preparation-01`(1건/초·30초) PASS. 관리자 화면과 Grafana는 로그인 없이 접근돼 인증 코드 변경은 필요 없었다.
- **warmup-01, normal-01**(정리 전 환경, 10건/초·600초): 6,001건 전부 DONE·5초 안 관측, confirm p95 12ms. Grafana의 "발행 vs 종결" 패널 제목(rate)과 식(increase) 불일치를 발견했으나 측정 중이라 바꾸지 않았다. DONE 가드 재수신 지표가 관측됐고 중복 원인은 미확정이다(`post-normal-01-duplicate-counters.json`).
- **r80-a 뒤 도구 보완**: 주문별 고유 URL로 시계열이 10만 개를 넘는 경고, VU 사전 할당 100에서 139까지 증가를 확인했다. 상태 URL name 태그를 고정하고 VU 650 사전 할당으로 바꿨다. 수정은 r80-a 부하 종료 뒤라 그 회차의 `sourceChanged` 기록 대상이다.
- **r80-b 로그 분석**: 초기 지연 뒤 약 105초부터 따라잡았고 수신 → DONE p95는 8ms였다. relay 완료 → 수신 p95 9,438ms는 음수 표본과 로그 없는 주문 47건이 있어 정확한 broker 체류 시간으로 해석하지 않는다.
- **r80-c·r80-d 비교의 조건 확인**: 두 회차는 JAR, 이미지 rootfs·설정이 같고(Compose 프로젝트 이름 라벨 제외) 실제 환경의 결과 소비 동시성 1 ↔ 3 말고 차이가 없다. 증빙 해시 35개씩 일치, 새 볼륨 14개씩 서로 겹치지 않음. product 그룹의 종료 lag 합 3은 파티션마다 마지막 트랜잭션 COMMIT 표식으로 확인했다(업무 이벤트 아님). broker의 초기 커밋 혼용 WARN은 기본 `LATEST_ONLY_NO_TX`와 정상 트랜잭션이 섞여도 반복될 수 있다.
- **T2.3 저부하 검증**: capacity·user-quality·legacy 각각 새 환경에서 1건/초·180초. 180·181·180건 시작, 전수 대조 PASS, 누락·오류 0, 소스 불변. user-quality 181건 모두 관측, 완료 p95 1,032·p99 1,037ms. 새 두 모드는 메모리 범위를 넓혀 전체 지속 분류를 INCONCLUSIVE로 남겼다. 이 검증을 서버 최대 TPS로 해석하지 않는다. 요약: [도구 검증](tps-tool-validation.md)
- **capacity-r80-a 판정 규칙 보완**: 마지막 두 시작이 예정 끝 +1·+13ms였고 예정 대비 최대 지연은 23ms였다. 새 모드는 연속 iteration·총량·dropped와 예정 대비 -1~100ms 시각 정밀도로 검사하게 바꿨다(100ms는 프로젝트 계측 허용치). legacy 판정 코드는 바꾸지 않았다. 원자료와 원판정은 보존하고 공식 근거에서만 뺐다.

## 판단과 다음 회차

- 결과 소비 동시성 1 → 3은 한 쌍 비교(r80-c → r80-d)에서 지연 1,553 → 544ms, 결과 lag 83 → 0을 보였다. 초기 편차가 커서 개선 배수, 최대 처리량, 운영 기본값 채택을 확정하지 않았다.
- r80-c가 동시성 1에서도 80/s 탐색을 통과해 "80/s가 한계"라는 가설은 성립하지 않는다.
- capacity-r80-b 구간 분해에서 80/s 지속 실패 증거는 없고 초기 일시 적체가 주된 현상이다. PG 승인 뒤 결과 반영 경로가 후보지만 내부 DB·ACK·트랜잭션 원인은 미확정이다.
- **다음**: 새 환경에서 capacity 100/s·180초. 이후 경계를 좁히고 후보를 10분 확인한 뒤, 결과 소비 동시성 비교([DESIGN](DESIGN.md)의 T3)로 간다.
- 2026-11-06: capacity 100/s는 80/s와 같은 모양(초기 약 30초 적체 → 부하 중 회복)이었다. 3분 탐색 한 번씩으로 보면 처리 용량 경계는 100/s와 120/s 사이다(회차당 1회라 회차 간 편차는 미확인). 다음 후보는 110/s 3분 탐색 또는 100/s 10분 확인이다.
- 2026-11-06: 120/s 재측정(capacity120-b)은 10/29 회차와 결과가 크게 달랐다. 10/29에는 부하 중 처리가 80.7/s에 머물러 잔량이 6,698까지 늘었고, 이번에는 초기 적체(최대 1,407) 뒤 부하 중 회복했다. 결과 토픽 lag 표본 최대도 6,918 → 1,370이다. 두 회차 사이에 바뀐 것은 Redis 이미지(7.2.17), Docker 데이터 초기화(이전 회차들의 볼륨이 쌓여 있던 상태 → 빈 상태), 날짜다. 어느 것이 원인인지, 회차 간 편차인지는 미확인이다. 따라서 "경계는 100/s와 120/s 사이"라는 위 판단은 보류한다.
- 2026-11-06: 160/s 재측정(capacity160-b)은 부하 내내 적체가 늘었다. 오늘 환경에서 3분 탐색 기준 처리 용량 경계는 120/s(부하 중 회복)와 160/s(부하 중 증가) 사이다. 160/s에서 부하 중 처리는 102/s로 120/s 회차(119.8/s)보다 낮았고, 입력이 끝나자 약 240/s로 처리했다. 유입이 늘면 결과 처리가 오히려 느려지고 유입이 멈추면 빨라진다는 뜻이다. 접수 경로와 결과 처리 경로가 같은 자원을 두고 경합하는 것으로 보이지만 어떤 자원인지는 미확인이다. payment DB 연결 대기는 0이었고 컨테이너 CPU 합은 중앙값 575%(할당 1,000%)였다.
- 2026-11-06: 120/s 반복(capacity120-c)은 capacity120-b와 같은 모양(잔량 최대 1,308 vs 1,407, DONE 기록 p95 13.0 vs 13.5초)이라 오늘 환경에서는 결과가 재현된다. 140/s(capacity140-a)는 부하 내내 적체가 늘었다. 3분 탐색 기준 처리 용량 경계는 120/s(회복, 2회)와 140/s(증가) 사이다. 부하 중 처리는 유입 120 → 140 → 160/s에서 119.8 → 109.5 → 102.3/s로 내려가고, 입력이 끝나면 140·160/s 모두 약 240/s로 처리한다.
