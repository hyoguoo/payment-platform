## 이번 재개에서 확정한 범위와 진행 제안

사용자가 확정한 범위는 장애 후 요청 도달·주문 저장 확인과 같은 구매의 안전한 재요청이다.
실제 부하 측정·성능 탐색은 기존 경계에 따라 별도 작업으로 유지한다.
두 목표가 다르다는 이유만으로 토픽을 나누거나 사용자에게 우선순위를 다시 선택하도록 요구하지 않는다.

현재 코드와 보고서 대조에서 다음을 추가로 확인했다.

- 기존 관측: Promtail의 Docker 로그 수집과 Loki 전송 설정이 이미 존재. 다만 이번에 실제 수집·보관 상태를 검증하지 않았고 실행별 증거 폴더로 내보내는 경로는 없음
- 주문 회수: 기존 checkout도 Redis 결과가 남아 있으면 같은 키의 기존 주문 ID와 금액을 반환. 별도 조회 API 없이 재요청으로 결과를 회수하는 출발점
- 영속 연결 부재: 현재 구매 키는 Redis에서만 연결되며, 주문 DB에는 구매 키 연결이 없음. 기본 10초 만료나 결과 저장 후 DB 롤백을 넘는 보장이 필요
- 요청 대응 부재: k6 시도 ID와 서버 trace를 연결하는 기록이 없음. 서버 내부 trace 연속성과 특정 클라이언트 실패 시도의 연결은 별도 검증 대상

assistant의 진행 제안은 다음과 같다. 제품 계약·DB 배치·새 API 도입의 확정 결정은 아니다.

1. 기존 관측 검증과 영속 멱등성 설계 검토를 함께 수행한다. 일반 요청의 Gateway·payment trace 연결을 실행으로 확인하고, 주문과 구매 키가 같은 트랜잭션에서 확정되는 구조를 비교한다.
2. 같은 키·같은 구매 내용의 재요청은 커밋된 기존 주문을 반환하고, 주문이 저장되지 않았다면 생성할 수 있도록 설계한다. 동시 요청이나 DB 조회 실패를 주문 부재로 간주하지 않는다.
3. 저장된 주문은 영속 구매 키 연결로 조사하고, Gateway·payment 도달 지점은 기존 trace·로그로 조사한다. 개별 실패 시도와 trace 연결의 최소 보완은 실행 검증 후 선택한다.
4. 기존 checkout 재요청으로 충분한지 먼저 비교한다. 본문 없이 키만으로 조회하거나 영속 도달 이력을 조회해야 한다는 요구가 있을 때 별도 조회 API를 검토한다.

영속 구매 키 연결은 안전한 재요청과 주문 저장 확인 양쪽에 활용할 수 있지만 주문 저장 전 도달을 증명하지는 않는다.
재요청으로 새 주문이 저장된 경우에도 원래 실패 시도가 도달했거나 커밋됐다고 소급해 판정하지 않는다.
새 DB 연결을 안전한 재요청 목표의 후보로 검토하는 것은 trace ID를 DB에 저장하는 방안을 장애 조사의 필수 변경으로 추천했던 이전 판단과 구분한다.

### 이번 재개에서 확정한 보장

사용자는 주문 저장 전 서버가 중단되고 로그까지 유실된 요청의 도달 여부를 미확인으로 남기는 것을 허용했다.
관측된 도달 지점과 커밋된 주문의 저장 여부를 구분하며 같은 구매의 안전한 재요청은 보장한다.
재요청 시 커밋된 주문이 있으면 재사용하고, 저장되지 않았다면 생성하는 방향이다.
별도 영속 도달 이력은 이번 보장의 필수 범위로 넣지 않는다.

같은 구매의 새 요청이 진행 중이거나 DB 확인이 실패한 경우에는 미저장으로 단정하지 않는다.
구매 키의 영속 연결을 확인하지 못했다는 이유로 다른 키로 새 구매를 시작하도록 유도하지 않는다.
영속 도달 기록을 추가해도 그 기록의 최초 커밋 전에 종료되는 구간까지 반드시 복원할 수 있는 것은 아니다.

구매 키 필수 여부, 보관 기간, 키 소지자의 접근 범위, 내용 충돌 정책은 아래 과거 사용자 선택을 설계 입력으로 존중한다.
최신 범위와 충돌하거나 구현상 변경이 필요한 부분만 다시 논의하며, 과거 기술 제안까지 이번 구현 계약으로 재확정된 것으로 기록하지 않는다.
구매 키 생성·보관은 클라이언트까지 이어져야 하므로 서버만 바꿔 안전한 재요청이 완성됐다고 설명하지 않는다.

### 독립 검토에서 보완한 설계 조건

reviewer와 domain-expert는 두 목표의 통합 범위를 검토했다.
보고서의 현재 코드 설명에는 명백한 불일치를 찾지 못했지만 안전한 재요청 설계에는 다음 조건을 추가 확인해야 한다.

- DB 원자성: 구매 키의 고유 제약과 주문·주문 항목의 동일 커밋. 경쟁 패자가 생성한 주문은 전체 롤백하며, 롤백된 트랜잭션에서 기존 주문을 다시 조회하지 않도록 경계 설계
- 커밋 전 결과: 현재 Redis 결과가 DB 커밋보다 먼저 보이므로, DB에 없는 주문 ID를 재요청 성공으로 반환하는 경로 제거
- 내용 대조: 현재 Redis 적중은 같은 키의 다른 사용자·상품·수량·결제수단을 검사하지 않음. 저장된 구매 내용과 비교하는 후보 검토
- 기존 주문 회수: 현재 가격 변경이나 상품·사용자 조회 장애로 이미 확정된 결과의 회수가 막히지 않도록 기존 주문 조회를 우선하는 후보 검토
- 재시도: DB 커밋 결과가 불명확하면 미저장으로 단정하지 않고 같은 구매 키 유지. 종결된 주문을 같은 키로 새로 만드는지의 계약 확인
- 클라이언트와 비노출: 현재 결제 화면은 구매 키를 보내지 않고, Redis 대기 초과 예외에는 원문 키가 포함됨. 구매 키 계약 적용 대상과 로그·오류 응답의 비노출 경로 확인

별도 공개 조회 API와 주문 저장 전 영속 도달 기록은 안전한 재요청의 필수 조건은 아니다.
구매 키는 여러 HTTP 재시도가 공유하므로 개별 시도 식별자와 구분한다.

### 검증 기준 후보

- 관측: traceparent 없는 checkout의 Gateway 수신과 payment 업무 로그 연결, 실행 구간·인스턴스·수집 실패를 포함한 원자료 보존
- 멱등성: 같은 구매의 동시 재요청, Redis 만료·유실, 서버 재기동 뒤에도 커밋된 주문 한 건과 같은 주문 ID 반환
- 부분 실패: 커밋 전 실패에서는 주문과 구매 키 연결이 함께 롤백, 커밋 후 응답 유실에서는 같은 키로 기존 주문 회수
- 요청 충돌: 같은 키의 구매 내용 변경을 기존 주문 반환이나 신규 주문 생성으로 처리하지 않도록 정책 검증
- 회수 안정성: 현재 가격 변경·상품 조회 장애에도 기존 주문의 확정 ID·금액 반환, 구매 키 원문 로그 비노출
- 조사 결과: Gateway 도달·payment 업무 진입·DB 저장을 각각 기록하며, 원래 실패 시도와 재요청의 증거를 구분

단위 테스트와 DB·동시성 통합 테스트, 일반 요청 trace 실행 검증을 구분한다.
구현 시 Java 정적 검사도 실행하며, DB·통합·관측 실행에는 Docker 기반 로컬 환경이 필요하다.
이번 재개에서는 코드 대조와 독립 reviewer·domain-expert 검토를 완료했으며 서비스 변경·기동·실측은 하지 않았다.

## 사용자가 명확히 설명한 요구

- 조사 목적: 서버 중단·재기동 후 요청 도달 지점과 실제 주문 저장 여부 확인
- 범위 점검: 기존 trace·로그·멱등성을 조사하고 필요한 변경인지 근거로 판단
- 복구 의도: 원래 저장되지 않은 주문을 재요청으로 생성하는 것은 정상 복구이며 조사 완료까지 구매 복구를 막지 않음
- 문서 표현: 처리 흐름과 상황별 판단을 중심으로 쉽게 설명하고, 이해하기 어려운 토글이나 과한 추상화는 제외
- 작업 경계: 실제 부하 측정·성능 탐색은 별도 작업. 제외한 과거 보고서·수치를 공식 결과나 확정 요구로 재사용하지 않음

## 현재 확인한 사실

Gateway·payment에 trace 계측과 로그 설정이 있고 주문 생성 로그에는 주문 ID가 남는다.
그러나 일반 요청에서 서버가 생성한 trace ID가 모든 필요한 로그에 이어지는지는 이번에 실행 검증하지 않았다.
기존 스모크는 클라이언트가 traceparent를 제공하는 경로만 검사한다.

k6는 구매 시도와 멱등키를 기록하지만 서버 trace ID는 보관하지 않는다.
현재 판정 도구는 주문 ID를 받지 못한 경우 Redis 결과와 DB만 대조하고 서버 로그를 활용하지 않는다.
실행 도구에도 해당 구간 서버 로그·trace를 원자료로 보존하는 경로가 없다.
이는 기존 관측의 활용 누락이며, 모든 미확인 요청을 로그만으로 복원할 수 있다는 증거는 아니다.

checkout의 시작 로그는 업무 코드 진입 기록이고 주문 생성 로그는 DB 커밋 전 기록이다.
따라서 로그로 주문 ID를 찾은 뒤 DB와 대조해야 한다.
confirm은 이미 주문 ID를 알고 시작하므로 기존 상태·outbox·이력을 조사에 활용할 수 있다.
outbox 부재는 미도달의 증명이 아니며 모든 202가 영속 접수를 확정하는 것도 아니다.

## 보고서 정정 당시 제안과 철회한 추천

보고서 정정 당시에는 기존 관측을 확인하고 조사에 활용하는 방향을 우선 제안했다.
먼저 일반 요청의 trace 연속성을 검증하고, 식별할 수 있는 서버 로그에서 주문 ID를 찾아 DB와 대조하는 조사 경로를 검토한다.
특정 k6 실패 시도와 서버 trace의 일대일 연결 방식은 아직 정하지 않았다.

다음 항목은 현재 장애 조사 목적의 필수 변경이라는 추천을 철회한다.

- k6에서 trace ID를 생성하도록 변경
- 별도 HTTP 시도 ID를 새로 도입
- 주문 DB에 trace ID나 생성 시도 ID를 추가
- 공개 접수 조회 API와 키 소지자 접근 체계를 신설
- 추적 개선과 모든 클라이언트의 재요청 계약 개편을 한 구현 범위로 묶음

이 방식들이 모든 상황에서 불필요하거나 기술적으로 잘못됐다는 뜻은 아니다.
이번 목적에 필요한 근거를 먼저 제시하지 못했다는 정정이다.

## 보고서 정정 당시 남은 논의

1. 특정 테스트 실패 요청을 서버 trace와 정확히 대응시키는 데 기존 정보로 충분한지, 어느 지점의 최소 보완이 필요한지
2. 로그·응답이 함께 유실된 요청을 미확인으로 남길 수 있는지, 추가 영속 연결이 필요한 보장이 있는지
3. 과거에 선택한 사용자용 복구와 영속 멱등성을 별도 범위로 계속 추진할지

이 중 두 목표를 한 토픽으로 추진하고 도달 증거 유실 시 미확인을 허용하는 것은 이번 재개에서 사용자 답변으로 확정했다.
개별 실패 시도의 연결 방식과 구매 키 계약·동시 요청 처리의 상세 설계는 남은 논의다.
시간·경로만으로 동시 요청을 매칭하거나, 로그가 없다는 이유로 미도달을 확정하는 방식은 사용하지 않는다.
일반 요청의 trace 연속성은 실행 검증 대상이며, 실제 실행 일정·환경과 구현 태스크는 아직 정하지 않았다.

## 함께 다룰 문제: 현재 멱등성의 한계

현재 checkout의 Redis 결과·잠금은 기본 10초 만료이고 주문 DB와 함께 확정되지 않는다.
이 구조가 장시간 장애 후 재요청까지 안전하게 보장하는 것은 아니다.
추적과 안전한 재요청은 다른 보장이며 이번 사용자 결정에 따라 같은 토픽에서 다룬다.
이 문제를 근거로 공개 API나 새 인증 계약까지 자동으로 범위를 확대하지 않는다.

## 과거 사용자 선택 — 재검토 이력

아래는 2026-10-12~13 논의 당시 문서에 기록된 사용자 선택이다.
최신 과설계 점검 이전의 선택을 보존하며, 현재 장애 조사 구현의 확정 요구로 사용하지 않는다.
사용자 선택을 없던 일로 만들거나 assistant의 범위 확대 책임을 사용자에게 돌리지 않는다.

- 대상과 목표: 접수 확인뿐 아니라 같은 구매의 안전한 재요청, 사용자·클라이언트도 이용
- 당시 범위: 확정 주문 조회와 안전한 재요청 중심, 도달·처리 중·실패 이력 제외. 이후 사용자가 도달 확인이 출발점이라고 설명해 범위 재검토
- 구매 식별: 모든 checkout에 구매별 Idempotency-Key 필수, 새 구매는 새 키, 같은 구매는 기존 키 유지
- 접근: 비공개 구매 키를 가진 요청의 조회·재요청 허용, 응답 최소화·키 로그 비노출, 로그인 체계 제외
- 보관: 주문 기록을 보관하는 동안 키 연결 유지, 시간 경과에 따른 같은 키의 신규 주문 생성 금지
- 충돌: 이미 접수된 키의 사용자·상품·수량·결제수단이 달라지면 거절하고 변경 구매는 새 키 사용
- 실패 경계: 주문과 키 연결을 함께 커밋·롤백하며 확정 전 실패한 요청의 최초 내용은 별도 보존하지 않음
- 재시도: 처리 중·DB 장애는 확인 보류, 같은 키로 제한된 자동 재시도 후 중단하고 키·내용 보관

SHA-256 digest, fingerprint, 생성 시도 ID의 DB 저장, 새 조회 API 응답·트랜잭션 상세 배치는 assistant의 기술 제안이었다.
해당 상세 설계는 이번 전면 수정에서 현재 설계 본문에서 제외했다.
안전한 재요청의 상세 설계는 현재 코드와 최신 통합 범위를 기준으로 진행한다.
