# 로컬 결제 품질 측정 도구

측정 도구와 실행 환경을 준비한 상태이며, 새 공식 실측은 아직 수행하지 않았다.
처리량·완료율·지연·복구시간의 달성 결과는 새 측정 이후 기록한다.

## 준비한 기능

- `quality` Compose 구성: 서비스별 컨테이너, 100~300ms 지연의 모의 PG, 로컬 알람 수신처
- k6 구매 시나리오: 주문 접수 전 시도 기록, 확정 요청, 최대 60초의 완료 상태 조회
- 실행 제어: 정상 부하와 payment 프로세스 강제 종료·재기동, 실행별 원자료 보존
- 판정·정합성 대조: 전체 시도 집계, 사용자 관측·DB 상태·플랫폼 PG 승인 금액·주문과 재고 대조
- HTML 생성: 저장된 원자료로 결과 표시, 실행하지 않은 조건은 미실행 표시

## 실행 안내

[실행·운영 안내](RUNBOOK.md)에 환경 준비, 시험 명령과 판정 기준을 정리했다.
초당 10시도는 초기 확인에 사용하는 부하 조건이며 최대 처리량이나 검증된 성능 수치가 아니다.
부하를 높이는 시험은 측정 도구가 목표 유입을 유지하는지도 함께 확인해야 한다.

```bash
python3 -m unittest discover -s scripts/quality -p 'test_*.py'
```

위 명령은 판정기와 실행 제어의 테스트이며 실제 부하 측정은 수행하지 않는다.
실제 실행에는 Java 21, Docker Compose, k6와 별도 시험 데이터 환경이 필요하다.

## 보완할 기능

현재 주문 ID가 없는 오류 응답은 Redis 멱등키 결과를 단서로 조회한다.
Redis 기록은 만료되며 주문 DB와 함께 확정되지 않으므로, 기록이 없다고 미접수를 확정하지 않는다.
요청 키와 주문의 영속 연결, 응답 유실·동시 재요청 검증, 주 DB 기반 접수 판정은 다음 별도 작업으로 남긴다.

정상 상태의 완료 목표와 의도적 단일 서버 중단 중 사용자 영향은 구분한다.
접수 확인은 결제 완료 확인과 다르며 주문 상태와 재고 반영을 별도로 대조한다.

## 결과 보존

전체 원자료와 생성 HTML은 Git에서 제외되는 `live-drill/` 아래 실행별 폴더에 보존한다.
공개 결과에는 새 측정의 실행 환경, 소스 버전, 판정과 한계를 함께 기록한다.
