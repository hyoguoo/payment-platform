# 로컬 결제 품질 측정 도구

현재 구현된 도구는 500ms 간격·최대 60초 상태 조회를 포함한 기존 품질 시나리오다.
이 조건의 로컬 탐색은 수행했으며 [실측 보고서](../reports/tps-clean-measurements.html)에 원래 판정으로 보존한다.
주입·관측 분리 용량 모드와 1초 조회 사용자 품질 모드를 추가했다.
새 두 모드의 지연·잔량·메모리·재고 반영 판정과 HTML은 T2.2에서 구현·모의 검증을 마쳤다.
모드별 새 환경 저부하 검증을 마쳤으며, 현재 새 기준 한계를 탐색 중이다.
[저부하 검증 요약](../reports/tps-tool-validation.md)에서 목표 충족과 전체 지속 처리 미확정을 구분했다.
기존 500ms 판정은 schema1로 보존하며 새 조건은 schema2로 구분한다.
새 기준과 재개 위치는 [합의](../topics/PAYMENT-THROUGHPUT.md), [PLAN](../PAYMENT-THROUGHPUT-PLAN.md),
[인계·미해결 항목](../reports/tps-handoff.md)을 따른다.

## 준비한 기능

- `quality` Compose 구성: 서비스별 컨테이너, 100~300ms 지연의 모의 PG, 로컬 알람 수신처
- k6 구매 시나리오: 주문 접수 전 시도 기록·확정 요청, legacy에서 최대 60초의 완료 조회
- 분리 모드: capacity의 전수 GET 제외, user-quality의 같은 주문 별도 관측·1초/최대 30회 조회·포화 기록
- 실행 제어: 정상 부하와 payment 프로세스 강제 종료·재기동, 실행별 원자료 보존
- 판정·정합성 대조: 전체 시도 집계, 사용자 관측·DB 상태·플랫폼 PG 승인 금액·주문과 재고 대조
- HTML 생성: 저장된 원자료로 결과 표시, 실행하지 않은 조건은 미실행 표시

## 실행 안내

[실행·운영 안내](RUNBOOK.md)에 환경 준비, 시험 명령과 판정 기준을 정리했다.
초당 10시도는 초기 확인에 사용하는 부하 조건이며 최대 처리량이나 검증된 성능 수치가 아니다.
부하를 높이는 시험은 측정 도구가 목표 유입을 유지하는지도 함께 확인해야 한다.
상태 조회의 주문별 URL은 고정된 지표 이름으로 집계하며, 개별 주문 연결은 시도 JSONL에 보존한다.
`dropped_iterations`가 발생하면 서버의 최대 처리량으로 확정하지 않는다.
유입 누락 등 실행 후 바뀔 수 없는 문제만 남으면 추가 관찰을 종료하지만 미확정 판정은 유지한다.
실제 미처리 작업이나 수량 불일치가 남으면 기존 관찰 기한까지 계속 대조한다.

```bash
python3 -m unittest discover -s scripts/quality -p 'test_*.py'
```

위 명령은 도구 테스트이며 실제 결제 서버의 부하 측정은 수행하지 않는다.
k6가 설치돼 있으면 매 테스트에 새 로컬 모의 HTTP 서버를 띄워 주입·관측 계약을 검증하고, 없으면 해당 계약 테스트를 SKIP한다.
실제 실행에는 Java 21, Docker Compose, k6와 별도 시험 데이터 환경이 필요하다.

## 보완할 기능

현재 주문 ID가 없는 오류 응답은 Redis 멱등키 결과를 단서로 조회한다.
Redis 기록은 만료되며 주문 DB와 함께 확정되지 않으므로, 기록이 없다고 미접수를 확정하지 않는다.
요청 키와 주문의 영속 연결, 응답 유실·동시 재요청 검증, 주 DB 기반 접수 판정은 다음 별도 작업으로 남긴다.

정상 상태의 완료 목표와 의도적 단일 서버 중단 중 사용자 영향은 구분한다.
접수 확인은 결제 완료 확인과 다르며 주문 상태와 재고 반영을 별도로 대조한다.

## 결과 보존

실행별 전체 원자료와 생성 HTML은 Git에서 제외되는 `live-drill/` 아래 보존한다.
`docs/reports/`에 기록한 분석·실측 요약과 구분한다. 요약의 `live-drill/` 링크는 이 로컬 작업 공간에서만 열리며 저장소 복제본에 원자료가 포함되지는 않는다.
공개 결과에는 새 측정의 실행 환경, 소스 버전, 판정과 한계를 함께 기록한다.
