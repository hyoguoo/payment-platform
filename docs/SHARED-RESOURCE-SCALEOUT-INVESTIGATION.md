# 처리량이 안 늘던 이유 — 측정 개선기

> 측정일: 2026-08-29 ~ 09-01
> 토픽: SHARED-RESOURCE-SCALEOUT (이슈/브랜치 #146)
> 사이클 30회+ / 늘려본 자원 8종 / 드러난 계측 결함 14건
> 선행: `SHARED-RESOURCE-SCALEOUT-REPORT.md` (원인 미상으로 닫힌 측정)

## 한 줄 결론

**병목은 자원이 아니라 컨슈머 병렬도였다. 파티션 3 개를 스레드 1 개가 다 들고 있었다.**

자원을 일곱 가지 늘려도 처리량이 안 늘었다. 당연했다 — 어느 자원도 차 있지 않았다. CPU 는 가장
많이 쓰는 컨테이너가 0.49 코어, Redis 블록 0, 큐 깊이 1 미만, 디스크는 낼 수 있는 fsync 의
4 분의 1. 늘릴 곳이 없는데 계속 늘리고 있었다.

정작 막혀 있던 건 Kafka 토픽의 **파티션 3** 이었다. 파티션 수는 컨슈머 병렬도의 상한이라
스레드도 인스턴스도 그 위로 못 간다. 파티션과 동시성을 9 로 풀자 **부하 중 종결이 33.9 → 74.3/s
(2.19 배)**, 컨슈머 적체는 7,866 → 1,140 으로 떨어졌다.

앞서 실패한 실험 두 개도 같은 벽에 막혀 있었다 — pg 인스턴스 2 대(0.93x)는 컨슈머가 2 개였고,
동시성 1 → 3(1.06x)은 정확히 파티션 상한에 닿은 값이었다. **파티션은 한 번도 올린 적이 없었다.**

가는 길에 고친 것과 접은 것이 있다.

- **고쳤다** — `pg_inbox` UPDATE 의 데드락. 결제 3.3% 가 실패해 60 초 안전망으로만 종결됐다.
  인덱스를 복합으로 바꿔 해결. **p99 73 초 → 9.3 초, 데드락 163 건 → 0.**
- **철회했다** — `payment_outbox` 잠금 경합을 천장으로 지목했던 것. 수치 단위를 1000 배 잘못
  읽었다(116,830 초가 아니라 116.8 초). 실제로는 COMMIT(1,331 초)의 9% 짜리 2 순위다.
- **철회했다** — 그 다음에 지목한 커밋 fsync. 직접 재보니 장치는 초당 2,400~4,032 회를 내는데
  부하는 1,000 회 남짓만 쓰고 있었다.

세 페이즈 동안 헤맨 이유는 전부 계측이다. 잠금을 "현재 대기 중" 으로만 재서 줄곧 0 으로 읽혔고,
돈 경로의 두 번째 DB 는 표본화 대상이 아니었고, 파티션 수는 아무도 보고 있지 않았다.

## 1. 경위 — 여섯 번 늘리고 여섯 번 실패했다

시작은 다른 분석 문서(`SHARED-RESOURCE-SCALEOUT-BOTTLENECK-ANALYSIS.md`)의 검증이었다. "Mac Docker 의 fsync 경합이 스케일아웃을 막는다"는 주장을 확인하려다 자원 증설 실험을 반복하게 됐다.

| 늘린 것 | 처리량 배수 | 관측 |
|:---|---:|:---|
| payment CPU 2 → 4코어 | 1.26x | 준 자원의 23% 만 사용 |
| payment 인스턴스 1 → 2 | 1.26x | n=3, 편차 작음 |
| pg 인스턴스 1 → 2 | **0.93x** | pg 큐는 절반으로 줄고 다음 단계로 이동 |
| 컨슈머 동시성 1 → 3 | 1.06x | 노이즈 범위 |
| pg 워커 5 → 20 / 릴레이 1 → 5 | 1.00x | 변화 없음 |
| fsync 끄기 | 1.84x | 유일하게 움직였으나 천장은 그대로 |

그리고 **어느 자원도 포화가 아니었다.** CPU 는 전 컨테이너가 30% 대, 행 잠금 대기 0, 재고 캐시 응답 1ms 미만. 30% 를 쓰는 자원을 두 배로 늘리면 60% 가 되는 게 아니라 그대로 30% 다.

부수적으로 원 분석 문서의 판정도 나왔다 — **fsync 는 2대 붕괴의 원인이 아니다**(같은 환경에서 fsync 를 켠 채 2대가 1.344x 로 늘었다). 다만 **fsync 비용 자체는 실재한다**(1대 54.4 → 100.3/s). 그리고 원 리포트의 "인스턴스를 늘리면 오히려 나빠진다"(0.599x)는 **재현되지 않았다.**

## 2. 전환점 — 측정을 의심하기 시작했다

### 2-1. CPU 상한을 걸었더니 오히려 느려졌다

인스턴스를 늘려도 CPU 총량이 안 느는 게 문제로 보여 컨테이너별 상한을 걸었다. 결과는 반대였다.

| 방식 | 부하 중 종결/s | 스로틀 비율 | 평균 사용 |
|:---|---:|---:|---:|
| quota 2코어 | 45.0 | 61.6% | 0.66코어 |
| 코어 고정(cpuset) 0-1 | **52.1** | **0.0%** | 0.62코어 |

같은 2코어인데 상한 방식이 **16% 느리고 시간의 62% 를 스로틀당했다.** 평균 가동률은 33% 였다.

CFS 할당량은 100ms 주기 예산을 소진하면 남은 주기 동안 컨테이너를 얼린다. 이 서비스는 평균 0.66코어를 쓰지만 순간 5.75코어를 요구하는 버스트형이라 치명적이다. **평균 CPU 만 보고 상한을 잡으면 안 된다** — 쿠버네티스 등에 CPU limit 과 함께 올릴 때 실무적으로 중요한 값이다.

부가로, JVM 기동은 정상 운영보다 CPU 를 훨씬 많이 쓴다. eureka 를 정상 사용량(10%) 기준 0.1코어로 묶었더니 기동이 compose 의존 대기를 넘겨 스택이 통째로 못 떴다.

### 2-2. 줄곧 포화 상태에서만 재고 있었다

모든 사이클이 도착률 97/s 였는데 능력은 52~62/s. **늘 능력의 두 배를 때리고 있었다.** 그 구간에서는 지연이 전부 큐 대기라 서비스 품질을 뜻하지 않고, 중간 단계의 개선도 뒤 단계가 막혀 있으면 가려진다.

pg 를 2대로 늘렸을 때 "0.93x, 실패"로 읽은 게 그 사례다. 실제로는 pg 앞 큐가 8,052 → 4,367 로 절반이 됐고 그만큼 다음 단계(payment 앞 4,141 → 7,703)로 옮겨갔을 뿐이다.

### 2-3. 지연 지표가 아예 비어 있었다

지연 표본 시나리오는 종결까지 폴링하며 VU 를 붙잡는데, VU 상한이 20 이고 폴링 타임아웃이 60초였다. 종결에 45초가 걸리는 구간에서 도착률 2/s 를 유지하려면 VU 가 90개 필요하다.

결과는 **3만 건 부하에서 지연 관측 4~31건, 나머지 전부 타임아웃.** 게다가 60초에서 잘린 값으로 낸 백분위는 백분위가 아니다. VU 상한을 300, 타임아웃을 180초로 올리자 같은 조건에서 종결 관측이 **241건, 타임아웃 0** 이 됐다.

### 2-4. 능력 이하로 내려가자 이상한 게 보였다

도착률을 40/s(적체가 안 쌓이는 정상 구간)로 낮췄더니 분포가 두 덩어리였다.

| | 값 | |
|:---|---:|:---|
| p50 | 509ms | 절반은 0.5초에 끝난다 |
| p95 | 5,633ms | 97.9% 가 여기 안에 |
| **p99** | **73,101ms** | 2.1% 가 62~77초에 몰림 |

중간이 없었다. 점진적으로 느려지는 게 아니라 소수가 별개 덩어리로 튀어나왔다. 포화에서만 쟀을 때는 전부 느려서 이 5건이 묻혀 있었다.

### 2-5. 느린 건들은 전부 같은 모양이었다

k6 가 남긴 결제별 상태 관측을 뜯어보니 흐름이 하나같이 똑같았다.

```
+0.0초   PENDING
+0.5초   PROCESSING   ← 여기까지는 빠른 건들과 동일
+76.9초  DONE         ← PROCESSING 에서 76초를 머묾
```

60초라는 숫자가 단서였다. `pg.scheduler.inbox-polling-worker.in-progress-timeout-ms` 가 정확히 60000 이다. 정상 경로가 놓친 확정 명령을 60초 뒤에 주워내는 **좀비 회수기**(`PgInboxPollingWorker`)가 있었고, 느린 건들은 전부 그 안전망에 걸려 종결된 것이었다.

## 3. 원인 — 인덱스 하나가 데드락을 만들고 있었다

로그를 따라가니 답이 명확했다.

```
23:11:23.293  PG_INBOX_WORKER_START   inboxId=486746
23:11:23.601  PG_INBOX_WORKER_FAIL    Deadlock found when trying to get lock
              ↓ 63초 공백
23:12:27.314  PG_INBOX_WORKER_START   inboxId=486746  zombie=true
23:12:27.318  PG_INBOX_ZOMBIE_RECOVERED_IN_PROGRESS
```

벤더 호출은 성공했는데 **그 결과를 인박스에 기록하는 UPDATE 가 데드락으로 죽고** 있었다. 부하 5,000건 중 163건, **3.3%**.

문제의 문장과 실행 계획:

```sql
UPDATE pg_inbox SET status=?, stored_status_result=?, updated_at=?
 WHERE order_id=? AND status=?
```

| | 접근 방식 | 사용 인덱스 | Extra |
|:---|:---|:---|:---|
| 인덱스 전 | `index_merge` | ux_order_id **+** idx_status | `Using intersect(...)` |
| 인덱스 후 | `range` | ux_order_id 단독 | `Using where` |

`order_id` 는 유니크라 이 조건 하나로 행이 특정된다. 그런데 옵티마이저가 `status` 인덱스까지 끼워 **두 인덱스를 교차(intersect)** 했다. UPDATE 한 건이 두 인덱스를 모두 잠갔고, 잡는 순서가 문장마다 달라지면서 **서로 다른 주문을 갱신하는 UPDATE 끼리 반대 순서로 물렸다.** InnoDB 데드락 기록에서 양쪽 트랜잭션이 같은 형태의 UPDATE 이고 각각 PRIMARY / `idx_pg_inbox_status` 를 엇갈려 쥔 것을 확인했다.

`status` 는 값이 다섯 개뿐인 enum 이라 단일 인덱스로는 선택도가 없다. **`(status, updated_at)` 복합으로 교체**하자 좀비 조회(`WHERE status=? AND updated_at<? ORDER BY updated_at`)는 그대로 인덱스를 타면서 옵티마이저가 유니크 인덱스 단독 경로를 골랐다.

마이그레이션: `pg-service/src/main/resources/db/migration/V8__pg_inbox_status_updated_at_index.sql`

> **처리 완료 (2026-08-30).** 측정 편의로 라이브 DB 에 인덱스를 손으로 먼저 적용했던 탓에
> Flyway 이력과 어긋나 있었으나, 볼륨을 지우고 이미지를 재빌드해 V8 이 정식 적용된 것을
> 확인했다(`flyway_schema_history` 에 `8 | pg inbox status updated at index | 1`).

## 4. 결과 — 꼬리가 사라졌다

같은 조건(도착률 40/s · payment 2대 · pg 2대)에서 인덱스만 바꿔 재측정했다.

| 구성 | 처리량/s | p50 | p95 | p99 | 최대 |
|:---|---:|---:|---:|---:|---:|
| 인덱스 전 · pg 1대 | 38.1 | 509ms | 9,232ms | 66,858ms | 89,249ms |
| 인덱스 전 · pg 2대 | 33.5 | 509ms | 5,633ms | 73,101ms | 76,871ms |
| **인덱스 후 · pg 2대** | **41.6** | 510ms | 7,855ms | **9,281ms** | **10,877ms** |

- **p99 73,101 → 9,281ms (8분의 1)**
- **처리량 33.5 → 41.6/s (+24%)**
- **데드락 163건 → 0건**
- **좀비 회수 다수 → 0건**

> 각 조건 1회 측정이다.

### 스케일아웃 배수는 바뀌지 않았다

경합이 사라졌으니 인스턴스를 늘리면 다른 결과가 나올 것으로 봤다. **아니었다.**

매 사이클 볼륨까지 지우고(`scripts/bench-clean-cycle.sh`) 계측 조건을 인덱스 전 측정과 동일하게
맞춰 1대·2대를 번갈아 돌린 결과다.

| | 1대 | 2대 | 배수 |
|:---|---:|---:|---:|
| 인덱스 전 (n=3) | 51.8/s | 65.3/s | **1.261x** |
| 인덱스 후 (n=2, 클린) | 47.2/s | 61.5/s | **1.302x** |

1.26 → 1.30 은 개별값 변동 폭(1대 48.6/45.8, 2대 58.8/64.1) 안이다. **데드락은 1대와 2대에
비슷하게 작용하던 문제였고, 없애도 스케일아웃을 막는 요인은 따로 남아 있다.**

데드락 수정의 가치는 처리량 배수가 아니라 **꼬리 지연**이다 — p99 73초 → 9.3초, 결제 3.3%가
60초 안전망을 타던 것이 사라졌다. 서비스 품질로는 큰 개선이지만 "자원을 늘리면 처리량이 는다"와는
다른 종류의 성과다.

> **폐기한 값** — 중간에 배수 1.56x 가 나온 적이 있으나 그 사이클들은 중단된 시리즈의 고아
> 샘플러 6개가 1시간 35분 동안 부하를 주던 환경에서 잰 것이다(계측 결함 12). 같은 환경에서
> 1대 절대값이 51.8 → 28.2/s 까지 떨어졌고 Kafka 브로커가 죽었다. 폐기한다.

## 4-2. 계측을 넓히자 진짜 천장이 나왔다 — payment_outbox 잠금 경합

데드락을 고쳤는데도 스케일아웃 배수가 안 움직였다(1.26 → 1.30x). 자원은 여전히 전부 여유로웠다.
그래서 "어느 자원에 압력이 몰리는가"를 볼 수 있게 계측을 넓혔다 — **그동안 아예 표본화하지 않던
`mysql-pg` 를 대상에 넣고, 잠금을 "현재 대기 중"이 아니라 누적 카운터로 재게 했다.**

클린 사이클 한 번(payment 2대, r120)의 결과다.

| 대상 | 누적 잠금 대기 | 최대 평균 대기 | 판정 |
|:---|---:|---:|:---|
| **payment 원본** | **721건** | **711ms** | 압력 집중 |
| pg | 27건 | 30ms | 여유 |
| replica | 0건 | 0ms | 여유 |

Redis 는 블록된 클라이언트 0 · PING 1.1ms, pg 큐는 IN_PROGRESS 평균 7건, 컨테이너 CPU 는 30%
대였다. **압력이 payment 원본 DB 한 곳에만 몰려 있다.**

`events_statements_summary_by_digest` 로 문장을 좁히니 하나가 압도적이었다.

| 문장 | 잠금 대기 | 호출 |
|:---|---:|---:|
| **`UPDATE payment_outbox SET status=?, in_flight_at=? WHERE order_id=? AND status=? AND (next_retry_at IS NULL OR next_retry_at<=?)`** | **116,830초** | 21,964 |
| `INSERT IGNORE INTO stock_hold_record ...` | 1,188초 | 20,641 |
| 나머지 전부 | 85초 이하 | — |

2위의 98배다. 호출당 잠금 대기 5.3초이고, 이 문장 총 실행 시간 130,433초 중 **90% 가 대기**다.

이번에는 실행 계획이 깨끗했다(`uk_payment_outbox_order_id` 단독 `range`, 1행) — pg 때와 달리
인덱스 문제가 아니다. **같은 행을 두 경로가 서로 다른 방식으로 잠근다.**

- 확정 트랜잭션이 `findByOrderIdForUpdate`(`@Lock(PESSIMISTIC_WRITE)`)로 그 행을 잡는다.
  앞선 요청의 커밋을 보기 위해 **일부러 블로킹으로 만든 조회**다(해당 메서드 주석에 명시).
- 아웃박스 릴레이가 `claimToInFlight` UPDATE 로 같은 행을 선점하려다 그 커밋을 기다린다.

호출 21,964건에 접수 20,641건 — 결제당 1.06회다. 중복 시도가 거의 없는데도 건당 5.3초를 기다린다.
**직렬 구간에 병렬 자원을 부어도 빨라지지 않는다.** 자원을 일곱 가지 늘려도 처리량이 안 늘던 이유가
여기서 설명된다.

### 왜 두 페이즈 동안 못 봤나

계측이 그 자리를 못 봤다. 두 가지가 겹쳤다.

- 잠금을 **`INNODB_ROW_LOCK_CURRENT_WAITS`(현재 대기 중)로만** 쟀다. 15초 표본 사이로 다
  빠져나가 줄곧 0 으로 읽혔고, 원 리포트는 그 0 을 근거로 잠금 경합을 후보에서 배제했다.
  누적 카운터(`INNODB_ROW_LOCK_WAITS`)를 넣자 같은 구간에서 721건이 잡혔다.
- 돈 경로의 두 번째 DB(`mysql-pg`)를 표본화 대상에 넣은 적이 없다. 데드락은 거기서 났다.

## 6. 교훈

- **자원이 안 찼는데 안 빨라지면, 자원을 늘릴 게 아니라 기다리는 곳을 찾아야 한다.** CPU 30% 에서 자원을 두 배로 늘린 실험을 여섯 번 했고 전부 헛수고였다.
- **포화에서만 재면 서비스 품질이 안 보인다.** 능력의 두 배를 때리면 모든 구성이 똑같이 느려 보인다. 진짜 문제는 능력 이하로 내려가서야 드러났다.
- **평균은 멀쩡한데 꼬리가 무너지는 패턴이 가장 위험하다.** p50 509ms 와 p99 73초가 공존했다. 평균만 봤다면 못 봤다.
- **지표가 관측하지 못하는 영역을 먼저 확인해야 한다.** 지연 표본이 VU 부족으로 붕괴한 것을 값이 작다는 이유로 오래 넘겼다.
- **안전망이 동작하면 문제가 숨는다.** 좀비 회수기가 60초 뒤 전부 건져냈기 때문에 정합 검증은 늘 통과했다. 데이터는 맞았고, 그래서 3.3% 의 실패가 오래 보이지 않았다.
- **"지표가 0" 과 "일이 안 일어남" 은 다르다.** 잠금 대기를 순간값으로만 재면 초당 수 건이 나는
  중에도 0 으로 읽힌다. 후보를 배제할 때는 그 지표가 그것을 관측할 수 있는 종류인지부터 봐야 한다.
- **직렬 구간이 있으면 자원 증설은 답이 아니다.** 자원을 일곱 번 늘려 전부 실패한 뒤에야 확인했다.
  자원 사용률이 낮은데 처리량이 안 오르면 늘릴 것을 찾을 게 아니라 기다리는 곳을 찾아야 한다.

## 7. 3일차 — 천장의 정체가 두 번 더 바뀌었다

### 7-1. 앞서 낸 결론 두 개를 철회한다

**(1) `payment_outbox` 잠금 대기 수치가 1000배 틀렸다.**

`performance_schema` 의 `SUM_LOCK_TIME` 은 피코초 단위다. 116,830 초가 아니라 **116.8초**,
호출당 5.3초가 아니라 **5.3ms** 다. 같은 구간을 다시 줄 세우니 순위가 뒤집혔다.

| 문장 | 호출 | 합계 | 잠금 대기 |
|:---|---:|---:|---:|
| COMMIT | 126,158 | **1,331초** | — |
| `payment_outbox` 선점 UPDATE | 21,964 | 130초 | 116.8초 |
| 그 아래 전부 | | 20초 미만 | |

잠금 경합은 1순위가 아니라 COMMIT 의 9% 짜리 2순위다. "진짜 천장" 이라고 쓴 것은 틀렸다.

**(2) 그 다음에 지목한 "커밋 fsync 가 천장" 도 틀렸다.**

COMMIT 이 2위의 10배라서 fsync 를 천장으로 지목했다. 스택을 내린 김에 직접 쟀다 — 같은
Docker 볼륨에 4KB 동기 쓰기를 날린 결과다.

| | fsync/s | 1회당 |
|:---|---:|---:|
| 단일 스트림 | 2,400 | 0.42ms |
| 4스트림 병렬 | 4,032 | — |

부하가 요구한 건 payment DB 기준 초당 1,000회 언저리다. **장치는 4분의 1도 안 쓰고 있었다.**
커밋 평균 10.56ms 중 실제 fsync 는 0.42ms 짜리 세 번 남짓이고, 나머지 9ms 는 I/O 가 아니라
대기다. 자원이 아니었다.

여기서 그림이 정리됐다. **어느 자원도 포화가 아닌데 자원을 늘려도 안 늘고, 유일하게 움직인
fsync 끄기(1.84배)는 용량을 더한 게 아니라 건당 지연을 깎은 것이었다.** 용량 부족 모델이
아니라 지연 × 고정 동시성 모델이다. 그러면 동시성이 어디에 묶여 있는지를 찾아야 한다.

### 7-2. 컨슈머 하나가 파티션 셋을 다 들고 있었다

파티션 수는 컨슈머 병렬도의 상한이다. 스레드를 늘리든 인스턴스를 늘리든 파티션 수를 못 넘는다.
그런데 이 프로젝트의 토픽은 전부 파티션 3 이고, `pg-service` 는 리스너 동시성을 지정한 적이
없어 Spring 기본값 1 로 돈다. 실측으로 확인했다.

```
GROUP        CONSUMER-ID                      CLIENT-ID               #PARTITIONS
pg-service   consumer-pg-service-1-446e571b   consumer-pg-service-1   3
```

**적체가 가장 심한 그룹(평균 7,866건)이 단일 스레드로 돌고 있었다.**

이걸 알고 나니 앞선 실패 두 개가 다시 읽힌다. 둘 다 파티션 3 에 막혀 있었다.

| 실험 | 당시 결과 | 다시 읽으면 |
|:---|---:|:---|
| pg 인스턴스 1 → 2 | 0.93x | 동시성이 1 이라 컨슈머는 2개. 파티션 3 을 둘이 나눠 가졌을 뿐 |
| 컨슈머 동시성 1 → 3 | 1.06x | payment 전용 손잡이. 1에서 3은 **정확히 파티션 상한에 닿은 것** |

**파티션은 한 번도 올린 적이 없었다.**

### 7-3. 게이트 — 병렬도를 9배로 풀었다

같은 이미지·같은 날·같은 부하로 두 사이클만 돌렸다. 매 사이클 볼륨까지 지우는 클린 사이클이다.

| | A | B |
|:---|---:|---:|
| 파티션 / 동시성 | 3 / 1 | **9 / 9** |
| 부하 중 종결 | 33.9/s | **74.3/s** |
| 같은 창에서 종결한 건수 | 9,186 | **20,135** |
| 제출 | 52,140 | 48,175 |
| pg 컨슈머 적체 평균 | 7,866 | **1,140** |
| payment 컨슈머 적체 평균 | 8,600 | 3,200 |

**B 는 일을 더 적게 받고도 2.19배를 종결했다.** 배선은 실측으로 확인했다 — 두 그룹 다 컨슈머가
9개로 늘고 각자 파티션 하나씩 가져갔다.

막혀 있던 물이 흐르자 아래 단계 지표가 같이 올라갔다. 이제야 자원들이 일을 한다.

| | A | B |
|:---|---:|---:|
| pg outbox 미발행 | 0.9 | 7.8 |
| MySQL 동시 실행 스레드 | 5.06 | 10.56 |
| Redis 재고 ops/s | 380 | 850 |

### 7-4. 도중에 틀린 추론 하나 — 고정 대기를 배수 시간으로 읽었다

A 와 B 의 총 소요 시간이 608초 대 610초로 같았다. 부하 구간만 2.19배 빠르고 총 시간이 같으면
용량이 는 게 아니라 일을 앞으로 당긴 것이라 판단했고, "A 가 배수를 더 빨리 했다" 고 적었다.

틀렸다. 로그를 열어보니 두 사이클 다 `settle 대기 (327초)` — **배수 완료를 기다리는 루프가
아니라 고정 대기**였다. 총 시간의 분모가 `부하 + 상수` 라 같을 수밖에 없었다. 두 사이클 다
327초 안에 다 끝냈다는 것 외에는 아무것도 말해주지 않는다.

같은 이유로 여기서 파생시킨 "전체/s" 지표와 그걸로 계산한 1대 대 2대 1.04배도 무의미하다.

  쓴다. `SPRING_KAFKA_LISTENER_CONCURRENCY` env 주입만으로 걸린다.

  컨슈머가 `metadata.max.age.ms`(기본 5분) 동안 새 파티션을 못 본다. 만든 뒤 파티션 수를 되읽어
  검증하고, 어긋나면 측정을 시작하지 않는다.
