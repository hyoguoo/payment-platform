# 결제 처리량 작업 인계와 미해결 항목

## 목표와 현재 단계

목표는 **현재 서버의 처리 한계 → 실측 병목 수정 → 개선 후 처리 한계**를 같은 조건으로 비교하는 것이다.
**execute T2.1 — 요청 주입과 완료 관측 분리**를 마쳤으며, **T2.2 — 처리량·지연·잔량 판정과 증빙**도 완료했다. **T2.3 — 새 환경 저부하 실구동**도 마쳤고, 현재 **T2.4 — 수정 전 한계 탐색**을 진행한다.
서버 Java 로직·운영 기본 소비 동시성은 아직 변경하지 않았다. 최종 최대 TPS와 개선 배수도 미확정이다.

- 태스크·완료 기준·검증: [PLAN](../PAYMENT-THROUGHPUT-PLAN.md)
- 실제 재개 위치: [STATE](../STATE.md)

## 컴팩트 체크포인트 — 100 TPS 실행 전

사용자 요청으로 **추가 실측을 멈추고 인계 정리까지 완료**한다.
60 TPS 품질 시험은 끝났고 해당 환경은 로그·이미지 근거를 보관한 뒤 **볼륨을 유지해 종료**했다.
현재 실행 중인 컨테이너·부하 프로세스는 없으며, 100 TPS 환경의 기동·시드·워밍업·본측정은 모두 미실행이다.
새 환경은 재개할 때 만들어 빈 상태와 시드부터 확인한다. 지금 서비스 프로세스를 미리 띄우거나 유지할 필요는 없다.
다음 사용자가 **“중단됐던 작업 진행”**이라고 하면 STATE에서 PAYMENT-THROUGHPUT를 선택하고 본 문서·PLAN·로컬 RESUME를 읽은 뒤 아래100 TPS 단계부터 진행한다.
현재 요청은 커밋·인계 정리까지이며 이번 턴에는100 TPS를 시작하지 않는다.
로컬 보고서 HTTP8872도 종료했다. HTML 화면 확인이 필요할 때만 저장소 루트에서 `python3 -m http.server 8872 --bind 127.0.0.1 --directory .`로 다시 띄운다.

다음은 **T2.4 — 조회 없는 capacity100/s·180초 경계 탐색**이다.
저장소 루트에서 아래 명령으로 새 환경부터 시작한다. 프로젝트 이름이 이미 존재하면 재사용하지 않고 새 이름을 선택한다.

```bash
QUALITY_CONFIRMED_CONCURRENCY=1 python3 \
  live-drill/throughput-split-measurements-20261029/run-round-v2.py \
  throughput-split-20261029-capacity-r100-a 100 180 capacity \
  > live-drill/throughput-split-measurements-20261029/capacity-r100-a-driver.log 2>&1
```

드라이버는 새20컨테이너·새14볼륨·빈 DB/Redis/Kafka·동일 시드·10/s120초 워밍업·본측정을 순서대로 진행한다.
정상 VU650/상한650, 워밍업 VU100, 관측 상한256이며 서버 결과 소비 동시성은1이다.
기존 `run-round.py`의 보조 VU 메타데이터 오류를 고친 **v2**를 사용한다. 예전 원형·정정 근거는 보존했다.
종료 뒤 원판정/유입/전수 대조/잔량·메모리를 읽고 `collect-diagnostics.py`·`capture-image-proof.py`로 보관한 뒤 볼륨 보존 종료한다.
100/s에서 누적되면90/s 등으로 좁히고 안정되면 후보10분 확인을 진행한다. 사용자 품질은 현재 최고 통과60/s이며 이쪽도10분 확인이 남았다.

## 현재 수치의 의미

모두 **기존 500ms 조회 정책**의 결과이며 새 합의 목표로 자동 재판정하지 않는다.

| 회차 | 실제 시작 / 최종 완료 | 요청 누락 | 접수 p95 | 완료 관측 p95 | 원래 판정 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| r80-c, 소비 동시성 1 | 14,400 / 14,400 | 0 | 33ms | 1,553ms | PASS |
| r80-d, 소비 동시성 3 | 14,401 / 14,401 | 0 | 34ms | 544ms | PASS |
| r160-a, 소비 동시성 1 | 10,062 / 10,062 | 18,738 | 694ms | 16,738ms | INCONCLUSIVE |

80/s는 3분 탐색 통과이며 최대치나 장시간 보장이 아니다. d의 1건은 종료 경계의 추가 시작이다.
r160-a는 28,800건을 예정했지만 약 65%가 발생기에서 시작되지 못했다.
최종 커밋된 DONE 이력을 기록 시각으로 나누면 부하 구간 9,426건(180초당 약 52.37건/초), 이후 636건이다.
기록 시각은 실제 commit 순간의 계측이 아니며 이 값도 최대 TPS는 아니다.
완료 관측 p99 18.53초·최대 21.68초, 5초 내 완료 136건(1.35%)이다. 694ms는 완료가 아닌 접수 응답이다.

받은 작업을 모두 처리한 점과 160/s를 지속 감내했다는 주장은 구분한다.
5초를 넘겼다고 지속 처리 불가로 판정하지 않으며, 모든 작업이 나중에 끝났다고 지속 가능으로 판정하지도 않는다.
유입 유지 중 잔량·메모리가 안정되면 지연 허용 지속 처리, 계속 쌓이고 종료 뒤 해소되면 일시 폭주 흡수다.
발생기 포화·접수 미확인·증거 부족이면 한계 판정은 미확정으로 남긴다.
