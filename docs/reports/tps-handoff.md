## 목표와 현재 단계

목표는 **현재 서버의 처리 한계 → 실측 병목 수정 → 개선 후 처리 한계**를 같은 조건으로 비교하는 것이다.
현재 discuss 합의와 PLAN 갱신을 마쳤으며, 다음은 **execute T2.1 — 요청 주입과 완료 관측 분리의 실패 테스트**다.
서버 Java 로직·운영 기본 소비 동시성은 아직 변경하지 않았다. 최종 최대 TPS와 개선 배수도 미확정이다.

| 사용자 품질 시험 | 실제 화면과 같은 1초 간격·최대 30회 조회, 같은 구매를 관측 |

| 지속 처리 | 실제 유입 유지, 완료 처리율·미완료 잔량·메모리의 관측 구간 추세 확인 |
| 새 환경 | 회차마다 새 컨테이너·새 볼륨, 기존 자료 보존 |

수치는 공식 사례를 참고한 프로젝트 자체 목표다. 업계 표준·외부 PG 보장으로 표현하지 않는다.
사용자 인증·3DS·입금 대기는 대상 승인 처리 시간에서 제외하며 Fake PG는 100~300ms를 유지한다.
조회 정책을 바꾼 결과를 서버 수정의 개선 배수로 계산하지 않고 새 조건의 기준부터 다시 측정한다.

## 현재 수치의 의미

모두 **기존 500ms 조회 정책**의 결과이며 새 합의 목표로 자동 재판정하지 않는다.

| 회차 | 실제 시작 / 최종 완료 | 요청 누락 | 접수 p95 | 완료 관측 p95 | 원래 판정 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| r80-c, 소비 동시성 1 | 14,400 / 14,400 | 0 | 33ms | 1,553ms | PASS |
| r80-d, 소비 동시성 3 | 14,401 / 14,401 | 0 | 34ms | 544ms | PASS |
| r160-a, 소비 동시성 1 | 10,062 / 10,062 | 18,738 | 694ms | 16,738ms | INCONCLUSIVE |

80/s는 3분 탐색 통과이며 최대치나 장시간 보장이 아니다. d의 1건은 종료 경계의 추가 시작이다.
r160-a는 28,800건을 예정했지만 약 65%가 발생기에서 시작되지 못했다.
최종 커밋된 DONE 이력을 기록 시각으로 나누면 부하 구간 9,426건(180초당 약 52.37건/초), 이후 636건이다.
기록 시각은 실제 commit 순간의 계측이 아니며 이 값도 최대 TPS는 아니다.
완료 관측 p99 18.53초·최대 21.68초, 5초 내 완료 136건(1.35%)이다. 694ms는 완료가 아닌 접수 응답이다.

받은 작업을 모두 처리한 점과 160/s를 지속 감내했다는 주장은 구분한다.
5초를 넘겼다고 지속 처리 불가로 판정하지 않으며, 모든 작업이 나중에 끝났다고 지속 가능으로 판정하지도 않는다.
유입 유지 중 잔량·메모리가 안정되면 지연 허용 지속 처리, 계속 쌓이고 종료 뒤 해소되면 일시 폭주 흡수다.
발생기 포화·접수 미확인·증거 부족이면 한계 판정은 미확정으로 남긴다.

## 서버 발견 사항의 처리 현황

이 표는 모든 항목이 실측 병목이거나 사고를 재현했다는 뜻이 아니다.

| 발견 사항 | 현재 판단·조치 | 남긴 이유·다음 검증 |
|:---:|:---:|:---:|
| 결과 소비 동시성 기본 1 | 3과의 단일 비교에서 지연 감소 관측, 기본값 미변경 | 지속 처리 한계와 관련 실패 경로 검증 후 채택 |
| Kafka 커밋 혼용 경고 반복 | 반복 로그 비용 확인, 미수정 | 초기 배정 커밋 계기설은 유력한 추론. 요청 추적·별도 설정 실험 필요 |
| payment relay가 DB TX 안에서 Kafka ACK 대기 | 구조 확인, 미수정 | 브로커 지연 시 풀 점유와 선점·발행·완료 경계 분리의 효과/복구 검증 필요 |
| checkout TX가 Redis·외부 HTTP까지 포함 | 자원 점유 후보, 미수정 | 실제 연결 점유·병목 기여도 확인. 멱등성 경계와 함께 다뤄야 함 |
| PG outbox 발행 선점 없음 | 중복 발행 경합 구조 확인, 미수정 | 중복 수신도 관측했으나 원인을 모두 이 경합으로 확정하지 않음. 선점·재배달 검증 필요 |
| PG 제출 작업의 처리 동시성 제한 없음 | 과부하 시 자원 누적 후보, 미수정 | 활성 작업·대기·메모리 계측으로 실제 포화 확인 |
| 상태 폴링이 주 DB를 조회 | 부하 증폭 후보. r160-a payment 연결 대기 표본 최대 411 | 주입/관측과 폴링 조건 분리로 기여도 확인. 단독 원인으로 확정하지 않음 |
| 상품별 순차 HTTP·DB·Redis 호출 | 다상품 비용 후보, 미수정 | 현재 단일 상품 시험으로 전체 증폭 검증 불가. 병목 확인 뒤 별도 비교 |
| product 소비 동시성 기본 1 | 미변경, 현재 업무 적체 확인 안 됨 | r80-d 마지막 lag 3은 TX COMMIT 표식. 실제 업무 잔량과 구분 |
| 반복 조회·엔티티 재조립·만료 DELETE | 추가 왕복·할당 후보, 미수정 | SQL·CPU 비용과 멱등/만료 계약을 대조한 뒤 판단 |
| 100% 트레이스·동기 로그 | 조건 유지 | 관측 비용 기여도 미확정. 증거를 꺼서 얻은 수치를 같은 조건 개선으로 제시하지 않음 |
| 전체 미처리 조회·정리량·Fake 승인 기록 누적 | 장시간 데이터/메모리 후보, 미수정 | 긴 시험과 프로파일링 필요 |
| checkout Redis 멱등성과 영속 구매 키의 빈틈 | 정합성 위험 설계 대상, 이번 성능 작업에서 미수정 | 별도 요청 추적 토픽 유지. 중복 청구 사고를 재현한 것으로 표현하지 않음 |

Redis 동기 기록·주문 잠금·멱등 기록·감사 이력·Kafka 트랜잭션은 필요한 보장 비용으로 유지한다.
재시도·회수 대기는 정상 경로의 고정 지연과 구분한다. 실제 HTTP 연결 병목·VT pinning은 확인하지 못했다.
발견 목록을 전부 고치거나 별도 정합성 토픽으로 전환하지 않고 첫 실측 병목부터 변경한다.

## 컴팩트 후 바로 재개할 절차

1. STATE와 PLAN의 T2.1을 읽고 #162 이슈·브랜치를 재사용한다.
2. 현재 `scripts/k6/quality-payment.js`, `scripts/quality/run.py`, `results.py`, `settlement.py`, 관련 테스트를 필요한 범위만 읽는다.
3. 느린 완료가 주입 슬롯을 점유하는 문제를 모의 서버·회귀 테스트로 RED 재현한다. 같은 구매의 주입과 관측을 분리해 GREEN으로 만든다.
4. T2.2 판정·증빙, T2.3 독립 검토·낮은 부하 실구동을 끝낸 뒤 T2.4의 새 기준 탐색으로 간다.
5. T3/T4에서 확인된 병목 하나씩 변경하고 두 시험의 한계를 다시 찾는다.

**현재 구현된 도구에는 새 모드가 없다.** 기존 RUNBOOK 명령을 새 모드 실행으로 표시하지 않는다.
현재 남긴 스택은 `throughput-clean-20261029-r160-a`다. 실행 전 실제 상태를 다시 확인한다.
새 회차는 해당 스택을 볼륨 보존 종료한 후 새 프로젝트로 구성한다. 기존 상태에 재시드하거나 `down -v`하지 않는다.
빈 DB·Redis·Kafka 확인, 상품 100종×재고 100,000, 10/s·120초 워밍업을 고정한다.
