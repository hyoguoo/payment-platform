결제 TPS, 왜 낮을 수 있나?

2026-10-28 초기 정적 검토 · 기준 코드 07f5196c · TPS = 초당 처리 건수

이 페이지는 초기 분석 요약이다. 이후 실측 결과, 현재 조치·인계, 합의한 시험 기준을 구분해 확인한다.

개선 여지는 있다. 현재 낮은 수치의 원인은 아직 확정되지 않았다.

결과를 한 줄로 처리하는 구조와 DB 연결을 잡고 기다리는 구조가 있다.
다만 측정 지표·부하 조건을 확인해야 실제 서버 한계인지 판단할 수 있다.

원인을 세 가지로 나누면 쉽다

보장을 위한 비용

안전하게 기록하고 기다림

외부 PG 승인, 결제·재고 기록, 중복 방지에는 비용이 든다. Redis의 동기 디스크 기록도 현재 내구성 선택이다. 제거하면 장애 시 보장이 달라진다.

개선 가능한 구조

불필요한 직렬 처리와 점유

서로 다른 주문도 결과 소비자 하나가 처리한다. Kafka·외부 HTTP를 기다리며 DB 연결을 점유하는 경로도 있다. 정합성을 지키면서 줄일 후보들이다.

측정·해석 문제

접수량과 완료량을 혼동

기본 품질 시험은 초당 10건을 보내므로 최대 용량을 알 수 없다. HTTP 접수, DB 완료, 60초 내 사용자 관측은 서로 다른 지표다.

결제 한 건이 지나가는 길

  1. 1. 주문 생성사용자·상품 조회
  2. 2. 확정 접수재고 선차감·의도 저장
  3. 3. PG 승인메시지 전달·외부 승인
  4. 4. 결제 완료payment DB의 DONE
  5. 5. 재고 반영product DB 차감

접수 응답이 빨라도 4번은 밀릴 수 있다. 4번이 완료돼도 5번은 남아 있을 수 있다.

후보왜 영향을 주나확인할 증거
결과 소비자 기본 1개서로 다른 주문의 DB 처리와 Kafka 커밋도 차례로 진행한다.PG 승인은 늘지만 결과 메시지가 쌓이고 DB DONE 증가가 뒤처지는지
기다리는 동안 DB 연결 점유payment 발행기는 DB 트랜잭션 안에서 Kafka 응답을 기다린다. 주문 생성도 외부 조회를 감싼다.DB 연결 대기가 Kafka·HTTP 지연과 함께 증가하는지
Redis 동기 디스크 기록재고 선차감 응답에 디스크 대기가 포함된다. 상품을 분산해도 같은 Redis를 공유한다.confirm 지연과 Redis 쓰기·디스크 지연이 함께 증가하는지
완료 확인을 위한 반복 조회미완료 주문마다 약 0.5초 간격으로 주 DB를 조회한다. 처리가 밀리면 조회 부하도 늘어난다.대기 주문 수·상태 조회량·DB 경쟁이 함께 증가하는지

조사 후보이며 실측 영향 순위는 아니다. checkout의 DB 연결 획득 시점도 실행 계측으로 확인해야 한다.

재검토에서 바로잡은 네 가지

  • 완료 카운터가 곧 DB 커밋 수는 아니다.

    기존 상태 전이 카운터는 최종 커밋 전에 증가해 롤백 건도 남을 수 있다. 타이머도 한 건의 소비 실행 시간이 아니라 이전 상태 이후 경과 시간이다.

  • PG 예약 재시도에는 폴링 대기가 추가된다.

    즉시 처리 시점이 예약 시각보다 이르면 반환하고, 이후 2초 폴러가 회수한다. 이 경로의 기본 배치 10건은 장기 평균 약 5행/초 이하의 제약을 만든다. 전체 결제 서버의 상한은 아니다.

  • 격리된 주문도 클라이언트에는 처리 중으로 보인다.

    현재 상태 API는 QUARANTINED를 PROCESSING으로 반환한다. 격리가 지속되면 품질 시험은 60초까지 조회한다. 정상 처리 적체와 복구 대기를 구분해야 한다.

  • PG의 Kafka 설정 설명은 기존 보고서의 오류다.

    PG는 Spring Boot가 만든 producer 팩토리를 사용한다. YAML 설정이 자동 반영되지 않는다는 지적은 payment의 직접 구성 팩토리로 한정한다.

다음 측정에서 할 일

  1. 무엇을 센 수치인지 확인: 접수 건수, 커밋된 DONE, 60초 내 관측 완료를 구분
  2. 어디부터 쌓이는지 확인: 유입을 높이며 단계별 미처리 수와 DB·Redis·Kafka 대기를 같은 시간축에서 관측
  3. 한 요소씩 비교: 첫 병목이 확인되면 소비 동시성 또는 폴링 등을 바꾸고, 완료량·지연·중복 처리·재고 정합성을 함께 비교

낮은 TPS에서도 병목 위치와 실패 경로를 찾는 실험은 의미가 있다. 최대 용량을 주장하려면 별도의 단계적 부하 측정이 필요하다.
