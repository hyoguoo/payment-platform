# 결제 처리량 측정 도구 검증

> 2026-10-29 · 이슈 #162 · T2.1~T2.3 완료, T2.4 수정 전 한계 탐색 진행

요청 주입과 완료 관측을 분리한 도구를 세 조건의 새 환경에서 확인했다.
각 회차는 20컨테이너·새 볼륨14개·빈 상태 확인·동일 시드·10/s120초 워밍업으로 시작했다.
본 검증은 **1/s·180초의 동작 확인**이다. 이후 경계 탐색 결과와 최신 재개점은 [인계](tps-handoff.md)에 기록한다.
서버 Java 로직·운영 기본 소비 동시성1은 아직 변경하지 않았다.

| 조건 | 실제 시작 / 전수 대조 | confirm 접수 p95 | 사용자 완료 관측 p95 / p99 | 원래 전체 판정 |
|:---:|:---:|:---:|:---:|:---:|
| capacity · 전수 상태 조회 제외 | 180 / PASS | 25ms | 미측정 | INCONCLUSIVE |
| user-quality · 1초·최대30회 | 181 / PASS | 23ms | 1,032 / 1,037ms | INCONCLUSIVE |
| legacy · 500ms·60초 | 180 / PASS | 21ms | 537 / 540ms | 기존 기준 PASS |

모두 요청 누락·API 오류·주문/승인/재고 불일치 관측0이며, 실행 중 소스 변경도 없었다.
사용자 품질 시험의 181건은 종료 경계의 추가1건을 포함하고 모두 같은 구매의 완료를 관측했다.
관측 포화·예정 조회 누락·조회 오류도0이었다.
조회 정책이 다르므로 위 지연 차이를 서버 수정의 효과로 계산하지 않는다.

**두 모드의 응답 목표·user-quality의 완료 목표·전수 대조는 통과**했지만,
메모리 관측 범위가 확장돼 전체 지속 처리 분류는 미확정으로 남겼다.
이는 1TPS의 요청을 처리하지 못했다는 뜻이 아니다.
부하 중 재고 반영과 메모리 근거까지 검사하는 새 판정을 기존 판정과 구분했다.

구현 검증은 Python122개·독립 코드/도메인 재검토 PASS이며, 검토에서 발견한
종결 상태 충돌·미확인 접수의 관찰 종료·재고 적체·표본 신선도·원자료/모드 불일치를 회귀로 확인했다.
T2.3에서는 실제 HTTP·DB·Kafka·product 재고까지 대조했다.
세 회차의 JAR 해시는 같고, 볼륨42개는 서로 겹치지 않으며 이전 볼륨도 보존했다.
