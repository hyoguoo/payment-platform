# 공유 자원 스케일아웃 병목 분석 리포트 (추가 분석)

> **⚠️ 이 문서의 핵심 주장은 실측으로 기각됐다 (2026-08-30).**
> 검증 결과와 실제 원인은 `SHARED-RESOURCE-SCALEOUT-INVESTIGATION.md` 참고.
>
> - **기각** — "Mac Docker 의 fsync 경합이 2대 붕괴의 원인": 같은 환경에서 fsync 를 **켠 채**
>   2대를 재니 붕괴가 없었다(1대 → 2대 1.344배). 대조군으로 갈렸다.
> - **기각** — "이전 450/s 가 149/s 로 3분의 1 토막": 450 은 폴링 끈 동기 confirm 한계점,
>   149 는 결제 종결 처리율로 서로 다른 지표다. 같은 지표로 보면 이전 페이즈 1대 종결 능력은
>   75/s 라 오히려 2배 개선이다.
> - **구성 불일치** — "virtiofs/osxfs 브릿지가 I/O 를 느리게 한다": MySQL 데이터는 named
>   volume 에 있어 그 브릿지를 타지 않는다. 지목한 경로가 실제 구성과 다르다.
> - **확인** — "binlog 를 켜면 커밋마다 fsync 가 늘어 처리량을 먹는다": 실재한다. 1대 기준
>   54.4 → 100.3/s (1.84배). 다만 천장을 낮추는 것이지 2대를 무너뜨리는 것이 아니다.
>

## 1. 개요
`SHARED-RESOURCE-SCALEOUT-REPORT.md`에서 원인 미상으로 남겨진 **"인스턴스를 1대에서 2대로 늘렸을 때 처리율이 149/s에서 100/s로 하락한 현상"**에 대한 추가 분석 결과입니다.

분석 결과, 애플리케이션의 동시성 제어나 아키텍처의 한계가 아닌 **Mac Docker 환경 특유의 디스크 I/O (fsync) 경합**이 원인으로 밝혀졌습니다.

## 2. 결정적 증거: 과거 리포트와의 수치 교차 검증

병목의 진짜 원인은 이전 페이즈(`CAPACITY-AND-SCALEOUT-REPORT.md`)와 이번 페이즈의 1인스턴스 처리율 차이에서 명확하게 드러납니다.

| 측정 환경 | 1인스턴스 최대 처리율 | 2인스턴스 최대 처리율 |
| :--- | :--- | :--- |
| **이전 페이즈** (Binlog OFF) | **450/s** | **450/s** |
| **이번 페이즈** (Binlog ON) | **149.2/s** | **100.3/s** |

동일한 애플리케이션 코드와 CPU 자원임에도 불구하고, 단일 인스턴스의 성능이 450/s에서 149.2/s로 3분의 1 토막이 났습니다. 유일한 환경 변화는 읽기 복제본(Read Replica)을 구성하기 위해 `docker-compose.scaleout.yml`에서 **MySQL의 바이너리 로그(log-bin)를 활성화**한 것뿐입니다.

## 3. 원인 상세 분석 (가짜 병목의 발생 원리)

### A. Binlog 활성화로 인한 fsync 2배 증가
MySQL에서 `log-bin` 옵션이 켜지면, 트랜잭션 커밋 시 데이터 유실을 방지하기 위해 2PC(Two-Phase Commit)가 강제됩니다. 이로 인해 한 트랜잭션당 디스크 강제 동기화(`fsync`)가 **기존 1번(InnoDB Redo Log)에서 2번(+Binlog)으로 두 배 증가**하게 됩니다.

### B. Mac Docker 가상화 환경의 I/O 한계
Apple Silicon(Mac)의 Docker Desktop은 가상 머신(VM) 파일시스템 브릿지(virtiofs/osxfs)를 통해 디스크 I/O를 처리합니다. 이 환경은 다수의 스레드가 동시에 `fsync`를 요청할 때 극심한 컨텍스트 스위칭과 병목을 일으켜 지연 시간이 기하급수적으로 늘어납니다.

### C. 동시성(Scale-out)이 오히려 독이 된 이유
* **1대 (149/s)**: HikariCP 커넥션 풀 80개 제한으로 인해 동시 `fsync` 요청이 어느 정도 제한되어 Mac Docker가 간신히 감당할 수 있었습니다.
* **2대 (100/s)**: 인스턴스가 2대로 늘어나며 DB를 타격하는 커넥션 풀이 160개로 2배 증가했습니다. 폭주하는 동시 `fsync` 요청에 가상화 디스크 I/O 큐가 마비되었습니다.
* **지표 교차 검증**: 리포트에 남겨진 `MySQL 실행 스레드 13 -> 35 증가`와 `행 잠금 대기 0`은 스레드들이 락(Lock)을 기다린 것이 아니라, **디스크 쓰기(I/O)가 끝나기를 기다리며 멈춰 서 있었다(I/O Wait)**는 것을 완벽하게 증명합니다.

## 4. 돌파구 및 향후 액션 아이템

현재 관측된 스케일아웃 성능 하락은 **로컬 테스트 환경(Mac Docker) 특유의 제약**일 뿐, 아키텍처의 실패가 아닙니다. 

> [!TIP]
> **단기 해결책: I/O 병목 통제 후 재측정**
> 로컬에서 앱과 인프라의 진짜 한계를 보려면 MySQL의 디스크 강제 동기화를 끄고 측정해야 합니다.
> `docker-compose.scaleout.yml`의 `mysql-payment` 커맨드에 아래 옵션을 추가하여 측정하세요.
> ```yaml
> - "--innodb_flush_log_at_trx_commit=2"
> - "--sync_binlog=0"
> ```

> [!IMPORTANT]
> **장기 해결책: 프로덕션 환경 검증**
> 이 "가짜 병목"은 AWS EC2, EKS 등 Native Linux 환경에서는 발생하지 않습니다. 수치 최적화에 더 이상 로컬 자원을 소모하지 말고, 향후 클라우드 프로덕션 환경에서 진짜 스케일아웃 성능을 벤치마크하는 것을 권장합니다.

> [!NOTE]
> **Kafka 파티션 확장 고려**
> 보고서에서 지적된 소비자 분산 편향(2:1) 문제를 근본적으로 해결하기 위해, 운영 배포 시에는 `payment.events.confirmed` 토픽의 파티션 수를 인스턴스 확장을 고려하여 넉넉히(예: 6개 또는 12개) 프로비저닝해야 합니다.
