# 공유 자원 동반 스케일아웃 측정 리포트 — SHARED-RESOURCE-SCALEOUT

> 측정일: 2026-08-26 ~ 08-27
> 토픽: SHARED-RESOURCE-SCALEOUT (이슈/브랜치 #146)
> 설계: `docs/topics/SHARED-RESOURCE-SCALEOUT.md` / 플랜: `docs/SHARED-RESOURCE-SCALEOUT-PLAN.md`
> 직전 측정: `docs/archive/capacity-and-scaleout/CAPACITY-AND-SCALEOUT-REPORT.md` (인스턴스 1→2 확정 처리율 1.0배로 막힌 지점)

## 이 리포트를 읽는 법

이 측정은 두 번 방식을 바꿨다. **처음 아홉 사이클의 처리율 수치는 무효다** — 부하가 시스템에 닿지 않은 상태에서 잰 값이다. 경위는 "무효가 된 측정" 절에 남긴다. 유효한 처리율 결론은 뒤에 다시 잰 값들이고, **정합성 결과는 부하량과 무관하게 전부 유효하다.**

## 후속 측정으로 정정된 부분 (2026-08-30)

이 리포트가 "원인 미상"으로 닫은 뒤 재측정했고, 결론 두 개가 바뀌었다. 상세는
`SHARED-RESOURCE-SCALEOUT-INVESTIGATION.md`.

- **"인스턴스를 늘리면 오히려 나빠진다"는 재현되지 않는다.** 같은 코드·설정·부하로 다시 재니
  1대 → 2대가 오히려 늘었다(부하 구간 종결 기준 54.4 → 73.1/s). 이 리포트의 역전 관측은
  그 환경에 고유한 조건이었을 가능성이 크다.
- **원인 미상이 아니다.** 확정 결과를 인박스에 기록하는 UPDATE 가 데드락으로 3.3% 실패하고
  있었고(옵티마이저가 유니크 인덱스와 `status` 인덱스를 교차 잠금), 실패분은 60초 좀비 회수로만
  종결됐다. 인덱스를 `(status, updated_at)` 으로 바꾸자 데드락 0, 종결 지연 p99 가 73초에서
  9.3초로, 처리량이 24% 올랐다.

아래 본문은 측정 당시 기록 그대로 둔다.

## 합격선 판정 — 인스턴스 1 → 2, 미달

이 토픽의 유일한 판정선은 인스턴스 1 → 2 구간의 확정 처리율 1.6배다.

같은 커넥션 상한, 같은 예열 상태, 1대가 확실히 못 따라가는 도착률(180/s)에서 잰 값이다.

| 구성 | 접수 | 종결 | 적체 최대 | MySQL 실행 스레드 | 행 잠금 대기 |
|:---:|---:|---:|---:|---:|---:|
| 인스턴스 1 | 153.0/s | **149.2/s** | 21,886 | 13 | 0 |
| 인스턴스 2 | 156.0/s | **100.3/s** | 27,485 | 35 | 0 |

**1 → 2 종결 처리율 0.67배. 판정선 1.6배 미달이며, 인스턴스를 늘리면 오히려 나빠진다.**

> **정정** — 이 역전은 후속 재측정에서 재현되지 않았다(같은 조건에서 1대 → 2대 1.344배). 판정선
> 미달이라는 결론은 유효하지만 "늘리면 나빠진다"는 이 환경 고유 관측으로 다뤄야 한다.

직전 측정이 1.0배로 막힌 뒤 이번에 공유 자원을 실제로 늘렸다 — 읽기 복제본을 붙이고 재고 캐시와 멱등 저장소를 클러스터로 나눴다. 그래도 결론은 바뀌지 않는다. **공유 자원을 나눈 것만으로는 인스턴스 확장의 이득이 나지 않는다.**

## 병목 — 후보를 하나씩 배제했지만 지목에 실패했다

가장 단순한 구성을 한계까지 밀고 자원 지표로 무엇이 포화했는지 지목한 뒤, 그것만 늘려 천장이 밀리는지 보는 방식으로 진행했다. 후보는 전부 배제됐고 **원인을 지목하지 못했다.**

| 후보 | 판정 | 근거 |
|:---|:---:|:---|
| 앱 자원(커넥션 풀·CPU) | 배제 | 전 컨테이너 CPU 합계 평균 1.2~1.5 / 10 코어. 커넥션 대기 없음 |
| 재고 캐시 대수 | 배제 | 마스터 1/2/4 처리율 차이 없음. fsync 정책 낮춘 확인 사이클도 같은 밴드 |
| 재고 캐시 자체 | 배제 | 블록된 클라이언트 0, 응답 지연 평균 0.38ms |
| 읽기 부하 | 배제 | 복제 라우팅 켬/끔 차이 없음. 복제 지연 평균 0.10초 |
| DB 잠금 경합 | 배제 | 행 잠금 대기 전 구간 0 |
| 파이프라인 고정 동시성 | 배제 | 확정 결과 소비자 동시성 1→3, pg 워커 상향 후에도 천장 그대로 |
| 메시지 커밋 직렬화(EOS) | 배제 | 트랜잭션 끈 확인 사이클에서 미종결 비율 3.35% vs 3.32% — 구분되지 않음 |
| 브로커 자원 | 배제 | Kafka 컨테이너 CPU 최대 1.3코어. 발행 지연은 부하 따라 137→202ms 로 완만 |

**설계가 천장으로 지목했던 두 후보(원본 DB 쓰기 경합, 메시지 커밋 직렬화)가 모두 근거로 배제됐다.** 남은 것은 프로파일링 영역이며 설정 손잡이로는 더 밀 수 없다. 원인 미상으로 남긴다.

**인스턴스 2대에서 나빠지는 것도 원인 미상이다.** MySQL 실행 스레드가 13에서 35로 늘지만 행 잠금 대기는 0이다. 확정 결과 토픽 파티션이 3개라 2대에 2:1로 갈리는 편향이 후보지만 확인하지 않았다.

> **정정** — 행 잠금 대기가 0 이었던 것은 여기서 본 DB 가 payment 원본이기 때문이다. 실제 경합은
> pg 쪽 `pg_inbox` 에서 데드락으로 나고 있었고, 이 리포트는 그 DB 를 표본화하지 않았다.

## 정합성 축 — 전 사이클 통과

부하량과 무관하게 유효한 결과다. 판정이 내려진 모든 사이클에서 상품 100종 재고 정합, 건별 대조, 미회수 선차감 기록 0, 격리 0을 통과했다.

**가장 의미 있는 지점은 다중 상품 축이다.** 재고 캐시 마스터 4대에 주문당 상품 3개 — 한 주문의 상품이 서로 다른 노드에 흩어지는 구성에서 정합이 유지됐다. 선행 토픽이 재고 게이트를 상품 단위로 쪼개며 열어준 것이 실제로 성립함을 확인한 자리다.

다만 처리율 대가는 크다. 캐시 왕복이 주문당 세 배가 되면서 처리율이 크게 떨어지고 지연 꼬리가 길어진다. 이 축의 목적은 처리율 비교가 아니었다.

## 무효가 된 측정과 그 경위

**처음 아홉 사이클의 처리율은 시스템 한계가 아니라 부하 도구 한계를 쟀다.** 부하 도구가 주문 종결까지 폴링하며 VU를 붙잡아, 의도한 요청의 60%(32,651건)가 발사되지 못했다. 실제로 닿은 것은 초당 79건이고 목표 400건은 한 번도 닿지 않았다.

그 상태에서 처리율은 `동시 VU ÷ 종결 시간`으로 정해진다. 다섯 구성에서 `확정/s × 종결시간`이 440~447로 거의 상수였던 것이 그 증거다. 종결이 조금 느려진 구성이 처리율이 낮게 찍혔고, 그래서 인스턴스를 늘릴수록 나빠 보였다.

기동 점검과 트레이스 점검은 전부 통과했지만 **부하 도구가 목표 도착률을 내는지는 보지 않았다.** 설계가 경계한 "구성 오류를 처리율 저하로 오독하는 실패"가 다른 형태로 일어났다.

### 무엇을 재고 있는지 착각한 세 번

이 측정에서 반복된 실패는 수치가 아니라 해석 쪽이다. 매번 숫자는 맞았고 그 값이 무엇을 세는지가 틀렸다.

1. **부하 도구 한계를 시스템 한계로** — 위 경위
2. **경사로 부하의 창 평균을 능력으로** — 목표치까지 올렸다 내리는 곡선이라 창 평균은 능력이 아니다. 고정 도착률로 유지해야 능력이 잡힌다
3. **처리 중 물량을 못 받아낸 대기열로** — 적체가 는 것을 능력 초과로 읽었으나, 적체를 종결 속도로 나누면 그대로 지연이 나온다. 처리 중이던 물량이지 대기열이 아니었다

세 번째 오독 때문에 "단일 인스턴스 능력 60~70/s"라고 적었다가 정정했다. **실제로는 1대가 149/s를 종결시킨다.**

## 측정 도구·인프라에서 드러난 결함

이번 작업의 실질 산출 중 하나다. 전부 실제로 돌려봤기 때문에 드러났다.

| 결함 | 영향 | 처리 |
|:---|:---|:---|
| 게이트웨이 기동이 payment 인스턴스를 삭제 | 인스턴스 축을 통째로 무효화할 뻔했다. compose가 의존 서비스를 기본 스케일로 되돌린다 | 의존 해석 없이 기동하도록 수정 |
| 정합 검증이 불일치에도 종료 코드 0 | 무인 사이클이 불일치를 통과로 읽고 캐시를 비워 증거를 지운다 | 통과/판단 보류/불일치 세 갈래로 분리 |
| 소비 적체 0이 도달 불가능한 기준 | 트랜잭션 커밋 표시가 파티션마다 오프셋을 차지해 실거래 뒤에는 0이 안 된다 | 파티션 수 이하·미감소·소비자 생존으로 기준 변경 |

| 재구성이 결제 원장을 안 비움 | 앞 사이클 잔류가 뒤 사이클 교차식을 무조건 어긋나게 한다 | 재구성 절차에 원장 정리 추가 |
| 커넥션 상한 설정이 덮어써짐 | compose가 `command` 배열을 병합하지 않아, 모든 실측이 기본값 151로 돌았다 | 설정 병합 |
| 부하 도구가 관측 시각에서 지연을 자름 | 10초에서 잘린 값은 백분위가 아니다 | 상향 |

## 제품 견고성 발견 (범위 밖)

측정 중 드러난 제품 쪽 문제 둘. 이번 범위 밖이라 고치지 않았다.

- **적용할 수 없는 확정 결과가 소비자를 막는다.** 회수가 되돌린 결제에 뒤늦은 승인이 도착하면 도메인이 전이를 거부하고, 소비자가 그 레코드를 건너뛰지 못해 파티션 전체가 멈춘다.
- **그 결제와 재고 선점이 자동으로는 영원히 안 풀린다.** 회수 판정이 종결 상태가 아니면 되돌리지 않게 설계돼 있어, 안전장치가 오히려 잔류를 영구화한다.

## 해석 범위

- 단일 머신 컨테이너 환경이다. 절대 수치에 의미를 두지 않고 상대비만 낸다.
- 부하 프로필이 상품 100종으로 바뀌어 직전 측정과 직접 비교하지 않는다.
- 핫 상품 쏠림에는 답하지 못한다. 한 상품에 부하가 몰리면 노드를 늘려도 키가 한 슬롯에 있어 흩어지지 않는다.
- 읽기 복제의 지연 교환 관계는 이 부하에서 관측되지 않았다. 복제 지연이 평균 0.1초로 거의 0이었다.
- 장애 전환(노드 전환, 복제본 승격)은 범위 밖이다.

## 종합 결론

**처리량** — 인스턴스 1 → 2 종결 처리율 0.67배. 판정선 1.6배 미달이고 늘리면 나빠진다. 공유 자원을 늘려도 스케일아웃 천장은 밀리지 않았다. *(정정: 역전은 재현되지 않았다 — 상단 안내 참고)*

**체감 지연** — 도착률이 오르면 지연이 급격히 늘어난다. 낮은 부하에서 종결 p50 0.5초, 능력 근처에서 18초대. 복제 라우팅은 지연에 사실상 영향이 없었다.

**정합성** — 판정이 내려진 전 사이클 통과. 재고 캐시를 여러 노드로 나누고 한 주문의 상품을 서로 다른 노드에 흩어도 정합이 유지된다.

**원인** — 지목 실패. 설계가 지목했던 두 후보를 포함해 여덟 개 후보를 근거로 배제했으나 남은 원인을 특정하지 못했다. 설정 손잡이로 밀 수 있는 범위를 벗어났고, 다음은 프로파일링이 필요하다.

> **정정** — 후속 측정에서 원인을 지목했다. `pg_inbox` UPDATE 의 데드락이다. 이 리포트가 못 찾은
> 이유는 표본화 범위에 있다 — 소비 적체는 재고 확정 그룹 하나만, 잠금은 payment 원본 DB 만 봤고,
> 정작 돈 경로의 pg DB 와 두 컨슈머 그룹은 관측 대상이 아니었다.
