# 입력 자료: 한국어 기술 문서 작성 및 문체 교정 지침

> 2026-11-06 개발자가 제공한 원문이다. 위키·포스팅용 강화 작성 기준의 바탕으로 쓴다(BRIEF 질문 4).
> 이 파일은 원문 보존용이며 고치지 않는다. 정리한 결과는 `.agents/skills/writing/` 아래에 둔다.

## 1. 목표 문체

자연스러운 한국어로 작성된 전문 기술 서적과 엔지니어링 문서를 지향한다.

독자가 문장을 해석하는 데 에너지를 쓰지 않고, **기술적 사실과 판단 근거를 이해하는 데 집중할 수 있도록** 작성한다.

다음 특성을 유지한다.

- 전문적이면서 담백한 문체
- 의미가 직접적으로 전달되는 표현
- 자연스러운 문장 흐름과 명확한 인과관계
- 불필요한 수식과 장식이 없는 간결함
- 구체적인 상황과 근거를 바탕으로 한 설명
- 핵심 내용의 이해에 필요한 충분한 깊이

**문장을 더 멋있게 만드는 것이 아니라, 더 정확하고 자연스럽게 읽히도록 만드는 것이 목적이다.**

## 2. 핵심 교정 원칙

### 원칙 1. 영어식 번역체를 자연스러운 한국어로 바꾼다

영어 문장의 어순과 표현을 직역한 듯한 문장을 피한다.

특히 다음 표현을 점검한다.

- 불필요한 명사화
- 영어식 수동 표현
- 추상명사를 지나치게 연결한 문장
- 한국어에서 잘 사용하지 않는 동사와 목적어의 조합
- 불필요한 관형어와 수식 구조

**수정 전**

> 숫자는 사실이지만 그 숫자에 붙이는 원인 설명은 별도의 검증이 필요할 수 있다.

**수정 후**

> 측정값이 확인됐더라도 그 원인이 무엇인지는 따로 검증해야 한다.

문장을 단순히 짧게 만드는 것이 아니라, 한국어 화자가 자연스럽게 사용하는 구조로 재작성한다.

### 원칙 2. 억지스러운 비유와 장식적인 표현을 제거한다

인상적인 문장을 만들기 위해 기술적 개념을 불필요하게 의인화하거나 비유하지 않는다.

**수정 전 → 수정 후**

- 질문에도 투자 대비 수익이 있다.
  → 설계에 영향을 주는 질문부터 한다.
- 운영의 최소 폐회로
  → 장애 탐지부터 복구·개선까지
- 반론과 변경 조건은 설계를 성장시키는 도구다.
  → 조건이 바뀌면 기존 설계를 다시 검토한다.
- 데이터 흐름과 상태가 시스템의 본체다.
  → 서비스 구성보다 데이터와 상태를 먼저 설계한다.

다만 비유가 실제로 복잡한 개념의 이해를 돕는 경우에는 유지할 수 있다.

**비유 자체가 문제가 아니라, 비유를 해석해야만 기술적 의미를 알 수 있는 문장이 문제다.**

### 원칙 3. 추상적인 설명을 구체적인 동작과 상황으로 바꾼다

다음과 같은 설명을 주의한다.

- 유연성이 향상된다.
- 안정성을 확보한다.
- 복잡도를 관리한다.
- 설계 품질을 높인다.
- 시스템의 신뢰성을 강화한다.

이런 표현이 항상 잘못된 것은 아니지만, 실제로 무엇이 달라지는지 설명하지 않으면 정보 가치가 낮다.

**수정 전**

> 외부에서 이미 일어난 비가역적 효과를 내부 상태 변경이 취소할 수 없다.

**수정 후**

> PG에서 이미 승인된 결제는 내부 상태를 `READY`로 되돌린다고 취소되지 않는다.

가능하면 다음 세 가지를 명확히 한다.

1. **무엇이:** 구체적인 데이터, 상태, 컴포넌트 또는 작업
2. **왜:** 원인, 제약 또는 판단 근거
3. **어떻게:** 실제 동작, 변경 사항 또는 결과

추상적 원칙이 중요하다면 구체적 사례로 설명한 뒤 일반화한다.

### 원칙 4. 문장 사이의 논리적 연결을 자연스럽게 만든다

각 문장이 개별적으로 정확하더라도 문단 전체의 흐름이 어색할 수 있다.

다음 관계를 확인한다.

- 앞 문장의 결론이 다음 문장과 연결되는가?
- 갑자기 다른 주제로 넘어가지 않는가?
- 원인과 결과가 뒤섞여 있지 않은가?
- 결론을 이해하는 데 필요한 전제가 생략되지 않았는가?
- 동일한 의미를 다른 문장으로 반복하지 않는가?

필요하면 문장을 단순 치환하지 말고 설명 순서를 재구성한다.

**수정 전**

> 좋은 질문은 설계 결정을 바꾸는 정보를 얻는다. 사용자가 많나요?는 방향성이 약하다. 피크 요청률은 큐의 필요성과 용량 산정을 바꿀 수 있다.

**수정 후**

> 설계에 영향을 주는 질문부터 해야 한다.
>
> 예를 들어 "사용자가 많나요?"보다 "가장 바쁠 때 초당 요청이 몇 건이고, 얼마 동안 몰리나요?"가 더 유용하다. 이 정보를 알아야 대기열이 필요한지, 어느 정도의 처리 용량을 확보해야 하는지 판단할 수 있다.

문장 사이에 접속사를 억지로 추가하지 않는다. 문장 자체의 논리적인 흐름으로 연결되도록 한다.

### 원칙 5. 제목과 소제목은 내용을 직접 설명해야 한다

제목만 읽어도 해당 부분에서 무엇을 배우거나 확인할 수 있는지 알 수 있어야 한다.

지나치게 추상적이거나 선언적인 제목을 피한다.

**수정 전 → 수정 후**

- 좋은 질문은 설계 공간을 좁힌다.
  → 좋은 질문은 설계 선택지를 줄인다.
- 트레이드오프를 한 장의 결정으로 남긴다.
  → 설계 결정과 근거를 한 페이지에 기록한다.
- 결론을 먼저 말하고 필요하면 깊어진다.
  → 결론부터 말하고 필요할 때 자세히 설명한다.
- 프로젝트 경험을 기여의 증거로 바꾸는 법
  → 프로젝트에서 맡은 일과 성과를 설명하는 법

다만 간결하고 의미가 명확한 제목은 수정하지 않는다.

예를 들어 다음 표현은 그대로 사용해도 좋다.

- 동시성·트랜잭션·멱등성은 별개의 문제다.
- 타임아웃은 실패 확정이 아니다.
- p99 개선이 전체 성능 개선은 아니다.

### 원칙 6. 간결하게 쓰되 중요한 설명은 줄이지 않는다

불필요한 단어와 반복 문장은 제거하지만, 글을 짧게 만드는 것 자체를 목표로 삼지 않는다.

**줄여도 되는 것**

- 같은 결론을 반복하는 문장
- 이미 표나 다이어그램으로 충분히 전달된 설명
- 의미를 추가하지 않는 수식어
- 일반론을 반복하는 도입과 마무리
- 장식적인 강조 문장

**유지해야 하는 것**

- 판단을 내리는 데 필요한 전제
- 기술적 제약과 예외 조건
- 선택한 대안의 근거
- 트레이드오프와 실패 가능성
- 원인과 결과를 연결하는 설명
- 검증 방법과 측정 조건

기술적으로 중요한 내용이라면 문장이 다소 길어져도 괜찮다.

### 원칙 7. 전문 용어를 억지로 번역하지 않는다

한국어 개발 문서에서 일반적으로 사용하는 용어는 그대로 활용한다.

- Cache → 캐시
- Queue → 큐
- Timeout → 타임아웃
- Retry → 재시도
- Deadlock → 데드락

반면 다음과 같은 기술 명칭이나 코드 식별자는 정확성을 위해 유지한다.

- Kafka, Redis, Outbox, ADR, SLO, p95
- API 명칭과 설정값
- 상태값 및 코드 식별자
- 공식적으로 정의된 기술 용어

전문 용어를 모두 한국어로 바꾸는 것보다 **독자가 익숙한 표현을 일관되게 사용하는 것**이 중요하다.

### 원칙 8. 과장하거나 불필요하게 단정하지 않는다

기술적 사실, 실험 결과, 해석, 추측을 구별한다.

**수정 전**

> MSA 도입으로 시스템의 성능과 유연성이 개선됐다.

**수정 후**

> 서비스를 분리해 독립 배포가 가능해졌다. 다만 서비스 분리 자체가 성능 개선을 보장하지는 않으므로 처리량과 응답 시간은 별도로 확인해야 한다.

다음 표현을 주의한다.

- 무조건
- 반드시
- 완벽하게
- 근본적으로 해결
- 최적의 구조
- 성능을 보장

기술적으로 타당한 근거가 있을 때만 단정적인 표현을 사용한다.

## 3. 문체와 어조

기본적으로 다음 기준을 적용한다.

- 기술 설명은 `~한다`, `~이다`를 사용한다.
- 실제 대화나 면접 답변은 `~입니다`, `~하겠습니다`를 사용해도 좋다.
- 과도하게 친근하거나 가벼운 말투를 사용하지 않는다.
- 독자를 가르치려 드는 어조를 피한다.
- 과장된 감탄과 불필요한 수사적 질문을 줄인다.
- 설명에 필요하지 않은 강조 표현을 사용하지 않는다.

문장 길이와 종결 어미를 기계적으로 통일하지 않는다. 자연스럽게 읽히는 리듬을 우선한다.

## 4. 문장 단위가 아닌 문단 단위로 검토한다

문체 교정은 개별 문장을 바꾸는 것만으로 끝나지 않는다.

문단을 검토할 때 다음을 확인한다.

1. 첫 문장에서 무엇을 설명하려는지 드러나는가?
2. 이어지는 문장이 그 주제를 충분히 뒷받침하는가?
3. 원인·현상·대응·결과의 순서가 자연스러운가?
4. 설명이 부족해 독자가 추론해야 하는 부분이 있는가?
5. 이미 설명한 내용을 불필요하게 반복하는가?
6. 다음 문단이나 소제목으로 자연스럽게 이어지는가?

필요하면 문장을 합치거나 나누고, 설명 순서를 바꿀 수 있다.

그러나 원문의 기술적 인과관계와 사실은 변경하지 않는다.

## 5. 수정하지 말아야 할 것

명시적인 요청이 없다면 다음 항목을 보존한다.

- 기술적 사실과 주장
- 실험 수치와 단위
- 측정 환경 및 검증 조건
- 예외 조건과 불확실성
- 설계 의사결정의 근거
- 장점과 단점, 트레이드오프
- 코드 식별자와 설정값
- 문서의 논리적 구조와 학습 목적

문체 수정 과정에서 기술적 오류가 의심된다면 임의로 의미를 변경하지 않는다. 별도의 검토 항목으로 보고한다.

**가장 중요한 원칙은 원문의 의미를 보존하는 것이다.**

## 6. 과도한 교정 방지

다음 행동을 하지 않는다.

- 이미 자연스러운 문장을 굳이 다른 표현으로 바꾸기
- 모든 문장을 무조건 짧게 만들기
- 전문 용어를 일상어로 과도하게 바꾸기
- 구체적인 기술 설명을 추상적인 요약으로 대체하기
- 원문에 없는 주장이나 해석 추가하기
- 글을 더 인상적으로 만들기 위해 새로운 비유 넣기
- 문서 전체를 획일적인 AI 보고서 문체로 바꾸기

**수정할 이유를 명확하게 설명할 수 없는 문장은 유지한다.**

## 7. 최종 품질 검증

교정 후 다음 기준으로 결과를 재검토한다.

| 평가 항목 | 확인할 내용 |
|---|---|
| 자연스러움 | 한국어로 자연스럽게 읽히는가? |
| 명확성 | 문장과 제목의 의미를 바로 이해할 수 있는가? |
| 구체성 | 실제 대상과 동작이 드러나는가? |
| 논리성 | 전제·원인·결과가 자연스럽게 연결되는가? |
| 간결성 | 불필요한 표현과 반복이 제거됐는가? |
| 정확성 | 기술적 의미와 주장 범위가 유지됐는가? |
| 일관성 | 용어·문체·설명 수준이 일관되는가? |
| 절제 | 수정할 필요가 없는 문장은 유지했는가? |

교정 결과를 다시 읽었을 때, 문장을 잘 썼다는 인상보다 **내용을 이해하기 편하다는 인상**이 들어야 한다.

## 최종 원칙

**좋은 기술 문장은 화려한 문장이 아니라, 정확한 내용을 자연스럽게 이해할 수 있는 문장이다.**

많이 고치는 것이 아니라 필요한 부분을 정확하게 고치는 것을 목표로 한다.
