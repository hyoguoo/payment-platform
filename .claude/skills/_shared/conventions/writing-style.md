# 문서 작성 컨벤션 — 문체

> `writing.md` 분할 파일. 인덱스: [`writing.md`](writing.md)

## 문체

### ~다. 또는 명사형 종결

서술은 `~다.`로 끝내거나 명사형으로 끝낸다.
`~입니다`, `~합니다`, `~요`, `~습니다` 형식은 사용하지 않는다.
명사형으로 끝낼 때는 문장 끝에 마침표를 찍지 않는다.

```markdown
# 잘못된 예
이 기능은 데이터를 처리합니다.

# 올바른 예
이 기능은 데이터를 처리한다.
이 기능의 역할: 데이터 처리
```

### 문장 길이와 리스트

본문 문장은 `~다.`로 끝낸다.
한 줄에는 가능한 하나의 문장만 작성한다.
세부 항목이 여러 개이거나 설명이 길어질 경우, 대시(`-`) 리스트로 전환한다.
대시 리스트 항목은 `~다.`가 아닌 명사형으로 끝낸다.

```markdown
# 올바른 예
Mockito는 Java 단위 테스트 작성을 돕는 모킹 프레임워크로, 실제 의존 객체 대신 가짜 객체를 생성하고 제어하는 기능을 제공한다.

- 테스트 환경 격리: 외부 요인에 영향 없이 테스트 대상 로직에만 집중할 수 있도록 지원
- 행동 제어 및 검증: 원하는 상황을 시뮬레이션하고 메서드 호출 여부를 검증하는 기능 제공
- 가독성 높은 테스트: BDD 스타일을 지원하여 테스트 코드의 의도를 명확하게 표현

# 잘못된 예 (길어지는 문장을 리스트로 분리하지 않은 경우)
Mockito는 Java 단위 테스트 작성을 돕는 모킹 프레임워크로, 외부 요인에 영향 없이 테스트 대상 로직에만 집중할 수 있도록 테스트 환경을 격리하고, 원하는 상황을 시뮬레이션하거나 메서드 호출 여부를 검증하는 기능을 제공하며, BDD 스타일을 지원하여 테스트 코드의 의도를 명확하게 표현할 수 있도록 지원한다.
```

### 평가·번역투 표현 금지

과시적 평가 형용사("가장", "최고의", "이상적인" 등)로 결론을 내리지 않는다. 사실·수치·비교 근거로 대체한다.

```markdown
# 잘못된 예
가장 정밀한 모델이다.

# 올바른 예
두 outbox 중 상태를 더 잘게 쪼갠 쪽이다.
```

번역투·교과서투 구문("~를 통해", "~함으로써", "~하는 방식을 사용한다")은 구체 동사로 바꾼다.

```markdown
# 잘못된 예
Kafka 메시지를 통해 전달한다.

# 올바른 예
Kafka 메시지로 전달한다.
```

### 문장 밀도 — 단정문 연발 대신 연결어미, 긴 불릿은 하위 뎁스

관련된 내용을 짧은 단정문으로 끊어 나열하지 않는다. 연결어미(-며, -라, -므로 등)로 이어 자연스러운 길이의 문장으로 구성한다. 단, 이어 붙인 문장이 다시 2줄 이상 길어지면 위 "문장 길이와 리스트" 원칙대로 리스트로 전환한다.

대시 리스트 항목 하나가 길어지면, 항목 전체를 재편하지 않고 부연 설명만 하위 뎁스로 한 단계 들여써 분해한다.

```markdown
# 올바른 예 (긴 불릿의 하위 뎁스 분해)
- 발행 실패 시 예외가 relay TX를 롤백해 선점까지 함께 되돌리므로 row는 PENDING 복귀
  - 발행 의도를 잃지 않는 것이 outbox의 존재 이유라, 실패 복구를 별도 상태 관리 없이 롤백 하나로 처리
```

## 목소리 — AI체·번역체 제거

"평가·번역투 표현 금지"의 확장. 아래 기준선은 이 프로젝트 문서(포트폴리오 등)가 실제로 쓰는 목소리이고, 안티패턴은 AI가 쓴 티가 나는 대표 구간이다.

### 목소리 기준선

- 단문 위주 — 한 문장에 한 가지만 담는다.
- 종결은 `~다.` 또는 명사형(`~ 차단`, `~ 방어`, `~ 보장`).
- 조건과 결과는 대시(—)나 쉼표로 직결한다.
- 주어는 도메인 주체(가드·워커·스크립트·스케줄러)로 둔다.
- 도메인 용어는 원형 유지(EOS·QUARANTINED·CAS·DLQ), 괄호 한글은 첫 등장 1회.
- 과장·홍보 형용사 없이 담백하게 — 수치는 실측만.

```markdown
# 올바른 예 (기준선 목소리)
재고를 선점한 후 확정을 진행한다. 재고를 못 잡으면 그 자리에서 실패 처리한다 — 초과 판매를 원천 차단한다.
```

### 은유·즉석 조어 금지

설명을 은유나 즉석 조어로 포장하지 않는다. 개념은 이름 그대로 부른다.

```markdown
# 잘못된 예
인과 다리가 빠졌고, 집 없는 개념이 둘 있다.

# 올바른 예
이유 설명이 빠졌고, 페이지에 자리 없는 개념이 둘 있다.
```

### 메타 도입어 금지

"결론적으로", "핵심은", "중요한 것은", "정리하면"으로 문장을 열지 않는다. 바로 본론으로 들어간다.

```markdown
# 잘못된 예
결론적으로, 이 설계는 유실을 막는다.

# 올바른 예
이 설계는 유실을 막는다.
```

### 명사화 남발 금지

"~하는 것", "~라는 사실", "~에 대한 처리"를 동사로 되돌린다.

```markdown
# 잘못된 예
재고를 복구하는 것을 먼저 수행한다.

# 올바른 예
재고를 먼저 복구한다.
```

### 균일 병렬 나열 금지

같은 구조를 3개 이상 이어 붙이지 않는다("A하고 B하고 C하며"). 끊거나 대시로 결과를 붙인다.

```markdown
# 잘못된 예
차감하고, 발행하고, 확정하고, 반영한다.

# 올바른 예
차감 후 발행한다. 확정되면 재고에 반영한다.
```

### 메커니즘은 이름만 대지 말고 동작으로

같은 메커니즘 이름(CAS·락 등)을 문장마다 반복하지 않는다. 이름은 태그·식별자에 한 번만 두고, 본문은 그게 어떻게 보장하는지 동작으로 푼다.

```markdown
# 잘못된 예
조건부 CAS로 선점하고, 조건부 CAS로 갱신하고, CAS로 방어한다.

# 올바른 예
현재 상태가 기대값일 때만 갱신 — 그 사이 값이 바뀌면 갱신 실패
```

### 번역투 조사 (확장)

"~를 통해" 외에 "~에 대해", "~를 위한", "~에 있어서"도 구체 표현으로 바꾼다.

```markdown
# 잘못된 예
격리에 대한 처리를 위한 로직.

# 올바른 예
격리 처리 로직.
```

## 구조

### 헤더 중심 구성

문서는 `#` 헤더를 기준으로 의미 단위를 나눈다.
산문형으로 이어지는 긴 단락 대신, 헤더와 짧은 설명의 조합으로 구성한다.

```markdown
# 올바른 구조 예시

## 개념

설명 텍스트.

## 동작 원리

단계별 설명.

### 세부 항목

세부 내용.
```

### 서머리·아웃라인은 참고용

만약 요약이나 아웃라인이 제공된다면 구성 힌트로만 활용한다.
그 구조를 그대로 따르는 것이 아니라, 참고하는 수준으로 사용한다.

## 팩트 검증

### 검증되지 않은 내용 금지

확실하지 않은 내용은 작성하지 않는다.
다음 순서로 검증 후 작성한다.

1. 공식 문서 확인 (언어·프레임워크·툴의 공식 사이트)
2. 웹 검색으로 최신 정보 확인
3. 검증 불가한 내용은 작성 범위에서 제외하거나 다시 질의

버전·수치·동작 방식 등 세부 사항은 특히 주의한다.
