# 결제 플랫폼 라이브 실측

payment-platform 을 실제로 구동해 **의도대로 도는지 확인**하는 작업이다.
정상 결제가 어떻게 끝나는지, 실패가 어떻게 되돌려지는지, 재시도가 어떻게 소진되어 격리되는지,
인프라가 무너졌을 때 알람이 어디까지 도달하는지를 직접 일으켜 화면과 대조한다.
어긋난 것이 있으면 그 자리에서 원인을 좇는다. 결과물은 잘 도는 모습을 보여주는
시연이 아니라 **확인한 결과**여야 한다.

## 검증 기준 다섯

매 실측에 적용되는 규칙이다. 특정 회차의 계획이 아니라 이 작업 자체의 규칙이므로
장면이 바뀌어도 그대로 적용한다. 하나만 어겨도 나머지 근거가 흔들린다.

1. **화면이 말하게 한다** — 모든 주장에 그 주장을 보여주는 캡처가 붙는다. 못 붙이면
   "여기는 볼 수단이 없다"고 적는다. "재고가 99→98→99로 움직였다"는 확인할 방법이
   없는 문장이다. 같은 사실을 되돌림 로그 화면으로 보여주면 근거가 된다.
2. **운영자 화면이 우선** — 로그, 터미널, DB 조회는 화면으로 안 될 때만 쓴다. 쓰게
   되면 그 자체를 관측 공백으로 기록한다.
3. **결과가 아니라 판단을 남긴다** — 무엇을 봤나에 더해, 왜 그렇게 했고 무엇이
   어긋났나.
4. **다시 돌릴 수 있다** — 같은 장면을 명령으로 재현할 수 있고, 리포트에서 그
   경로를 가리킨다.
5. **못한 것을 적는다** — 한계를 감추면 나머지 근거의 신뢰도까지 떨어진다.

1차 실측은 1·2 를 어겼다. 재시도 경과는 로그 조회 화면으로, 재고 변화는 터미널
수치를 옮겨 적어 보여줬다 — 읽는 사람이 검증할 수 없는 근거였다. 이번 개편은
거기서 출발한다.

## 화면 판독은 에이전트의 일

결제 구동과 캡처는 스크립트로 결정적으로 처리한다. 하지만 **화면을 보고 판단하는
일은 스크립트가 못한다.** 비어 있는 패널, 앞뒤가 안 맞는 숫자, 예상과 다른 상태는
캡처 파일이 만들어졌다는 사실만으로는 드러나지 않는다. 찍은 화면을 열어서 직접
읽어야 보인다.

찾았다고 끝이 아니다. **그 자리에서 원인까지 추적한다.** 이번 준비 과정에서 실제로
있었던 일이다 — 캡처 이미지를 읽다가 대시보드 패널 하나가 데이터 없이 비어 있는
것을 발견했고, 쿼리를 따라가 보니 패널이 찾는 지표 이름이 실제 지표와 처음부터
어긋나 있었다. 스크립트였다면 캡처 파일이 생겼다는 사실만 확인하고 지나쳤을 자리다.

빈 화면, 어긋난 숫자, 예상과 다른 상태를 만나면 먼저 원인을 추적하고, 그 결과를
판단으로 남긴다(기준 3) — "왜 비었는지 모르겠다"로 끝내지 않는다.

## 전체 흐름

```
무대 세팅 → 시나리오 장치 → 장면별 구동·캡처·판정 → 리포트 작성
```

각 단계에서 필요한 상세는 참고 문서에 있다. 지금 하는 단계의 문서만 열면 된다.

| 단계 | 하는 일 | 열어볼 문서 |
|---|---|---|
| 무대 세팅 | 스택 기동, 캡처 권한, 시드, 시작 상태 캡처 | `references/setup.md` |
| 시나리오 장치 | 실패·재시도를 원하는 시점에 일으킬 준비 | `references/scenarios.md` |
| 구동·캡처·판정 | 장면별로 결제를 태우고 화면을 남긴 뒤 기대와 대조 | `references/scenarios.md` + `references/capture.md` |
| 리포트 | 판정 결과를 엮어 HTML 결과물로 | `references/report.md` |

**캡처를 한 장이라도 찍기 전에 `references/capture.md` 를 먼저 읽는다.** 화면마다
함정이 있어서, 모르고 찍으면 스타일이 빠진 화면이나 로그인 화면을 찍게 된다.

## 다시 시작할 때

실측은 한 번에 끝나지 않을 수 있다(기준 4). 스택을 띄운 채로 세션이 끊겼으면
처음부터 다시 세우기 전에 `references/setup.md` 의 "이어서 할 때" 절부터 본다 —
컨테이너, 시드, Grafana 캡처 권한이 얼마나 살아있는지에 따라 다시 할 절만 다르다.

## 진행 방식

**장면 하나가 끝날 때마다 사용자에게 보고한다.** 무엇을 찍었고 어떻게 나왔는지, 계획과
다른 게 있었는지. 전체를 다 돌린 뒤 한 번에 보고하면 중간에 방향을 틀 기회가 사라진다.

**사용자 손이 필요한 지점이 두 곳 있다.** 통지 채널 캡처는 로그인 세션이 필요해
사용자의 브라우저를 빌려야 하고, 관리자 화면의 위험한 조작(격리 종결 등)은 확인 창이
떠서 브라우저 조작이 멈춘다. 두 경우 모두 그 시점에 미리 알리고 요청한다.

**한 장면은 몇 분씩 걸린다.** 재시도 소진은 간격이 벌어지며 1~2분, 알람은 발화 조건
때문에 수십 초에서 2분. 기다리는 동안 다음 장면 준비나 다른 캡처를 하면 시간이 덜 든다.

## 캡처 도구

`scripts/capture.sh` — 헤드리스 Chrome 으로 2배 해상도 PNG 를 남긴다.

```bash
CAPTURE_OUT_DIR=<저장폴더> scripts/capture.sh <파일이름> <URL> [창높이]
```

기본 저장 위치는 현재 작업 디렉토리의 `live-drill/originals/`.
창 너비는 `CAPTURE_WIDTH`(기본 1440), 렌더 대기는 `CAPTURE_DELAY`(기본 5000ms)로 조절한다.
그래프가 많은 대시보드나 트레이스 화면은 대기를 25000 이상으로 넉넉히 준다.

**파일명은 `<순번>-<내용>.png`.** 시간에 따라 변하는 과정은 순번을 이어 붙여
흐름을 남긴다(`18-attempt-1.png`, `-2`, `-3`). 결과 한 장으로는 재시도가 쌓이는 과정이나
알람이 울렸다 꺼지는 과정이 보이지 않는다.

## 실측 중 결함을 발견했을 때

실제로 돌려보면 계획과 다른 것이 나온다. 이건 실패가 아니라 **이 작업의 수확**이다.
두 갈래로 처리한다.

- **리포트에 남길 것** — 예상과 실제가 달랐다는 사실 자체. 정직하게 적으면 리포트가 강해진다.
- **고칠 것** — 명백한 결함이면 사용자와 상의해 처리한다. 실측 산출물과 코드 수정은
  섞지 않는다 — 캡처와 리포트는 `live-drill/` 아래 로컬에 남고, 코드 변경은 이
  저장소의 통상 커밋 방식(feat/fix)으로 간다.

판단이 서지 않으면 사용자에게 묻는다. "이건 버그로 보이는데 어떻게 할까" 한마디면 된다.

## 산출물 위치

```
live-drill/
├── report.html      결과 리포트
├── PLAN.md          계획 (있으면 갱신, 없으면 생략 가능)
├── originals/       캡처 원본
└── RESUME.md        중단 시 재개 메모
```

실측 산출물은 **저장소 밖에 남는다.** `.gitignore` 가 `live-drill/` 디렉토리를 통째
무시하므로 브랜치를 나눠 격리할 필요가 없다 — 스킬 자체는 main 에 상주해 브랜치
이동 없이 바로 발동한다. 캡처 원본이 수십 MB라 코드 이력에 섞이면 곤란하고,
리포트는 특정 시점의 기록이라 코드와 함께 진화할 필요가 없다는 점은 그대로다.
