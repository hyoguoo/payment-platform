# 결제 플랫폼 라이브 실측

payment-platform 이 **말이 아니라 실제 화면으로** 무엇을 하는지 남기는 작업이다.
정상 결제가 어떻게 끝나는지, 실패가 어떻게 되돌려지는지, 재시도가 어떻게 소진되어 격리되는지,
인프라가 무너졌을 때 알람이 어디까지 도달하는지를 직접 일으켜 캡처하고 리포트로 엮는다.

## 이 작업의 성패를 가르는 것

리포트를 보는 사람은 **"정말 그랬나"** 를 묻는다. 그래서 이 작업에는 원칙이 하나 있다.

> **수치를 글로 적지 말고 화면이나 로그로 보여준다.**

"재고가 99에서 98로 잡혔다가 99로 돌아왔다"고 쓰면 읽는 사람은 확인할 방법이 없다.
같은 사실을 되돌림 로그 화면으로 보여주면 근거가 된다. 캡처 한 장을 더 찍는 편이
문장 세 줄보다 낫다. 화면으로 보여줄 수 없는 사실을 발견하면 그건 대개
**관측이 비어 있다는 신호**다 — 리포트에 "여기는 확인할 수단이 없다"고 정직하게 적거나,
로그를 보강할 만한 곳인지 사용자와 상의한다.

## 전체 흐름

```
무대 세팅 → 시나리오 장치 → 장면별 구동·캡처 → 리포트 작성
```

각 단계에서 필요한 상세는 참고 문서에 있다. 지금 하는 단계의 문서만 열면 된다.

| 단계 | 하는 일 | 열어볼 문서 |
|---|---|---|
| 무대 세팅 | 스택 기동, 캡처 권한, 시드, 시작 상태 캡처 | `references/setup.md` |
| 시나리오 장치 | 실패·재시도를 원하는 시점에 일으킬 준비 | `references/scenarios.md` |
| 구동·캡처 | 장면별로 결제를 태우고 화면을 남김 | `references/scenarios.md` + `references/capture.md` |
| 리포트 | 캡처를 엮어 HTML 결과물로 | `references/report.md` |

**캡처를 한 장이라도 찍기 전에 `references/capture.md` 를 먼저 읽는다.** 화면마다
함정이 있어서, 모르고 찍으면 스타일이 빠진 화면이나 로그인 화면을 찍게 된다.

## 진행 방식

**장면 하나가 끝날 때마다 사용자에게 보고한다.** 무엇을 찍었고 어떻게 나왔는지, 계획과
다른 게 있었는지. 전체를 다 돌린 뒤 한 번에 보고하면 중간에 방향을 틀 기회가 사라진다.

**사용자 손이 필요한 지점이 두 곳 있다.** 통지 채널 캡처는 로그인 세션이 필요해
사용자의 브라우저를 빌려야 하고, 관리자 화면의 위험한 조작(격리 종결 등)은 확인 창이
떠서 브라우저 조작이 멈춘다. 두 경우 모두 그 시점에 미리 알리고 요청한다.

**한 장면은 몇 분씩 걸린다.** 재시도 소진은 간격이 벌어지며 1~2분, 알람은 발화 조건
때문에 수십 초에서 2분. 기다리는 동안 다음 장면 준비나 다른 캡처를 하면 시간이 덜 든다.

## 캡처 도구

`scripts/capture.sh` — 헤드리스 Chrome 으로 2배 해상도 PNG 를 남긴다.

```bash
CAPTURE_OUT_DIR=<저장폴더> scripts/capture.sh <파일이름> <URL> [창높이]
```

기본 저장 위치는 현재 작업 디렉토리의 `live-drill/originals/`.
창 너비는 `CAPTURE_WIDTH`(기본 1440), 렌더 대기는 `CAPTURE_DELAY`(기본 5000ms)로 조절한다.
그래프가 많은 대시보드나 트레이스 화면은 대기를 25000 이상으로 넉넉히 준다.

**파일명은 `<순번>-<내용>.png`.** 시간에 따라 변하는 과정은 순번을 이어 붙여
흐름을 남긴다(`18-attempt-1.png`, `-2`, `-3`). 결과 한 장으로는 재시도가 쌓이는 과정이나
알람이 울렸다 꺼지는 과정이 보이지 않는다.

## 실측 중 결함을 발견했을 때

실제로 돌려보면 계획과 다른 것이 나온다. 이건 실패가 아니라 **이 작업의 수확**이다.
두 갈래로 처리한다.

- **리포트에 남길 것** — 예상과 실제가 달랐다는 사실 자체. 정직하게 적으면 리포트가 강해진다.
- **고칠 것** — 명백한 결함이면 사용자와 상의해 별도 브랜치로 분리한다. 실측 브랜치는
  리포트 산출물 전용이고, 코드 수정은 main 으로 가야 한다.

판단이 서지 않으면 사용자에게 묻는다. "이건 버그로 보이는데 어떻게 할까" 한마디면 된다.

## 산출물 위치

```
live-drill/
├── report.html      결과 리포트
├── PLAN.md          계획 (있으면 갱신, 없으면 생략 가능)
├── originals/       캡처 원본
└── RESUME.md        중단 시 재개 메모
```

실측 산출물은 **별도 브랜치에 두고 main 에 병합하지 않는다.** 캡처 원본이 수십 MB라
코드 이력에 섞이면 곤란하고, 리포트는 특정 시점의 기록이라 코드와 함께 진화할 필요가 없다.
