# discuss-ready 체크리스트

관련 항목을 적용하고 해당 없는 항목은 생략한다. 수행 주체나 도구는 고정하지 않는다.

# Gate checklist

## scope

- [ ] 문제·목표·영향 모듈과 이번 범위가 분명하다.
- [ ] 결정이 필요한 가정과 확정된 사실이 구분되어 있다.

## design decisions

- [ ] 핵심 결정에 근거가 있고 필요한 대안의 장단점이 비교되어 있다.
- [ ] 실제 코드의 레이어·포트 배치와 충돌하지 않는다.
- [ ] 상태·메시지 흐름 변경이면 기존 결제 경로와 실패·복구 경로를 설명한다.

## verification plan

- [ ] 관찰 가능한 성공 기준과 이를 확인할 테스트·실측 방법이 정해져 있다.
- [ ] 필요한 환경과 검증하지 못할 수 있는 경로가 드러나 있다.

## domain risk

결제 상태·멱등성·복구·정산·민감정보 또는 그 런타임 설정이 바뀌거나 해당 동작을 서술할 때 적용한다.

- [ ] 중복·부분 실패·타임아웃·동시성 중 변경과 관련된 시나리오와 대응이 식별되어 있다.
- [ ] 재시도 정책이 있으면 종료 조건과 부작용을 검토했다.
- [ ] 민감정보의 로그·저장·전송 경로를 확인했다.

# Post-phase checklist

- [ ] 설계 문서와 STATE에 결정·미결 사항·다음 작업이 반영되어 있다.
- [ ] 이슈·브랜치·커밋은 요청 범위에 포함된 경우에 처리했다.
