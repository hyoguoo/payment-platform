# GitHub 컨벤션

요청에 포함된 이슈·푸시·PR 작업에 적용한다. 사용 가능한 연결 도구 또는 인증된 `gh`를 사용한다.
저장소와 기존 이슈·PR·브랜치를 확인해 중복 생성을 피한다.

## Step 1 — 이슈

- 제목은 작업 내용을 나타내는 한글로 쓴다. 내부 토픽·태스크 식별자를 제목에 넣지 않는다.
- 본문에는 문제·목표·범위·검증 기준 중 필요한 내용을 적는다. 명사형 헤더와 담백한 `~다` 문체를 쓴다.
- 실제 존재하는 변경 유형 라벨과 확인된 담당자를 지정한다. 권한·라벨이 없으면 그 제한을 보고한다.

## Step 2 — 브랜치

기존 작업 브랜치를 우선 사용한다. 새 브랜치의 기본 기준은 `main`이며, 다른 기준을 요청받으면 따른다.
이슈가 있으면 `#<issue-number>`, 없으면 작업을 나타내는 이름을 사용한다.
미커밋 변경을 버리거나 main에 직접 push하지 않는다. 강제 push는 자동 선택하지 않는다.

## Step 3 — PR

- 변경에 맞는 검증을 완료하고 결과를 명시한다. 미검증 상태라면 이를 본문에 드러내고 draft로 만든다.
- 제목은 `<type>: <한글 요약>`이다. 본문은 문제와 최종 동작을 먼저 설명하고 필요한 구현·검증 근거를 덧붙인다.
- 관련 이슈가 있을 때만 `Closes #<번호>`를 사용한다. 라벨·담당자는 지원되는 도구로 함께 지정한다.
- 파일·수치·성공 여부는 실제 diff와 실행 결과를 근거로 쓴다. 다이어그램은 동시성·분기·경계를 설명할 때 사용한다.
- 여러 줄 본문은 구조화된 인자나 임시 파일의 `--body-file`로 전달한다.
- 저장소 기본 형식에는 생성 푸터가 없다. 세션의 명시적 지시가 있으면 그 지시를 따른다.

## Step 4 — 갱신

리뷰 수정은 새 커밋으로 기록한다. PR 제목·본문은 최종 구현을 기준으로 다시 정리한다.
평가에 필요한 설계 근거와 검증 결과는 보존하고, 폐기한 접근이나 대화 이력을 무작정 누적하지 않는다.
별도 댓글은 요청받았을 때 작성한다. merge는 명시적으로 요청받았을 때 수행한다.
