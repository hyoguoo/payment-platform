# HTML 변경 설명·보고서

개발자가 어떤 형식을 원하는지 먼저 정한다. 말하지 않았으면 토픽 마무리에서는 둘 중 무엇을 원하는지 묻는다.

| 형식 | 목적 | 독자 |
|---|---|---|
| 변경 설명 | 코드 변경을 바닥부터 이해시킨다 | 이 변경을 처음 보는 개발자 |
| 보고서 | 토픽에서 무엇을 왜 바꿨고 결과가 어땠는지 전달한다 | 결과를 공유받는 사람, 나중의 나 |

## 대상

| 입력 | 대상 |
|---|---|
| PR 번호·URL | `gh pr diff <번호>` |
| 브랜치·커밋 범위 | `git diff <기준>...<브랜치>` 또는 지정 범위 |
| workflow-ship에서 호출 | 토픽의 최종 diff와 토픽 폴더(BRIEF, DESIGN, EXPERIMENTS) |
| 지정 없음, 작업 트리 변경 있음 | 작업 트리 diff |
| 지정 없음, 작업 트리 깨끗함 | 현재 브랜치와 기준 브랜치. 변경이 없으면 대상을 묻는다 |

`docs/`, `.agents/`, `.claude/` 변경은 코드 서사를 흐리므로 설명 대상에서 빼고 배경 자료로만 쓴다.
개발자가 문서·스킬 변경 자체의 설명을 원하면 포함한다. 진행 중인 토픽의 일부를 설명하면 어느 태스크까지의
스냅샷인지 페이지 맨 위에 적는다.

## 사전 조사

- 변경 영역과 관련된 [docs/context](../../../docs/context/README.md) 문서를 먼저 읽는다.
- 변경 파일 주변 코드(호출자, 상태 enum, 테스트)를 읽어 문서와 현재 코드를 대조한다.
- 토픽 산출물이면 BRIEF의 합의·완료 요약과 DESIGN의 결정 표에서 설계 의도를 가져온다.

## 페이지 구성

한 페이지 세로 스크롤에 목차와 섹션 헤더를 둔다. 탭 구조는 쓰지 않는다. 맨 위에는 한 화면짜리 요약을 둔다:
무엇이 바뀌었나, 핵심 결정, 검증 결과, 읽는 순서. 요약에 다 올리지 못한 결정은 본문 어디에 있는지 적는다.

### 변경 설명

1. **배경**: 깊은 배경(입문자용, 아는 사람은 건너뛰어도 된다고 표시)과 좁은 배경(이 변경에 직접 닿는 부분)
2. **주제별 섹션**: 변경을 이해 단위(예: 결제 결과 불명, 동시 요청)로 나누고, 각 섹션 안에서 아래 순서로 닫는다.
   문제와 해결, 코드를 서로 다른 섹션으로 흩지 않는다.
   1. 문제: 예시 데이터로 그대로 두면 무엇이 깨지는지 보여 준다
   2. 처리: 이번 변경이 그것을 어떻게 막는지 짧은 설명과 그림으로
   3. 코드: 여기서 볼 것을 한 줄 적고 핵심 발췌만 보여 준다(파일 경로 표시)
   4. 확인: 이 경로를 확인한 테스트와 결과
3. **남은 위험**: 이번 변경이 막지 못하는 것과 조건

### 보고서

1. **요약**: 문제, 결과, 남은 일을 한 화면에. 페이지 맨 위 요약은 이 섹션으로 대신한다.
2. **전후 비교**: as-is와 to-be 흐름도, 바뀐 결정과 이유
3. **결과와 근거**: 명령별 검증 결과, 요구사항·장애 시나리오별 확인 케이스 표, 측정값(실험 토픽이면 회차별 표나 차트), 리뷰 처리
4. **남은 위험과 다음 단계**

## 문체

[문서 작성 기준](../../conventions/writing.md)을 따른다. 페이지에서 특히 지킬 것:

- 제목은 그 섹션의 결론을 직접 말한다("직관", "코드" 같은 범주 이름만 쓰지 않는다).
- 줄글이 길어지면 내용을 줄이지 말고 표, 목록, 그림, 접기로 바꾼다.
- 태스크 ID나 결정 ID 대신 내용으로 부른다.
- 예시 코드는 [stack.md](../../profiles/stack.md)의 코드 규칙을 따른다.

## 시각화

HTML의 표현력을 쓴다. 줄글로 설명하기 전에 그림이나 표로 보여 줄 수 있는지 먼저 본다.

| 용도 | 도구 |
|---|---|
| 상태 전이, 시퀀스, 흐름도 | Mermaid |
| 예시 데이터를 넣은 시나리오, 타임라인, 전후 비교 카드, 상태 뱃지, 비교표 | HTML/CSS |
| 긴 코드나 부가 설명 | `<details>` 접기 |
| 코드 | 언어별 구문 강조 |

- Mermaid에 데이터를 욱여넣어야 하면 HTML/CSS로 바꾼다.
- flowchart 노드 라벨은 큰따옴표로 감싼다. sequence·state 다이어그램의 메시지와 전이 라벨은 따옴표가 그대로
  보이므로 감싸지 않는다. 어느 라벨이든 `"`, `<`, `>`, `{`, `}`, `|`, `#`, `;`를 쓰지 않는다.
  Mermaid는 파일을 열기 전까지 렌더 실패를 알 수 없으므로 작성할 때 막는다.
- ASCII 다이어그램을 쓰지 않는다. 핵심 개념과 엣지 케이스는 콜아웃 박스로 강조한다.
- 코드 블록은 `<pre><code class="language-java">`로 쓰고 `<`, `>`, `&`를 이스케이프한다. 긴 줄은 `white-space: pre-wrap`으로 감싼다.

## 형식

- CSS와 JS를 포함한 단일 HTML 파일. 외부 리소스는 버전을 고정한 CDN 스크립트 두 가지만 허용한다:
  Mermaid(다이어그램), highlight.js(구문 강조, 라이트·다크 테마 CSS 포함).
- 휴대폰 폭에서도 읽히는 반응형 스타일, 라이트·다크 모드
- 저장 위치
  - 토픽에서 호출: 토픽 폴더(아카이브 후면 `docs/archive/<topic>/`)에 `CHANGE.html` 또는 `REPORT.html`
  - 단독 호출: `docs/explanations/YYYY-MM-DD-<slug>.html`
