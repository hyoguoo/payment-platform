# 토픽 workflow

전체 흐름도: [flow.md](flow.md)

## 시작과 재개

1. [docs/STATE.md](../../../docs/STATE.md)에서 요청과 관련된 진행 중 토픽을 찾는다.
   - 있으면 그 토픽 폴더의 BRIEF와 DESIGN의 "진행 기록"을 읽고, 끝난 단계를 반복하지 않고 다음 지점부터 이어간다.
     STATE에 브랜치가 적혀 있고 현재 브랜치와 다르면 그 브랜치로 전환한다. 전환 전에 아래 "작업 트리 확인"을 한다.
   - 없으면 새 토픽을 만든다. 이름은 UPPER-KEBAB-CASE, 폴더는 `docs/topics/<TOPIC>/`.
     만든 즉시 STATE의 "진행 중"에 항목을 추가한다(단계 discuss). 이후 단계가 바뀔 때마다 그 항목을 갱신한다.
2. 개발자가 단계를 지정하지 않은 새 토픽은 discuss의 0단계(요청과 요구사항 구체화)부터 시작한다.
   이미 합의된 목표·범위나 기존 DESIGN이 있으면 해당 단계부터 진행한다.
3. 현재 단계의 스킬만 읽는다. 다음 단계로 넘어갈 때 그 단계의 스킬을 읽는다.

| 단계 | 스킬 | 산출물 |
|---|---|---|
| 1. 설계 논의 | [workflow-discuss](../workflow-discuss/SKILL.md) | BRIEF(사전·합의), DESIGN(결정·장애 시나리오·검증 기준) |
| 2. 계획 | [workflow-plan](../workflow-plan/SKILL.md) | DESIGN의 태스크 목록 |
| 3. 구현 | [workflow-execute](../workflow-execute/SKILL.md) | 코드, 검증 결과, 진행 기록 |
| 4. 마무리 | [workflow-ship](../workflow-ship/SKILL.md) | 리뷰 처리, 문서 동기화, 완료 요약, 아카이브 |

## 개발자 확인 지점

단계 진행을 멈추고 승인받는 확인 지점은 아래 세 곳이다. 실험 모드는 1만 있다.

1. 사전 브리핑 승인 또는 정정 (discuss)
2. 합의 브리핑 확정 (discuss → plan). [진행 중 변경 요청](change-request.md)의 L3·L4a 재확정도 여기에 해당한다.
3. 리뷰 결과의 항목별 수정 여부 (ship). 남은 지적이 없으면 멈추지 않는다.

확인 지점 사이의 단계 전환은 승인 범위 안이면 묻지 않고 이어간다. 다만 아래 경우에는 확인 지점이 아니어도 멈추고 묻는다.

- discuss의 요청·요구사항 구체화 질의. 애매한 점이 없어질 때까지 필요한 만큼 한다
  ([질문하는 방법](../workflow-discuss/SKILL.md#질문하는-방법)).
- 합의 이후 아직 정하지 않은 제품 동작이나 범위 확장이 생길 때([진행 중 변경 요청](change-request.md)의 L2 이상).
  실험 모드에서 목표·판정 기준·고정 조건을 바꿀 때.
- 되돌리기 어려운 작업: 다른 작업의 변경이 섞인 작업 트리에서 브랜치 전환, 토픽을 닫을 때 남은 코드와 이슈 처리.

마지막에 HTML 변경 설명과 Git 게시 여부를 한 번 묻는다(ship).

단계나 확인 지점을 넘어갈 때는 묻지 않더라도 한 줄로 알린다. discuss·ship 안의 하위 단계도 포함한다
(discuss: 요구사항 질의 → 사전 브리핑 → DESIGN → 사전 점검 → 합의 브리핑, ship: 리뷰 → 수정 → 전체 검증 →
문서 동기화 → 완료 요약·아카이브). 예: `▶ discuss · 사전 브리핑 → DESIGN: 사전 브리핑 승인. 다음은 설계 상세.`

진행 범위: 개발자가 범위를 정하지 않고 토픽을 시작했으면, 확인 지점에서 승인을 받는 대로 다음 단계로 이어가
ship의 마지막 질문까지 진행한다. 합의 브리핑 확정은 그 설계의 계획과 구현을 승인한 것으로 본다.
"브리핑만", "계획까지만"처럼 범위를 제한했으면 그 산출물까지만 완성하고 멈춘다.

## 규모별 차이

| 규모 | discuss | plan | ship 리뷰 |
|---|---|---|---|
| 중간 | 사전 브리핑 → DESIGN → 합의 브리핑. risk.md 호출 조건에 해당하면 risk-reviewer 사전 점검 | DESIGN에 짧은 태스크 목록 | 변경 내용에 따른 검토 배정 |
| 큼 | 같음. 결정 표와 장애 시나리오를 더 자세히 쓴다 | 태스크마다 의존성·검증 명령·위험 표시 | 같음 |
| 실험 | 사전 브리핑에 측정 목표·판정 기준·고정 조건·첫 가설. DESIGN·합의 브리핑 없음 | 없음. 회차를 EXPERIMENTS.md에 기록 | 실험 중 바뀐 코드에 한해 같음 |

## 실험 모드

측정·튜닝처럼 결과를 보고 다음 작업이 정해지는 토픽에 쓴다. 결과를 미리 알 수 없으므로 to-be를 합의하는
합의 브리핑과 plan을 거치지 않는다.

1. 사전 브리핑에 측정 목표, 판정 기준(언제 끝내는가), 매 회차 고정할 조건, 첫 가설을 적고 승인받는다.
   이 승인이 확인 지점 1이자 실험 전체의 승인이다. 승인되면 이슈와 브랜치를 준비한다.
2. 회차마다 [EXPERIMENTS 템플릿](../../templates/EXPERIMENTS.md)에 가설 → 실행 → 결과 → 판단을 추가한다.
   계획 전체를 다시 쓰지 않는다. 코드를 바꾸는 회차는 execute의 검증 규칙을 따른다.
3. 회차가 끝나면 결과와 다음 가설을 짧게 보고하고, 목표·판정 기준·고정 조건 안이면 이어서 진행한다.
   목표나 판정 기준, 고정 조건을 바꿔야 하거나 승인 범위 밖의 코드 구조 변경이 필요하면 개발자에게 확인받고
   BRIEF의 사전 브리핑을 갱신한다.
4. 판정 기준을 충족하거나 개발자가 종료를 정하면 ship으로 간다. 리뷰 대상은 실험 중 남기기로 한 코드 변경이고,
   BRIEF의 완료 요약에는 회차 요약표와 채택한 변경을 적는다.

설계 결정이 필요한 코드 변경이 실험 중에 생기면 DESIGN을 만들어 결정과 근거를 기록한다.

## 진행 중 변경 요청

합의 브리핑 확정 뒤부터 PR 병합 전까지(아카이브 뒤 포함) 요구가 추가·변경되거나, 구현 중 개발자에게 물어야 할
범위 확장을 발견하면 [change-request.md](change-request.md)를 읽고 수준(L1~L4)을 정해 처리한다. 그 전에는 읽지 않는다.

## 이슈와 브랜치

토픽은 기본적으로 GitHub 이슈와 작업 브랜치로 추적한다. 개발자가 "이슈 만들지 마", "로컬에서만"처럼
명시한 경우에만 생략한다. 세부 규칙은 [Git 규칙](../../conventions/git.md)을 따른다.

1. 합의 브리핑이 확정되면(실험 모드는 사전 브리핑 승인 후) 열린 이슈와 브랜치를 확인하고, 같은 작업이 있으면 재사용한다.
2. 없으면 BRIEF의 문제·목표·요구사항·범위·완료 기준으로 이슈를 만든다.
3. execute에 들어가기 전에 작업 브랜치를 준비한다. 기존 미커밋 변경은 보존하되, 먼저 아래 "작업 트리 확인"을 한다.
4. 원격 저장소가 없거나 인증·권한 문제로 실패하면 이슈 본문을 DESIGN의 "진행 기록"에 남기고
   실패 사유를 STATE에 적은 뒤 로컬로 계속한다. 생성 후 오류가 나면 원격 상태를 먼저 조회해 중복 생성을 피한다.

이슈와 브랜치 준비는 푸시·PR·병합을 승인하지 않는다. 커밋은 [Git 규칙](../../conventions/git.md#커밋)의 커밋 시점을 따른다.

**작업 트리 확인**: 브랜치를 만들거나 전환하기 전에 `git status`로 미커밋 변경을 본다. 이 토픽의 변경(토픽 폴더,
DESIGN 태스크의 변경 위치)만 있으면 그대로 진행한다. 다른 토픽이나 개발자가 만든 변경이 섞여 있으면 전환하지 않는다.
어떤 파일이 어느 작업의 것인지 보여 주고, 먼저 커밋할지, stash할지, 그대로 함께 가져갈지 묻는다.
커밋 시점 사이에는 미커밋 변경이 남아 있는 것이 보통이고, 묻지 않고 전환하면 두 토픽의 변경이 한 브랜치에 섞인다.

## 토픽 닫기 (완료하지 않고 끝낼 때)

조사해 보니 필요 없는 일이었거나, 개발자가 중간에 접거나, 방향을 폐기해 토픽을 완료하지 않고 끝내는 경우다.
어느 단계에서 끝나든 "왜 하지 않았는지"를 남긴다. 다음에 같은 요청이 오면 discuss 0단계가 이 기록을 근거로 쓴다.

1. BRIEF의 "완료 요약"에 결과를 "닫음"으로 적고, 이유, 어디까지 진행했는지, 근거(파일:라인, 개발자 결정)를 쓴다.
2. 토픽 폴더를 `docs/archive/<topic-kebab>/`로 옮기고 [docs/archive/README.md](../../../docs/archive/README.md)에
   결과 "닫음"으로 한 줄을 추가한다. STATE에서 해당 항목을 지운다.
3. 브랜치에 코드 변경이 남아 있으면 버릴지, 브랜치째 남길지 개발자에게 묻는다. GitHub 이슈가 있으면 닫을지도 함께 묻는다.
   되돌리기 어려운 작업이므로 묻지 않고 처리하지 않는다.

## 문서와 STATE

| 문서 | 위치 | 작성 기준 |
|---|---|---|
| BRIEF | `docs/topics/<TOPIC>/BRIEF.md` | 개발자가 읽고 승인하는 문서. 각 섹션은 한 화면 안에 들어오게 쓴다. [템플릿](../../templates/BRIEF.md) |
| DESIGN | `docs/topics/<TOPIC>/DESIGN.md` | 에이전트가 근거와 작업 기록으로 쓰는 문서. 필요한 만큼 자세히 쓴다. BRIEF에서 합의하지 않은 결정은 넣지 않는다. [템플릿](../../templates/DESIGN.md) |
| EXPERIMENTS | `docs/topics/<TOPIC>/EXPERIMENTS.md` | 실험 모드에서만. [템플릿](../../templates/EXPERIMENTS.md) |
| STATE | `docs/STATE.md` | 진행 중인 토픽의 목차. 아래 형식만 쓴다. |

STATE의 토픽 항목은 아래 줄만 쓴다. 측정 결과, 판단 근거, 상세 재개 메모는 토픽 폴더(DESIGN의 "진행 기록"
또는 EXPERIMENTS)에 쓰고 STATE에는 쓰지 않는다.

```markdown
### <TOPIC> — <한 줄 설명>
- 규모·단계: <중간|큼|실험> · <discuss|plan|execute|ship> — <현재 태스크와 내용>
- 추적: <이슈 링크 또는 생략 사유> · 브랜치 `<이름>`
- 다음: <바로 다음 할 일>
- 막힘: <없음 또는 개발자 판단이 필요한 것>
- 문서: [BRIEF](topics/<TOPIC>/BRIEF.md) · [DESIGN](topics/<TOPIC>/DESIGN.md) (실험이면 EXPERIMENTS)
```

중단할 때는 DESIGN의 "진행 기록"에 완료한 일, 남은 일, 검증 상태, 다음 실행 지점을 남기고 STATE의
"다음" 줄을 갱신한다. 다른 토픽 항목은 건드리지 않는다. 상태 갱신만을 위해 커밋하지 않는다.

## 협업

[AGENTS.md](../../../AGENTS.md)의 서브에이전트 기준을 따른다. 메인은 설계, 분해, 결과 통합, 최종 검증과
보고를 맡는다. 검토 결과는 코드와 테스트 근거로 판단하고, 근거 없는 지적은 반영하지 않는다.
