# 토픽 워크플로우

`docs/STATE.md`에서 요청과 관련된 활성 토픽·단계·재개 메모를 확인한다. 이미 끝난 단계를
반복하지 않는다. 활성 토픽이 없고 사용자가 새 토픽을 요청하면 목적에 맞는 단계에서 시작한다.

## 단계 선택

| 요청 | 읽을 스킬 | 산출물 |
|---|---|---|
| 설계 논의 | [workflow-discuss](../workflow-discuss/SKILL.md) | `docs/topics/<TOPIC>.md` |
| 구현 계획 | [workflow-plan](../workflow-plan/SKILL.md) | `docs/<TOPIC>-PLAN.md` |
| 계획 구현 | [workflow-execute](../workflow-execute/SKILL.md) | 코드·검증 결과·진행 상태 |
| 검증·마무리 | [workflow-ship](../workflow-ship/SKILL.md) | 검토 결과·문서 동기화·아카이브 |

현재 단계의 스킬만 읽는다. 사용자가 특정 단계만 요청하면 그 산출물까지 완료한다.
구현이나 전체 완료를 요청했다면 그 범위 안에서 계속 진행한다. 설계·계획 요청 자체를
구현·커밋·외부 게시 권한으로 해석하지 않는다. 이미 받은 승인은 다시 묻지 않는다.

## 실행과 검토

[공통 협업 방식](../../roles/README.md)에 따라 메인이 설계·분해·결과 통합을 맡고,
분리 가능한 구현은 implementer, 독립 검토는 reviewer, 결제 위험은 domain-expert에 맡긴다.
작은 작업은 직접 처리한다. 위임 시 대상·판정 기준·허용 쓰기 범위를 명시하고 중복 편집을 피한다.
검토 결과는 코드와 테스트 근거로 판단한다. 도구가 없거나 상위 지침이 위임을 제한하면 같은
기준으로 직접 진행하고 독립 검토를 수행하지 못했다는 사실을 보고한다.

체크리스트는 해당 항목만 적용한다. 명백한 결함은 승인된 수정 범위에서 해결한다.
재검증은 수정된 경로와 남은 위험에 집중하고, 미해결 결정이나 환경 문제는 구체적으로 보고한다.
브리핑은 작업의 목적·결정·남은 일을 짧게 전달하고, 다이어그램은 분기·경계를 설명할 때 사용한다.

## 상태 기록

`docs/STATE.md`에는 활성 주제, 단계, 활성 태스크와 내용, 실제 존재하는 이슈·브랜치,
산출물 경로를 기록한다. 중단 시 완료/남은 작업, 검증 결과, 다음 실행 지점을 재개 메모에 남긴다.
완료 이력은 `docs/archive/<topic>/COMPLETION-BRIEFING.md`에 두고 최근 완료 링크는 최대 2개다.
다른 작업의 재개 메모를 지우지 않는다. 상태 갱신만을 위해 자동 커밋하지 않는다.
