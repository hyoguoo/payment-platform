# 구현 계획

진행 범위와 STATE 기록은 [workflow](../workflow/SKILL.md)를 따른다.

## 태스크 작성

DESIGN의 "태스크" 섹션에 쓴다. 별도 PLAN 파일은 만들지 않는다. 합의 브리핑과 DESIGN의 결정을 현재 코드와
대조하고, 설계 문서가 없는 계획 요청이면 받은 요구를 근거로 쓰되 가정을 표시한다.

각 태스크에는 다음을 적는다.

| 항목 | 내용 |
|---|---|
| ID와 제목 | `T1 — 결제 상태 전이 검증 추가`처럼 내용이 드러나게 |
| 변경 위치 | 모듈, 패키지, 주요 클래스 |
| 의존 | 먼저 끝나야 하는 태스크 |
| 완료 기준 | 관찰 가능한 결과. 관련 요구사항(R-n)과 장애 시나리오(FS-n)를 연결하고, [테스트 관점](../../conventions/testing.md)에서 해당하는 예외 케이스를 적는다 |
| 검증 | 실행할 명령. [stack.md](../../profiles/stack.md)의 순서대로 단위 테스트와 정적 분석, 배선을 바꾸면 통합 테스트까지 |
| tdd | true: 비즈니스 로직·상태 전이·버그 회귀. false: 문서·상수·단순 선언 |
| risk | true: risk.md의 핵심 경로나 불변식을 건드림 |

- 실행 순서는 실제 코드 의존 관계로 정한다. 레이어 이름만 보고 순서를 정하지 않는다.
- 각 태스크는 독립적으로 검증할 수 있는 크기로 나눈다. 태스크가 끝났을 때 전체 테스트가 통과해야 한다.
  인터페이스와 그 구현처럼 함께 있어야 동작하는 것은 같은 태스크에 둔다.
- 규모가 "중간"이면 태스크 수와 항목을 필요한 만큼만 쓴다. 의존이 없으면 생략한다.
- 분리해 맡길 수 있는 태스크 묶음(implementer 후보)을 표시한다. 쓰기 범위가 겹치지 않게 나눈다.

## 점검과 다음 단계

작성 후 직접 확인한다.

- BRIEF의 모든 요구사항, DESIGN의 모든 결정과 장애 시나리오가 어떤 태스크의 완료 기준에 반영됐는가
- 합의 범위 밖의 태스크나, 요구사항·결정에 연결되지 않는 태스크(미래 대비 추상화, 쓰이지 않을 설정 등)가 끼어들지 않았는가
- 이미 있는 코드로 대신할 수 있는 태스크를 새로 구현하게 하지 않았는가
- 각 태스크의 검증 명령이 실제로 그 변경을 확인하는가

STATE에 다음 태스크를 기록한다. 개발자가 범위를 계획까지로 제한했으면 태스크 목록을 전달하고 멈춘다.
그렇지 않으면([workflow의 진행 범위](../workflow/SKILL.md#개발자-확인-지점)) 브랜치 준비를 확인하고
[workflow-execute](../workflow-execute/SKILL.md)로 이어간다.
