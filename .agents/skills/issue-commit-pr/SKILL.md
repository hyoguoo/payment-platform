# 커밋과 GitHub 게시

요청이 커밋, 이슈, 푸시, PR 중 어디까지 포함하는지 기존 대화에서 확인한다.
[commit](../_shared/conventions/commit.md)과 [github](../_shared/conventions/github.md)의 해당 규칙을 읽는다.

1. `git status --short`, staged/unstaged diff, 필요하면 기준 브랜치 diff를 확인한다.
   미추적 파일과 기존 사용자 변경을 구분하고 이미 있는 이슈·PR·브랜치를 재사용한다.
2. 실제 변경과 검증 결과로 제목·본문을 준비한다. 필요한 검증은 게시 전에 마친다.
3. 요청 범위에 이슈 생성이 있으면 저장소·라벨·담당자를 확인해 생성한다.
   새 브랜치가 필요하면 이슈 번호가 있을 때 `#<번호>`를 사용하고, 없으면 내용을 나타내는 이름을 쓴다.
4. 커밋 대상 파일을 경로로 명시해 staging하고 staged diff를 검토한다.
   커밋이 요청되었으면 구현과 테스트를 함께 논리적 단위로 커밋한다.
5. 푸시·PR이 요청되었으면 해당 브랜치를 push하고 기존 PR을 갱신하거나 새 PR을 만든다.
   제목·본문은 최종 구현 기준으로 정리하고 실제 관련 이슈만 연결한다.

현재 제공된 GitHub 연결 도구 또는 인증된 `gh`를 사용한다. 사용 불가능한 MCP 도구명을
호출하지 않는다. 인증이 없으면 완성된 로컬 변경과 게시용 본문을 남기고 막힌 작업을 보고한다.
본문은 구조화된 도구 인자 또는 임시 파일과 `--body-file`로 전달한다.
작업이 일부 성공한 뒤 실패하면 원격 상태를 조회하고 미완료 단계만 재시도해 중복 생성을 피한다.
완료 보고에는 커밋·브랜치·생성한 URL과 미완료 작업을 적는다.
