# 설계 논의

공통 진행 범위와 상태 기록은 [workflow](../workflow/SKILL.md)를 따른다.

## 사용자와 논의

먼저 사용자가 해결하려는 문제와 이번 범위를 확인한다. 기존 답변과 명시적 요구는 재사용해 같은 질문을
반복하지 않는다. 목표·범위·제품 동작을 바꾸는 핵심 선택이 남아 있으면 사용자가 선택할 근거를 제시한다.
현재 세션에 질답 모듈이 있으면 적극 활용하고, 없으면 일반 대화로 질문한다.

- 한 번에 연결된 질문 1~3개를 제시하고, 대안의 효과·제약과 추천 이유를 짧게 설명
- 사용자 답변에 따라 다음 쟁점을 좁히며, 답하지 않은 핵심 선택을 기본값·시간 경과로 확정하지 않음
- 질문을 기다리는 동안 관련 코드·실패 경로를 조사하되, 사용자 판단에 의존하는 구현·게시를 앞서 진행하지 않음
- 조사와 서브에이전트 검토는 토론의 근거로 사용하며 사용자와의 목표·범위 합의를 대신하지 않음

핵심 목표·범위가 이미 명시돼 있으면 재확인을 위한 질문을 만들지 않는다.
파일명·문서 배치 같은 일상적 선택은 직접 한다. 확인한 범위로 토픽 이름을 UPPER-KEBAB-CASE로 정한다.

## 논의 기록과 검토

`docs/topics/<TOPIC>.md`에 문제, 영향 범위, 결정과 근거, 필요한 대안 비교,
장애 시나리오, 관찰 가능한 성공 기준, 검증 계획을 기록한다. 내용 없는 섹션은 만들지 않는다.
아키텍처 변경이면 `docs/context/ARCHITECTURE.md`에서 실제 포트 위치와 의존 방향을 확인한다.
결제 상태 변경이면 정상·중복·실패·복구 경로를 코드와 대조하고 필요한 전이도를 작성한다.

[discuss-ready](../_shared/checklists/discuss-ready.md)의 적용 항목으로 설계를 검토한다.
사용자 답변·명시적 요구로 확정한 내용, 에이전트의 제안·가정, 사용자 판단이 필요한 미결 사항을 구분한다.
논의 중 문서를 작성할 수 있지만 핵심 목표·범위·제품 동작의 선택이 남아 있으면 discuss 진행 중으로 기록한다.
문서 작성이나 독립 검토 통과만으로 discuss를 완료 처리하지 않는다.

핵심 선택이 합의되고 적용 체크리스트를 충족하면 논의 결과와 미결 사항을 요약하고 STATE에 다음 단계와
문서 경로를 기록한다. 이후 이슈 생성·plan·execute는 [workflow](../workflow/SKILL.md)의 진행 범위에 따른다.
이슈·브랜치·커밋이 요청에 포함돼 있으면 [GitHub 규칙](../_shared/conventions/github.md)과
[커밋 규칙](../_shared/conventions/commit.md)을 따른다.
