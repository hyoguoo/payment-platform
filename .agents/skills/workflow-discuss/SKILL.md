# 설계 논의

진행 범위, 확인 지점, STATE 기록은 [workflow](../workflow/SKILL.md)를 따른다.

## 질문하는 방법

discuss 전체에 적용한다. discuss의 목적은 개발자의 의도를 검증 가능한 요구사항과 결정으로 바꾸는 것이고,
애매한 것을 남긴 채 다음 단계로 넘어가지 않는다.

- 코드, [docs/context](../../../docs/context/README.md), 지난 토픽([archive](../../../docs/archive/README.md))으로
  답할 수 있는 것은 먼저 조사한다. 조사로 알 수 있는 것을 개발자에게 묻지 않는다.
- 한 번에 1~3개를 묻는다. 결과를 가장 크게 바꾸는 것부터 묻고, 답에 따라 다음 질문을 좁혀 이어간다.
  개수 제한은 한 번에 묻는 양이다. 애매한 점이 남아 있으면 라운드를 더 돈다.
- "어떻게 할까요?" 같은 열린 질문 대신 해석 후보나 선택지를 구체적인 예시와 함께 제시한다.
  질문마다 무엇이 달라지는지, 선택지별 효과와 제약, 추천과 이유를 붙인다. 선택지는 같은 기준(복잡도, 위험,
  되돌리기 비용, 이후 작업에 주는 영향)으로 비교해 트레이드오프가 드러나게 한다.
- 데이터 구조, 상태 모델, 새 인프라처럼 범위가 큰 결정은 질문 도구의 짧은 설명만으로 고르게 하지 않는다.
  대화에서 선택지 비교표와 예시를 먼저 보여 준 뒤 묻는다.
- 선택지형 질문은 질문 도구(AskUserQuestion)를 쓸 수 있다. 어떤 방식으로 받든 답은 BRIEF의 질문 목록에 기록한다.
- 답하지 않은 질문을 기본값이나 시간 경과로 확정하지 않는다. 개발자가 "알아서 해"라고 맡긴 항목은
  "위임"으로 기록하고, 에이전트가 정한 내용을 합의 브리핑에서 보여 준다.

무엇을 묻고 무엇을 직접 정할지는 아래 기준을 따른다. 어느 쪽인지 애매하면 묻는다.

| 반드시 묻는다 | 에이전트가 정하고 DESIGN에 기록한다 |
|---|---|
| 호출자·사용자에게 보이는 동작(응답, 오류, 상태 변화) | 내부 구조, 클래스·메서드 이름, 파일 배치 |
| 범위에 넣을지 뺄지 | 기존 규칙(stack.md, docs/context)으로 답이 정해지는 것 |
| 외부 계약: API·메시지 형식, 하위 호환 | 테스트 구성 방식 |
| 데이터 보존·삭제·마이그레이션 | 같은 결과를 내는 구현 방식 중 선택 |
| 성능과 정합성처럼 업무 판단이 필요한 트레이드오프 | |
| 새 외부 라이브러리·인프라(DB, 메시지 브로커, 캐시) 도입 | |
| 기존 동작을 바꾸는 것 | |

## 0. 요청과 요구사항 구체화

사전 브리핑을 쓰기 전에, 요청을 검증 가능한 요구사항으로 바꾼다. 요청이 짧거나 모호할수록 여기에 시간을 쓴다.
잘못 이해한 요청으로 브리핑과 설계를 쓰는 것이 가장 비싼 실패다.

1. 관련 코드와 문서를 읽고, 요청을 아래 관점으로 나눠 빈 곳을 찾는다.

| 관점 | 확인할 것 |
|---|---|
| 목적 | 왜 필요한가, 누가 쓰는가, 끝나면 무엇이 달라지는가 |
| 기존 기능 | 같거나 비슷한 기능, 재사용할 코드·유틸, 같은 문제를 다룬 지난 토픽의 결정이 이미 있는가 |
| 필요성 | 새로 만들지 않고 기존 기능 확장, 설정 변경, 운영 절차로 충분하지 않은가 |
| 기능 | 입력, 출력, 상태 변화, 정상 흐름 |
| 경계와 예외 | 잘못된 입력, 없는 대상, 중복·동시 요청, 외부 실패일 때 호출자에게 보이는 동작 |
| 비기능 | 성능·처리량, 보안·권한, 데이터 보존, 호환성 |
| 범위 | 이번에 하지 않는 것 |
| 완료 기준 | 무엇을 보면 끝났다고 판단하는가 |

2. 빈 곳 중 "반드시 묻는다"에 해당하는 것을 위 질문 방법으로 묻는다. 요청을 두 가지 이상으로 해석할 수 있으면
   해석 후보를 나란히 보여 주고 고르게 한다. 예: "주문 취소 API"라면 "결제 전 주문만 취소" vs "결제 후 환불까지 포함".
   목표(끝나면 무엇이 달라지는가)와 판정(무엇을 실행해 보면 끝났다고 믿을 수 있는가)이 요청에 없으면 첫 질문에 함께 묻는다.
   열린 질문 대신 목표 한 줄과 판정 시나리오 초안을 제시하고 고치게 한다.
3. 답을 반영해 요구사항을 R1, R2 … 로 정리한다. 각 요구사항은 관찰 가능한 문장으로 쓴다
   ("수량이 0 이하면 400과 오류 코드 INVALID_QUANTITY를 돌려준다"처럼). 이 목록이 BRIEF의 "요구사항"이 된다.

요청이 이미 구체적이면 빈 곳만 짧게 확인하고, 물을 것이 없으면 바로 사전 브리핑으로 간다.

조사해 보니 이미 있는 기능으로 충분하거나 한두 파일 수정으로 끝나는 일이면, 근거(파일:라인, 지난 토픽)를 보여 주고
토픽을 닫을지, 작은 작업으로 바로 처리할지, 그래도 토픽으로 진행할지 묻는다. 닫거나 작은 작업으로 바꾸면
[workflow의 토픽 닫기](../workflow/SKILL.md#토픽-닫기-완료하지-않고-끝낼-때)로 기록을 남긴다(작은 작업으로 처리했으면
그 사실과 변경 파일을 완료 요약에 적는다). 토픽 이름은 사전 브리핑 승인 전까지 내용에 맞게 바꿀 수 있다.

토픽 폴더를 만들 때 BRIEF를 템플릿으로 만들어 두고, 이 단계의 질문과 답도 BRIEF의 질문 목록에 기록한다.
세션이 끊겨도 질의를 이어 가기 위해서다. 정리한 요구사항은 사전 브리핑에 담아 함께 승인받는다.

## 1. 사전 브리핑 (확인 지점 1)

설계를 쓰기 전에 요구사항, 현재 상태, 문제를 짧게 보여 주고 방향을 맞춘다.
BRIEF를 쓰기 전에 [문서 작성 기준](../../conventions/writing.md)을 읽고 따른다(합의 브리핑도 같다).

1. 관련 코드와 docs/context를 읽어 현재 동작을 파악한다.
   추측으로 as-is를 그리지 않는다. 확인하지 못한 부분은 "미확인"으로 표시한다.
2. [BRIEF 템플릿](../../templates/BRIEF.md)의 "사전 브리핑" 섹션을 채운다.
   - 목표: 끝났을 때 달라져 있어야 하는 것 한두 줄
   - 판정: 0단계에서 정한 판정 시나리오. ship 전체 검증에서 실제로 실행한다
   - 요구사항: 0단계에서 정리한 R1, R2 …
   - as-is 흐름도: 이번 문제와 관련된 경로만, 노드 10개 안팎. 새 기능이면 기능이 붙을 지점을 그린다
   - 문제: 무엇이 왜 문제인지 3줄 안팎. 새 기능이면 왜 필요한지를 쓴다
   - 제안 방향: 한두 문장. 아직 확정이 아니다. 기존 기능을 쓰거나 고칠 수 있으면 그 방법을 먼저 적고,
     새로 만든다면 기존 것으로 부족한 이유를 한 줄 붙인다.
   - 결정이 필요한 질문: 아직 답을 받지 못한 것. 답을 받으면 질문 옆에 답과 날짜를 적는다.
   - 범위 밖, 제안 규모(중간/큼/실험)
3. 개발자에게 BRIEF 경로와 핵심 질문을 전달하고 답을 기다린다.
   - 답이 새 질문을 낳으면 다음 라운드로 묻고 BRIEF를 고쳐 다시 보여 준다.
   - 질문이 모두 답변·위임·보류(범위 밖으로 미룸) 중 하나가 되고 개발자가 승인하면 BRIEF의 상태를
     "승인됨 (날짜)"로 바꾼다. 미결 질문이 남은 채 승인으로 처리하지 않는다.
   - 기다리는 동안 관련 코드와 실패 경로를 조사할 수는 있지만, 답에 의존하는 설계·구현·이슈 생성은 하지 않는다.

개발자가 목표와 범위를 이미 명확히 준 경우에도 사전 브리핑은 만든다. 다만 질문 섹션은 비우고 승인만 받는다.
"브리핑만" 요청이면 여기서 멈춘다.

실험 모드면 제안 방향에 측정 목표, 판정 기준, 고정 조건, 첫 가설을 적는다. 승인되면 DESIGN과 합의 브리핑을
거치지 않고 [workflow의 실험 모드](../workflow/SKILL.md#실험-모드)로 넘어간다.

## 2. 설계 상세 (DESIGN)

사전 브리핑이 승인되면 [DESIGN 템플릿](../../templates/DESIGN.md)으로 설계를 쓴다. 에이전트가 이후 단계에서
근거로 쓰는 문서이므로 필요한 만큼 자세히 쓴다.

- 결정 표: 결정, 이유, 버린 대안. 각 결정은 개발자의 답, 승인된 브리핑, 위임 중 하나에 근거해야 한다.
  "에이전트가 정한다"에 해당하는 것만 근거 없이 정할 수 있고, "제안"으로 표시해 합의 브리핑에서 보여 준다.
  호출자에게 보이는 동작(응답 형식, 오류 코드, 검사 순서)은 여기에 해당하지 않는다.
- 설계 중에 "반드시 묻는다"에 해당하는 새 애매함을 발견하면 "제안"으로 넘기지 않는다. DESIGN 작성을 멈추고
  BRIEF의 질문 목록에 추가해 묻는다. 답이 요구사항을 바꾸면 사전 브리핑의 요구사항도 고친다.
- 영향 범위: 바뀌는 모듈, 포트·어댑터, 데이터 구조, 외부 계약. 아키텍처 변경이면 실제 의존 방향을 코드로 확인한다.
  설계가 기대는 프레임워크·라이브러리 동작이 미확인이면 DESIGN을 확정하기 전에 확인한다.
- 단순성: 결정마다 "버린 대안"에 요구사항을 만족하는 가장 단순한 방법을 넣고, 그것을 버렸다면 이유를 적는다.
  요구사항(R-n)이나 결정에 연결되지 않는 추상화, 설정값, 확장 지점, 범용화는 넣지 않는다.
  "나중에 필요할 수 있다"는 근거가 되지 않는다. 필요하다고 보면 질문으로 올린다.
- 장애 시나리오: 정상·중복·동시·부분 실패·복구 경로. 상태를 바꾸면 전이도를 넣는다.
  이 설계가 맞으려면 무엇이 참이어야 하는지(전제)를 적고, 전제가 깨질 때의 결과를 시나리오에 넣거나 범위 밖으로 명시한다.
  각 시나리오에 ID(FS-1, FS-2 …)를 붙이고, 관련 불변식(risk.md의 INV-n)을 연결한다.
- 검증 기준: 관찰 가능한 성공 조건과 그것을 확인할 테스트·측정. 요구사항(R-n)마다 확인 방법이 하나 이상 있어야 한다.

### risk-reviewer 사전 점검

risk.md가 비어 있는데 토픽이 상태 전이·영속 데이터·동시 요청을 다루면, 불변식 후보를 붙여 채울지 묻는다.
[risk.md의 호출 조건](../../profiles/risk.md#호출-조건)에 해당하면(영향 범위가 핵심 경로에 걸리면) DESIGN 초안을
risk-reviewer에게 사전 점검으로 맡긴다. 해당하지 않으면 규모가 "큼"이어도 메인이 risk.md의 위험 범주로 직접 점검한다.
요청 내용은 설계가 깨뜨릴 수 있는 불변식, 빠진 장애 시나리오, 검증 기준의 빈틈, 기존 보호 장치와 겹치는 장치다. 결과는 근거와 대조해 DESIGN에 반영하고, 반영하지 않은 지적은 이유와 함께 기록한다.
사전 점검은 최대 2회로 끝낸다. 사용량 제한 등으로 못 하면 메인이 같은 관점으로 점검하고 그 사실을 기록한다.

## 3. 합의 브리핑 (확인 지점 2)

BRIEF의 "합의 브리핑" 섹션을 [문서 작성 기준](../../conventions/writing.md)에 따라 채운다.

- to-be 흐름도: as-is와 같은 범위, 바뀐 부분을 표시. 바뀌는 핵심 로직(분기, 상태 판단, 실패 처리)은
  플로우차트로 따로 그리고 분기 끝에 결과(응답, 상태 변화)를 적는다.
- 확정된 결정: DESIGN 결정 표의 요약. "위임"으로 정한 항목은 모두 올리고, "제안"은 구조에 영향을 주는 것
  (새 패키지·모듈, 데이터 구조, 레이어 배치, 기존 코드 재사용·확장 여부)만 따로 표시해 확인받는다.
  이름, 파일 배치 같은 세부는 DESIGN에만 둔다.
- 완료 기준과 검증 방법(요구사항별), 남은 위험
- 미결 사항: 비어 있어야 확정을 요청할 수 있다. 개발자가 미룬 것은 "보류"로 이유와 함께 적고 docs/TODOS.md에도 남긴다.

개발자가 확정하면 BRIEF의 상태를 "확정됨 (날짜)"로 바꾸고 STATE를 plan 단계로 갱신하고 [workflow의 이슈와 브랜치](../workflow/SKILL.md#이슈와-브랜치)를
처리한 뒤 plan으로 넘어간다. 재논의가 필요하면 사전 브리핑으로 돌아가 바뀐 부분만 고친다.
문서 작성이나 사전 점검 통과만으로 discuss를 완료 처리하지 않는다.
