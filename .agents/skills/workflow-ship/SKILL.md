# 마무리

진행 범위와 STATE 기록은 [workflow](../workflow/SKILL.md)를 따른다. DESIGN(실험은 EXPERIMENTS)과 실제 변경 범위를 확인한다.
diff는 작업 브랜치와 기준 브랜치를 비교하고, 미커밋·미추적 파일도 포함한다.

ship 중이거나 아카이브 뒤 PR 병합 전에 요구가 추가되거나 바뀌면 workflow의
[진행 중 변경 요청](../workflow/change-request.md#ship-중에-들어온-경우)을 따른다. 리뷰 뒤에 변경 요청으로 코드가 바뀌면
리뷰부터 다시 한다(리뷰 지적 수정은 아래 6단계의 재검토로 끝난다).

## 1. 리뷰 (확인 지점 3)

1. 단위 테스트와 정적 분석을 먼저 실행해 결과를 확보한다. 이후 코드가 바뀌지 않으면 "2. 전체 검증"에서 재사용한다.
2. [review](../review/SKILL.md)의 검토 배정에 따라 reviewer와 risk-reviewer에게 같은 diff 스냅샷과 위 검증 결과를
   병렬로 맡긴다. risk-reviewer에게는 DESIGN의 장애 시나리오(FS-n)와 risk.md의 불변식을 점검 목록으로 준다.
   검토가 끝날 때까지 작업 트리를 고치지 않는다.
3. 결과를 근거와 대조해 하나의 목록으로 합친다. 중복은 묶고, 근거가 없는 지적은 이유를 붙여 제외한다.
4. 등급을 매긴다.

| 등급 | 기준 |
|---|---|
| critical | 불변식 위반, 데이터·금액 정합성 손상, 보안 문제, 장애 시나리오 미처리 |
| major | 요구 미충족, 회귀, 중요한 테스트 누락, 실패 경로 처리 미흡, 기존 기능과 중복돼 같은 규칙이 갈릴 수 있는 구현 |
| minor | 가독성, 작은 개선, 요구에 연결되지 않는 과설계·불필요한 코드, 범위 밖이지만 기록할 만한 것 |

5. 개발자에게 등급별 목록(파일:라인, 발생 조건, 영향, 수정 방향)을 보여 주고 항목별 수정 여부를 받는다.
   critical에는 수정 권고를 분명히 적는다. 남은 지적이 하나도 없으면 결정할 것이 없으므로 멈추지 않고,
   검토 범위와 한계를 보고에 적은 뒤 다음 단계로 간다.
6. 수정 승인된 항목을 고친다. 묶음이 크면 implementer에게 맡긴다. 수정분과 남은 위험에 한해 1회 재검토한다.
   수정분이 핵심 경로를 건드리면 risk-reviewer가, 아니면 reviewer가 재검토한다.
   같은 시점에 처리한 변경 요청이 있으면 그 diff도 이 재검토에 함께 넣는다.
7. DESIGN의 "리뷰 처리"에 항목, 등급, 결정(수정/보류/제외), 근거를 기록한다. 보류한 항목은 docs/TODOS.md에도 남긴다.

## 2. 전체 검증

[stack.md](../../profiles/stack.md)의 순서로 영향받는 모듈의 단위 테스트, 정적 분석, 필요한 통합 테스트를 실행한다.
이미 통과한 검사는 그 뒤로 코드와 환경이 바뀌지 않았을 때만 재사용한다. 환경 제약으로 못 한 검사는 사유와
남은 위험을 기록한다.

테스트와 별개로, BRIEF의 판정 시나리오를 실제로 띄운 애플리케이션에서 실행하고 결과를 완료 요약에 붙인다.
결과가 목표에 못 미치면 고치지 말고 [진행 중 변경 요청](../workflow/change-request.md) 기준으로 처리한다.

## 3. 문서 동기화

이번 변경이 사실과 다르게 만든 문서를 갱신한다.

- [docs/context](../../../docs/context/README.md)의 구조·흐름·규칙 문서
- README나 API 문서처럼 외부에 노출된 설명
- 새로 생긴 함정이나 규칙은 해당 context 문서에 추가

문서에 적힌 동작은 실제 코드로 다시 확인하고 쓴다. 바꿀 문서가 없으면 그렇게 판단한 근거를 진행 기록에 남긴다.
context 문서를 고르고 대조하는 절차는 [context-update](../context-update/SKILL.md)를 따른다.

## 4. 완료 요약과 아카이브

1. BRIEF의 "완료 요약" 섹션을 채운다: 문제와 결과, 주요 결정, 실제 검증 근거, 리뷰 처리 요약, 남은 일.
   합의 뒤 변경 요청(C-n)이 있었으면 주요 결정과 검증 표에 그 결과를 함께 넣는다.
   개발자가 이 섹션만 읽고도 무엇이 바뀌었는지 알 수 있게 [문서 작성 기준](../../conventions/writing.md)을 따른다.
   검증 근거는 명령별 결과와 요구사항·장애 시나리오별 확인 케이스 표로 쓴다.
2. 토픽 폴더를 `docs/archive/<topic-kebab>/`로 옮긴다. 추적 중인 파일은 `git mv`를 쓴다. 문서 안의 상대 링크를 고친다.
3. [docs/archive/README.md](../../../docs/archive/README.md)에 한 줄을 추가한다: 폴더, 한 줄 설명, 결과(완료), 기간, 이슈.
4. STATE에서 해당 토픽 항목을 지우고 "최근 완료"에 링크를 남긴다(최대 2개 유지). 다른 토픽 항목은 건드리지 않는다.

## 5. 마지막 질문

완료 보고(결과, 검증, 아카이브 위치, 남은 일)와 함께 한 번에 묻는다. 검증은 AGENTS.md "구현과 검증"의 완료 보고 형식
(명령별 건수, 확인 케이스 표)으로 쓴다.

- HTML 변경 설명이나 보고서를 만들지. 원하면 [explain-change-html](../explain-change-html/SKILL.md)로 만든다.
- 푸시·PR을 진행할지(커밋은 커밋 시점마다 이미 했다). 원하면 [Git 규칙](../../conventions/git.md)으로 진행하고
  PR 본문에 이슈를 연결한다.
  변경 이슈가 있으면 함께 연결한다.

이미 요청 범위에 포함돼 있던 항목은 묻지 않고 진행한다.
