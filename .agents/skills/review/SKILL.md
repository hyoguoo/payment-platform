# 코드 리뷰

## 대상

개발자가 지정한 diff를 기준으로 한다. 지정이 없으면 `git status --short`, staged·unstaged diff, 미추적 파일을 본다.
작업 트리가 깨끗하면 현재 브랜치와 기준 브랜치의 차이를 본다. 변경이 없으면 임의로 과거 커밋을 고르지 않고 대상을 묻는다.

## 검토 배정

| 변경 내용 | 검토 |
|---|---|
| [risk.md의 호출 조건](../../profiles/risk.md#호출-조건)에 해당(핵심 경로를 건드림) | risk-reviewer + reviewer, 같은 diff 스냅샷으로 병렬 |
| 의미 있는 로직 변경 | reviewer |
| 문서·테스트·설정만 변경 | 메인이 직접 |

risk-reviewer를 부를지는 risk.md의 호출 조건만으로 정한다. 프로필의 불변식이나 핵심 경로가 비어 있으면 부르지 않고,
reviewer와 메인이 위험 범주로 점검한다.
이미 reviewer나 risk-reviewer로 호출된 서브에이전트는 직접 검토하고 다시 위임하지 않는다.
검토자에게는 메인이 실행한 테스트·정적 분석 결과를 함께 준다. 같은 작업 트리에서 검토자 여럿이 빌드를 동시에
돌리면 빌드 산출물과 잠금이 충돌하므로, 검토자는 빌드·테스트를 다시 실행하지 않고 받은 결과와 코드로 판단한다.
서브에이전트를 쓸 수 없으면 메인이 같은 기준으로 검토하고 결과에 "독립 검토 미실시"를 적는다.

## 기준

- 요구와 설계(있으면 DESIGN의 결정·완료 기준)를 충족하는가
- 회귀: 기존 호출 경로, 공개 계약, 데이터 형식이 깨지지 않는가
- 테스트: 바뀐 동작과 실패 경로를 테스트가 실제로 확인하는가. 테스트 결과가 없으면 "미검증"으로 표시한다.
- 서버 백엔드 공통 위험: risk.md의 위험 범주 중 이번 변경에 해당하는 것
- 중복: 이미 있는 기능·유틸·검증 로직과 같은 일을 새로 구현하지 않았는가. 같은 규칙이 두 곳에 생겨 나중에
  갈라질 수 있으면 결함이다(ship 등급 major).
- 과설계: 요구사항이나 결정에 연결되지 않는 추상화, 설정값, 확장 지점, 쓰이지 않는 코드가 있는가(ship 등급 minor).
  "더 일반적으로 만들 수 있다"는 지적은 하지 않는다. 지금 요구에 비해 불필요한 것만 지적한다.
- 스타일은 정적 분석 결과에 맡기고 결함으로 올리지 않는다.

## 보고

실질적인 결함만 영향도 순으로 보고한다. 각 항목에 다음을 적는다.

- 파일:라인
- 발생 조건: 어떤 입력·순서·장애에서 문제가 되는가
- 영향
- 수정 방향

취향과 추측을 결함으로 만들지 않는다. 결함이 없으면 그 사실과 검증 한계(실행하지 않은 테스트, 확인하지 못한 경로)를 적는다.
workflow-ship에서 호출됐으면 등급(critical/major/minor) 분류는 ship 스킬을 따른다.

검토만 요청받았으면 코드를 고치지 않는다. 수정까지 요청받았으면 승인된 범위에서 고치고 바뀐 경로를 다시 검증한다.
