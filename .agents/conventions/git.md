# Git 규칙

이슈 생성과 브랜치 준비는 workflow 토픽에서 기본으로 수행한다([workflow](../skills/workflow/SKILL.md#이슈와-브랜치)).
푸시·PR·병합은 요청받았을 때만 한다. 커밋은 workflow 토픽이면 아래 커밋 시점에 하고, 그 밖에는 요청받았을 때만 한다.
GitHub 작업은 인증된 `gh`나 연결된 도구로 하고, 시작 전에 저장소의
기존 이슈·PR·브랜치를 확인해 중복 생성을 피한다.
작업이 일부 성공한 뒤 실패하면 원격 상태를 먼저 조회하고 남은 단계만 다시 한다. 인증·권한이 없으면 게시용 본문을 로컬에 남기고
막힌 단계와 이유를 보고한다. 지금 세션에 없는 도구 이름을 부르지 않는다. 이슈·PR 댓글은 요청받았을 때만 단다.

## 이슈

- 제목은 작업 내용을 나타내는 한글로 쓴다. 토픽 이름이나 태스크 ID를 제목에 넣지 않는다.
- 본문은 BRIEF에서 가져온다: 문제, 목표, 요구사항, 범위(범위 밖 포함), 완료·검증 기준. 명사형 헤더와 `~다` 문체를 쓴다.
  본문은 [문서 작성 기준](writing.md)을 따른다.
- 합의 뒤 변경 요청(L3·L4a)은 기존 이슈를 고쳐 쓰지 않고 변경 이슈를 추가한다
  ([진행 중 변경 요청](../skills/workflow/change-request.md#변경-이슈-l3l4a)). 본문 첫 줄에 기존 이슈를 링크한다.
- 저장소에 실제로 있는 라벨과 확인된 담당자만 지정한다. 권한이나 라벨이 없으면 그 제한을 보고한다.

## 브랜치

- 기존 작업 브랜치가 있으면 그것을 쓴다. 새 브랜치의 기준은 `main`이며, 다른 기준을 요청받으면 따른다.
- 이름은 `<type>/<이슈 번호>-<요약>`이다. 이슈가 없으면 `<type>/<요약>`으로 쓴다.
  - `<type>`은 커밋 type과 같은 목록에서 고른다(`feat`, `fix`, `refactor`, `docs`, `chore` 등).
  - `<요약>`은 영문 소문자 kebab-case 2~4단어다. workflow 토픽이면 토픽 이름을 줄여 쓴다.
  - 예: `feat/12-order-cancel`, `fix/order-quantity-validation`
- 미커밋 변경을 버리지 않는다. main에 직접 push하지 않고, 강제 push를 스스로 선택하지 않는다.

## 커밋

- 파일 경로를 지정해 staging하고 staged diff를 확인한다. 무관한 사용자 변경과 비밀 파일(`.env`, 키, 토큰)을 제외한다.
- 구현과 그 동작을 검증하는 테스트를 같은 커밋에 둔다. 실패 테스트만 따로 커밋할 필요는 없다.
- 형식: `<type>(<scope>): <한글 제목>`, 제목 70자 이내. 본문에는 변경 이유를 쓴다.
  - type: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style`, `perf`, `build`
  - scope: [stack.md](../profiles/stack.md) 모듈 표의 scope(`payment`, `pg`, `product`, `user`, `gateway`, `eureka`) 또는 `docs`, `build`, `infra`, `deps`.
    한 범위로 묶이지 않으면 생략한다. 토픽 이름이나 태스크 ID를 scope로 쓰지 않는다.
- 기본은 새 커밋이다. 기존 커밋 수정(amend, rebase)은 요청받았을 때만 한다. 검증 hook을 우회하지 않는다.
- 작성자 표기(Co-Authored-By 등)는 세션의 지시를 따른다. 모델명이나 이메일을 지어내지 않는다.
  Codex는 `Co-Authored-By: Codex <noreply@openai.com>`을 쓴다.
- workflow 토픽에서는 아래 시점에 작업 브랜치에 커밋한다. 이력만 보고도 설계 → 구현 → 변경 순서를 따라갈 수 있게 하기 위해서다.
  - 합의 브리핑 확정 후 브랜치를 준비하면: BRIEF·DESIGN
  - 태스크 완료: 태스크 검증이 통과한 뒤 그 태스크의 구현·테스트와 DESIGN 결과 기록. 실패하는 상태는 커밋하지 않는다
  - 변경 요청 재확정(L3·L4a): 바뀐 BRIEF·DESIGN. 이후 코드 수정은 다시 태스크 단위로 커밋한다
  - ship: 리뷰 수정 묶음마다, 그리고 아카이브
- 상태 갱신만을 위한 커밋(STATE만 바뀐 경우 등)은 만들지 않는다.
- hook이 실패하면 원인을 고치고 실제 Git 상태를 확인한 뒤 다시 커밋한다.

## PR

- 변경에 맞는 검증을 마치고 결과를 본문에 적는다. 검증하지 못한 것이 있으면 본문에 밝히고 draft로 만든다.
- 제목: `<type>: <한글 요약>`. 본문은 문제와 최종 동작을 먼저 쓰고, 필요한 구현·검증 근거를 덧붙인다.
  본문은 [문서 작성 기준](writing.md)을 따른다.
- 관련 이슈가 있을 때만 `Closes #<번호>`를 쓴다. 변경 이슈가 있으면 기존 이슈와 함께 한 PR에서 닫는다.
- 파일, 수치, 성공 여부는 실제 diff와 실행 결과를 근거로 쓴다. 동시성·분기·경계는 다이어그램으로 설명한다.
- 여러 줄 본문은 `--body-file`로 전달한다.
- 리뷰 수정은 새 커밋으로 기록하고, PR 제목과 본문은 최종 구현 기준으로 다시 정리한다.
- 병합은 명시적으로 요청받았을 때만 한다.
