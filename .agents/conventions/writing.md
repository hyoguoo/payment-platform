# 문서 작성 기준

사람이 읽는 문서에 적용한다: BRIEF(브리핑, 완료 요약), HTML 변경 설명·보고서, PR·이슈 본문, 길어진 보고.
DESIGN, STATE는 에이전트가 근거와 기록으로 쓰고 읽는 문서라 정확성만 지키면 된다. 개발자는 이 문서를 직접 읽기보다
필요한 내용을 에이전트에게 묻는다.

목표는 독자가 문장을 해석하는 데 힘을 쓰지 않고 사실과 판단 근거에 집중하게 하는 것이다.
잘 쓴 문장이라는 인상보다 내용을 이해하기 편하다는 인상이 들어야 한다.

## 문서는 그것만 읽어도 이해돼야 한다

CLI 대화에서는 개발자가 되물을 수 있지만 문서는 그렇지 않다.

- 결론부터 쓴다. 섹션 첫 문장에서 무엇을 말하려는지 드러낸다.
- 내부 ID(D9, FS-8, R3, "질문 14")를 단독으로 쓰지 않는다. 처음 나올 때 내용을 함께 적는다.
  예: "결제·취소 동시 요청(FS-8)".
- 문제를 꺼냈으면 같은 자리에서 닫는다: 무엇이 문제인가 → 어떻게 처리했나 → 어디서(코드·테스트) 확인했나.
  문제만 나열하고 해결은 다른 섹션에서 설명하면 독자가 둘을 이어 붙여야 한다.
- 코드 블록 앞에는 그 코드에서 무엇을 볼지 한 줄로 적는다. 설명 없이 코드를 먼저 보여 주지 않는다.
- 독자가 추론해야 하는 전제를 빼먹지 않는다. 앞 섹션의 결론이 다음 섹션의 출발점이 되게 순서를 짠다.

## 줄글보다 구조와 그림

- 비교는 표로, 흐름과 상태는 다이어그램으로, 시간 순서는 타임라인으로 보여 준다.
- 핵심 로직(요청 하나가 거치는 분기, 상태 판단, 실패 처리)은 플로우차트로 그린다. 각 분기 끝에 결과(응답, 상태 변화)를 적는다.
- 문단은 한 가지 내용만 다룬다. 문단이 길어지면 내용을 줄이지 말고 목록, 표, 하위 섹션으로 나눈다.
- 표나 그림으로 이미 전달한 내용을 문장으로 반복하지 않는다.

## 숫자 기준은 상한이 아니다

문서와 스킬에 나오는 숫자("한 화면", "노드 10개 안팎", "핵심 2~3개" 등)는 구조를 나눌지 점검하라는 신호다.
숫자를 맞추려고 내용을 빼지 않는다.

- 기준을 넘으면 먼저 구조를 바꾼다: 표로 묶기, 하위 섹션으로 나누기, `<details>` 접기, 상세 문서로 옮기고 링크하기.
- 요약에 일부만 올리면 나머지가 어디 있는지 적는다(예: "나머지 3건은 아래 표"). 요약에 없다고 문서에서 사라지면 안 된다.
- 판단에 필요한 전제, 예외, 트레이드오프, 실패 경로는 길이와 상관없이 남긴다.

## 문장

이 절은 [위키·포스팅 작성 기준](../skills/writing/references/style-guide.md)의 문장 원칙을 줄인 것이다. 위키, 포스팅, README처럼 밖에 공개하는 글은 그 기준을 따른다.

| 원칙 | 수정 전 | 수정 후 |
|---|---|---|
| 번역체(명사화, 수동, 추상명사 연결)를 한국어 어순으로 | 원인 설명은 별도의 검증이 필요할 수 있다 | 원인은 따로 검증해야 한다 |
| 추상적인 표현을 실제 대상과 동작으로 | 외부의 비가역적 효과를 내부 상태 변경이 취소할 수 없다 | PG가 승인한 결제는 주문을 PENDING으로 되돌려도 취소되지 않는다 |
| 장식적 비유·의인화를 빼고 직접 말한다 | 락이 주문을 지키는 문지기 역할을 한다 | 같은 주문의 결제와 취소를 한 번에 하나씩 처리한다 |
| 제목은 내용을 직접 설명한다 | 돈과 주문 상태가 어긋나는 순간들 | 결제 결과를 모를 때 취소하면 승인이 남는다 |
| 근거 없이 단정하지 않는다 | 동시성 문제를 완벽하게 해결했다 | 같은 주문의 동시 요청은 직렬화된다. 서버가 여러 대면 해당하지 않는다 |

- 무엇이(데이터·상태·컴포넌트), 왜(원인·제약), 어떻게(동작·결과)가 드러나게 쓴다.
- 사실, 측정 결과, 해석, 추측을 구분한다. 확인하지 않은 것은 "미확인"이라고 쓴다.
- 접속사를 억지로 붙이지 말고 설명 순서로 문장을 잇는다.
- 기술 설명은 `~한다`, `~이다`로 쓴다. 가르치려는 어조, 감탄, 수사적 질문을 쓰지 않는다.
- 캐시, 큐, 타임아웃, 재시도처럼 익숙한 용어는 그대로 쓰고, 코드 식별자·상태값·설정값은 원형을 유지한다.

## 줄여도 되는 것과 남겨야 하는 것

| 줄인다 | 남긴다 |
|---|---|
| 같은 결론의 반복, 일반론 도입·마무리, 의미 없는 수식어, 장식적 강조 | 판단에 필요한 전제, 제약과 예외, 선택 근거, 트레이드오프와 실패 가능성, 검증 방법과 조건 |

중요한 설명이면 문장이 길어져도 된다. 짧게 만드는 것 자체가 목표가 아니다.

## 기존 문서를 고칠 때

- 기술적 사실, 수치, 조건, 트레이드오프, 코드 식별자를 바꾸지 않는다. 오류가 의심되면 고치지 말고 따로 보고한다.
- 이미 자연스러운 문장, 수정 이유를 설명할 수 없는 문장은 그대로 둔다.
