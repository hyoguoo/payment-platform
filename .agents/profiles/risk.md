# 위험 프로필

risk-reviewer가 지키는 대상이고, risk-reviewer를 언제 부르는지 정하는 유일한 기준이다.
프로젝트마다 "불변식"과 "핵심 경로"를 채운다.

## 호출 조건

| 상황 | 검토 |
|---|---|
| 불변식과 핵심 경로가 채워져 있고, 변경(또는 DESIGN의 영향 범위)이 핵심 경로를 건드림 | risk-reviewer 호출. discuss에서는 설계 사전 점검, ship에서는 마무리 리뷰 |
| 핵심 경로를 건드리지 않음 | 호출하지 않는다. 규모가 "큼"이어도 같다 |
| 불변식이나 핵심 경로가 비어 있음 | 호출하지 않는다. 메인과 reviewer가 아래 위험 범주로 점검한다 |
| 개발자가 위험 검토를 직접 요청함 | 프로필 상태와 상관없이 호출한다 |

핵심 경로 해당 여부는 변경 파일 경로를 아래 glob 패턴과 대조해 정한다. 패턴에 걸리는지 애매하면 포함한다.
표에 주석(`<!-- -->`)으로 된 예시 행만 있으면 비어 있는 것으로 본다.

## 불변식

시스템이 어떤 상황(재시도, 동시 실행, 부분 실패, 재기동)에서도 지켜야 하는 규칙이다. ID는 DESIGN의 장애 시나리오와
리뷰에서 참조하므로 바꾸지 않는다. 폐기할 때는 지우지 않고 "폐기"로 표시한다.

| ID | 불변식 | 깨지면 생기는 일 |
|---|---|---|
| INV-1 | 같은 결제는 PG에 한 번만 승인을 요청하고, 승인은 한 번만 반영된다. 요청·메시지가 다시 와도 같다 | 이중 결제 |
| INV-2 | 종결 상태(`DONE`, `FAILED`, `CANCELED`, `PARTIAL_CANCELED`, `EXPIRED`)로 간 결제는 다른 상태로 되돌아가지 않는다 | 승인된 결제가 실패로 보이거나 다시 승인됨 |
| INV-3 | PG의 "이미 처리됨" 응답은 주문 ID·금액·상태를 대조한 뒤에만 성공으로 본다 | 다른 주문이나 다른 금액의 승인을 성공으로 처리 |
| INV-4 | 승인 금액은 주문 금액과 같다 | 금액 불일치 |
| INV-5 | 재고 차감과 복구(보상)는 주문·상품마다 한 번만 반영된다. 보상을 다시 실행해도 결과가 같다 | 재고 과다·과소 |
| INV-6 | 결과를 모르는 결제(타임아웃 등)를 실패로 확정하지 않는다. 확인 경로를 거쳐 종결한다 | 승인됐는데 실패 처리, 재고만 복구 |
| INV-7 | 로그·응답·메시지에 결제 키·카드 정보·비밀 값이 남지 않는다 | 민감정보 노출 |

## 핵심 경로

glob 패턴으로 적는다.

| 경로 | 관련 불변식 |
|---|---|
| `payment-service/src/main/java/**` | INV-1 ~ INV-7 |
| `payment-service/src/main/resources/lua/**` | INV-5 |
| `pg-service/src/main/java/**` | INV-1, INV-3, INV-4, INV-6, INV-7 |
| `product-service/src/main/java/**/*Stock*` | INV-5 |
| `product-service/src/main/java/**/messaging/**` | INV-5 |
| `*/src/main/resources/db/migration/**`, `*/src/main/resources/db/schema/**` | 데이터 전체 |
| `*/src/main/resources/application*.yml` 중 Kafka·트랜잭션·재시도·타임아웃 설정 | INV-1, INV-5, INV-6 |

## 위험 범주 (서버 백엔드 기본)

risk-reviewer와 reviewer가 쓰는 점검 관점이다. 이 프로젝트에 해당하지 않는 범주는 "해당 없음"으로 표시하고,
프로젝트 고유의 주의점은 "프로젝트 메모"에 적는다.

| 범주 | 점검 질문 | 프로젝트 메모 |
|---|---|---|
| 데이터 정합성·트랜잭션 | 하나의 업무 단위가 하나의 트랜잭션 경계 안에서 확정되는가. 커밋 전에 외부에 결과를 알리지 않는가 | 결제 상태 변경과 발행 행(Outbox) 저장이 같은 트랜잭션에서 확정되는지, broker 도달 전에 발행 완료로 표시하지 않는지 본다 |
| 멱등성·재시도 | 같은 요청·메시지가 다시 와도 결과가 한 번만 반영되는가. 재시도가 중복 부작용을 만들지 않는가 | 멱등 키의 수명과 충돌, Kafka 재전송, 보상·취소의 반복 실행을 본다 |
| 동시성 | 동시 요청에서 경쟁 조건, 잃어버린 갱신, 데드락이 없는가. 락·버전·고유 제약이 실제로 막는가 | 상태 조회 폴링과 이벤트 처리의 경합, 같은 주문의 결제·취소 동시 요청을 본다 |
| 부분 실패·복구 | 중간 단계 실패 후 상태가 일관되게 남는가. 보상이나 재처리 경로가 있고 그것도 멱등한가 | 재고 선차감 뒤 결제 실패, 승인 뒤 결과 발행 실패, 재시도 소진 뒤 격리(DLQ) 경로를 본다 |
| 보안·권한·민감정보 | 인증·인가가 모든 진입점에 걸리는가. 로그·응답·예외 메시지에 민감정보가 새지 않는가 | INV-7 |
| API·데이터 호환 | 공개 API, 메시지 형식, DB 스키마 변경이 기존 소비자와 롤백을 깨지 않는가. 마이그레이션이 되돌릴 수 있거나 안전한가 | Flyway 마이그레이션은 이미 적용된 파일을 고치지 않는다 |
| 외부 연동 | 타임아웃, 재시도, 서킷 차단이 있는가. 외부의 "이미 처리됨" 같은 응답을 검증 없이 성공으로 보지 않는가 | INV-3, INV-6. 타임아웃 뒤 상태 불명, 재시도 종료와 그 부작용을 본다 |
| 관측성 | 실패 경로에 원인을 추적할 로그·지표·trace가 남는가. 알람이 필요한 상태를 감지할 수 있는가 | |
| 성능·자원 | N+1 조회, 무한 대기, 커넥션·스레드 고갈, 큰 결과의 메모리 적재가 없는가 | |
